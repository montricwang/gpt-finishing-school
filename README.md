# GPT Finishing School

一套用于规范 ChatGPT 输出的个人提示词与行为规范。

这个仓库主要解决一个问题：**怎样让 ChatGPT 按预期说话、排版、组织文档，并在不同任务中保持稳定的表达与工作方式。**

它不是一个单体 Prompt，而是一组按职责拆分、可以组合加载的规范。核心规则负责跨场景的语言与排版，扩展规则负责技术文档、审校流程和特定内容类型。

## 目录结构

### 核心规范

跨项目、跨领域使用的基础规则。

- **中文表达**：规定中文回答的基本表达原则，包括如何直接回答当前问题、控制篇幅、使用术语、组织句子，以及避免不必要的抽象化和重复总结。
- **对话排版**：规定 ChatGPT 普通对话中的 Markdown 排版，包括自然段、标题、列表、表格、粗体、引用块和代码格式等。
- **文档排版**：规定较长 Markdown 文档、学习笔记、报告和说明文的全文结构、章节关系与版式选择。
- **技术文档**：在通用表达与文档排版之上，规定技术学习文档怎样选择定义、表格、流程图、代码、输出与自然段等表达形式。

### 技术文档插件

用于进一步约束工程与技术学习文档。它们依赖核心规范，并按当前知识对象选择性加载。

- **技术对象**：用于介绍系统、框架、组件、协议等技术对象。
- **工程方法**：用于解释调试、测试、设计、排障等工程方法。
- **工程专题**：用于组织跨多个对象或机制的技术专题。
- **工程文档风格**：统一工程学习文档的阅读入口、总图与局部图节奏、章节推进方式和收尾体验。

### 审校与工作流

用于对已有回答或文档做专项检查，而不是替代起草规范。

- **行文审校**：检查中文表达、句法、重复、抽象化和行文摩擦。
- **排版审校**：检查 Markdown 结构和版式是否准确反映内容关系。
- **术语审校**：检查术语、缩写、中英文主称和技术字面量。
- **多模型审查**：用于组织不同模型参与复核和交叉检查。
- **Obsidian**：记录与 Obsidian 相关的文档整理与工作流约定。
- **教学与开发协作手册**：记录跨项目的 AI 辅助开发、工程学习、评测、文档归档与人机分工原则；具体项目事实仍留在各自仓库。

### 文学鉴赏

面向特定内容类型的扩展规范。

- **诗词鉴赏与典故考证规范**：用于诗词阅读、鉴赏、典故核查与相关文学讨论。

## 使用方式

根据任务加载必要的上位规范和领域扩展，而不是默认将整个仓库一次性塞进上下文。

例如：

- 普通聊天：中文表达 + 对话排版
- 正式长文：中文表达 + 文档排版
- 技术学习文档：中文表达 + 文档排版 + 技术文档 + 对应技术文档插件
- 文档冻结前检查：在起草规范之外，按需追加行文、排版或术语审校
- 诗词讨论：核心规范 + 对应文学鉴赏规范
- AI 结对开发 / 工程学习：教学与开发协作手册 + 当前项目自身的开发、架构与测试文档

具体依赖关系以各文档头部的「依赖」「被依赖」「配合」等说明为准。

## 版本管理

仓库中的文件名保持稳定，**不再在文件名中写版本号**。例如始终使用：

```text
中文表达.md
对话排版.md
文档排版.md
```

当前 `main` 分支代表现行有效版本。修改历史交给 Git 保存，不再通过复制 `v0.3`、`v0.4` 文件维护旧版；《教学与开发协作手册》同样固定使用 `教学与开发协作手册.md`，不再附日期或“第几次修订”等后缀。

维护时优先使用：

- **Commit**：记录一次已经落实的规则修改；
- **Issue**：记录观察到的 ChatGPT 输出问题、待讨论规则、Bad Case 或改进方向；
- **Branch / Pull Request**：处理较大的规范重构，在合并前查看 diff 和讨论修改；
- **Tag / Release**：在需要时标记整套规范的稳定阶段。

因此，一条规则最好能够追溯到「发现了什么问题 → 怎样讨论 → 修改了哪份规范 → 哪个 commit 落地」。

## 维护原则

现行目录只保留当前有效规则。Git 历史已经能够承担旧版本保存和差异比较，因此不在仓库中另建按版本复制的历史文件夹。

规范本身也应保持职责清楚：公共规则只维护一份，下游规范通过依赖关系继承，不重复复制。发现 ChatGPT 的新问题时，可以先建立 Issue；只有形成稳定、可复用的解决原则以后，再进入正式规范。
