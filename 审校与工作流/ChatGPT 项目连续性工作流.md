# ChatGPT 项目连续性工作流

**状态**：第一版  
**适用范围**：长期使用 ChatGPT 参与软件开发、研究、学习或其他需要跨多轮、多对话连续推进的项目。  
**目标**：把长期连续性从单条 Chat 的上下文窗口中移出，交给可检索、可版本控制、可由不同模型共同读取的外部项目状态。

# 1. 核心原则

不要把 Chat 本身当作长期知识载体。

> **Chat 是临时工作分支；Issue、文档、ADR 和项目状态文件才是长期公共状态。**

一条对话可以很长，也可以因为上下文上限被迫结束，但项目的重要状态不应只存在于该对话中。

长期连续性的目标不是让一条 Chat 永远不结束，而是：

> **任何一条新 Chat 都能在较小的 Context 中恢复项目当前真正重要的状态。**

# 2. 各类载体的职责

## 2.1 Chat：工作分支

Chat 用来：

- 探索问题；
- 比较方案；
- 临时推理；
- 写代码前讨论；
- 阅读与调试；
- 形成新的问题或判断。

Chat 允许重复、试探、反悔和未完成推理。它不是项目最终的 source of truth。

可以把一条 Chat 近似理解为一条 Git branch：它承载某段工作的展开，但不要求本身永久保存全部价值。

## 2.2 Project Context：项目 HEAD

每个长期项目应尽量维护一份很短的项目状态入口，例如：

~~~text
PROJECT_CONTEXT.md
docs/context/README.md
~~~

它不保存详细知识，只回答：

- 项目现在在做什么；
- 当前主线是什么；
- 哪些关键判断已经冻结；
- 哪些问题仍悬而未决；
- 哪些 Issue / 文档 / ADR 是当前入口；
- 哪些方向暂时不要提前展开。

它相当于项目当前认知状态的 **HEAD 指针**。

新 Chat 开始时，优先读取 Project Context，再根据当前任务继续读取少量相关 Issue / Docs，而不是重放全部历史聊天。

## 2.3 Issue：还在想什么

Issue 保存尚未成为稳定知识的问题：

- 待讨论问题；
- 未验证假设；
- 方案选择；
- Bad Case；
- 暂时悬而未决的判断；
- 将来值得研究但尚不应实现的方向。

一个问题一旦可以独立命名，就可以考虑拆成独立 Issue，而不必等到当前 Chat 快超限才拆。

## 2.4 Docs：目前已经知道什么

知识文档、架构文档和规范保存已经足够稳定、可以作为后续工作前提的认识。

例如：

- 当前架构职责；
- 已冻结的数据边界；
- 稳定的术语解释；
- 已验证的工作方法；
- 可以跨多个任务复用的知识。

文档应面向“现在有效的状态”，不必保留所有探索过程。

## 2.5 ADR：为什么这样决定

Architecture Decision Record 用来保存：

- 当时面对什么问题；
- 考虑过哪些方案；
- 最后选择了什么；
- 为什么这样选；
- 什么条件出现时需要重新评估。

Issue 可能关闭，架构文档可能只保留现状；ADR 专门保存决策史，避免以后只记得“曾经决定过”，却忘记理由。

## 2.6 Migration Document：换代 checkpoint

对话迁移文档继续保留，但降级为临时 checkpoint，而不是长期知识体系的主要组成部分。

适用场景：

- 当前 Chat 已接近上下文上限；
- 当前分支仍有大量未沉淀的中间状态；
- 下一条 Chat 需要无缝继续同一复杂讨论；
- 暂时还无法把全部内容整理成 Issue / Docs / ADR。

理想流程：

~~~text
长 Chat
↓
Migration / Checkpoint
↓
新 Chat 继续
↓
重要内容逐步进入 Issue / Docs / ADR / Project Context
↓
Migration 文档归档
~~~

如果公共状态已经及时更新，新 Chat 通常不再需要专门生成迁移提示词。

# 3. 新 Chat 的最小恢复流程

长期项目开启新对话时，优先加载：

~~~text
Project Context
+
当前主 Issue
+
必要的正式文档 / ADR
+
当前用户任务
~~~

而不是：

~~~text
上一条完整 Chat
+
更早的完整 Chat
+
所有历史迁移文档
~~~

目标是恢复“当前有效状态”，不是恢复过去所有说过的话。

# 4. 对话拆分原则

## 4.1 feat 型 Chat

小功能尽量短生命周期：

~~~text
讨论
→ 实现
→ 测试 / 文档 / Issue 更新
→ PR / Commit
→ Chat 可以结束
~~~

一旦价值已经进入公共状态，聊天记录不再承担长期保存责任。

## 4.2 research 型 Chat

研究型讨论可以产生多个 Issue：

~~~text
一个大问题
→ 若干独立子问题
→ Issue
→ 稳定结论进入 Docs / ADR
~~~

不必为了保存研究过程而无限延长同一条 Chat。

## 4.3 long-running 型 Chat

长期学习、观察、共读等对话可以保持较长生命周期，但仍应定期：

~~~text
Conversation
→ Checkpoint
→ Canonical Knowledge
~~~

否则上下文迟早会被历史过程淹没。

# 5. 并行长期对话如何同步

两条长期 Chat 不应主要靠彼此人工转述同步。

避免：

~~~text
Chat A ↔ Chat B
~~~

优先：

~~~text
Chat A ─┐
        ├→ Shared Project State
Chat B ─┘
~~~

一条 Chat 形成稳定判断后，更新公共 Issue / Docs / ADR / Project Context；另一条 Chat 下次读取公共状态即可。

公共状态是 single source of truth，避免两条 Chat 各自维护“对另一边的总结”后逐渐漂移。

# 6. Project Context 应保持很短

Project Context 不是另一本项目百科。

建议只保留：

~~~text
当前主线
关键已冻结判断
当前开放问题
当前不要提前做的事
入口 Issue / Docs / ADR
最近一次重要状态变化
~~~

详细内容通过链接进入其他文档。

如果 Project Context 开始持续膨胀，应把稳定知识下沉到 Docs，把开放问题下沉到 Issue，把历史选择下沉到 ADR，只留下索引和当前状态。

# 7. 知识的晋升路径

一次聊天中的内容不因“听起来有价值”就立即写入永久规范。

可以采用：

~~~text
Chat 中的观察
↓
Issue / Candidate
↓
重复出现、验证或讨论
↓
稳定判断
↓
Docs / ADR / 规范
~~~

这与 Finishing School 已有维护原则一致：先记录问题，只有形成稳定、可复用的规则以后，才进入正式规范。

# 8. 删除 Chat 的判断

不要求主动大量删除，但可以用一个简单标准降低心理负担：

> **如果这条 Chat 消失，项目是否仍能从公共状态恢复关键事实、开放问题和后续方向？**

如果答案是“能”，这条 Chat 已经完成了作为工作分支的职责。

如果答案是“不能”，说明仍有知识或状态只存在于聊天中，应先沉淀，而不是仅仅因为对话很长就保留。

# 9. 与 ChatGPT Memory 的关系

OpenAI 提供的 Memory / 个性化可以辅助记住用户偏好、长期习惯和部分跨对话信息，但不作为项目 source of truth。

项目级长期状态应尽量具备：

- 可见；
- 可审查；
- 可版本化；
- 可由不同模型读取；
- 可由人主动更正；
- 不依赖某一家模型产品的内部记忆策略。

GitHub、Project files、知识库等外部载体更适合承担这一职责。

# 10. 最小可行实践

不需要一开始建立复杂知识管理系统。

一个长期项目只要先有：

~~~text
PROJECT_CONTEXT.md
GitHub Issues
docs/
必要时 ADR/
~~~

就足以替代大量“每次 Chat 超限都重新写迁移提示词”的工作。

Migration Document 仍作为异常情况下的 checkpoint，而不再是默认交接方式。

# 11. 核心锚点

> **Chat 是 branch，公共文档是 main；长期连续性来自可恢复的项目状态，而不是无限增长的聊天上下文。**
