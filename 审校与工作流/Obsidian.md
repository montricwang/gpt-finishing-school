# Obsidian

**状态：可选环境约定**  
**用途**：用于在 Obsidian 中维护技术学习文档时的文件、双链、导航和可选样式约定。  
**依赖**：《文档排版》《技术文档》  
**被依赖**：采用 Obsidian 作为维护环境的技术知识库  
**替代**：旧工程知识设计规范中的 Obsidian 双链、文件组织和统一 Mermaid 配色规则。  
**适用边界**：本约定只处理 Obsidian 环境。迁移到其他编辑器时可以整体停用，不影响正文知识结构和语言规范。

# 1. 文件名表达稳定身份

知识正文使用稳定、可识别的主题名，例如：

```text
缓存专题.md
Redis.md
重试与退避.md
可观测性.md
```

文件名优先表达文档对象，不将当前 P0 / P1、完成百分比、日期或项目阶段写入长期文件名。这些状态放入文档元数据、学习地图或任务系统。

规范、审校手册和其他需要独立加载的插件文档可以作为例外，在文件名末尾增加 `_vX.Y.Z`，让使用者从文件列表中直接识别当前版本。正文标题、双链显示文本和交叉引用仍然使用不带版本号的稳定名称；现行目录只保留最新版，旧版需要追溯时移入历史目录。

同一知识库对「专题」「方法」等后缀保持一致。只有在去掉后缀仍然不会混淆类型时，才采用更短文件名。

# 2. 文件开头声明文档关系

需要显式管理依赖的规范和长期文档，可以在开头写：

```markdown
**依赖**：《上位文档》
**被依赖**：《下游文档》
**替代**：旧文档或旧规则
```

普通学习笔记只在关系确有维护价值时加入，不为所有文件制造元数据负担。

# 3. 双链用于导航和依赖

跨笔记链接使用 Obsidian 双链：

```markdown
[[缓存专题]]
[[缓存专题#核心机制]]
[[缓存专题#核心机制|缓存为什么能加速]]
```

适合添加链接的位置包括：

- 总纲第一次引出专题；
- 专题第一次连接具体工具或工程方法；
- 方法文档连接所属专题和实现工具；
- 文档明确依赖另一份定义或规则。

同一小节内反复出现同名对象时，只在第一次或最有导航价值的位置链接。普通术语不因为存在同名文件就全部加链。

# 4. 总纲、专题、对象和项目方案形成清楚路径

推荐关系是：

```text
技术学习总纲
├─ 工程专题
│  ├─ 工程方法
│  └─ 具体技术对象
└─ 项目方案
   └─ 引用所采用的专题、方法和对象
```

总纲建立地图，专题组织问题域，对象和方法提供下探入口，项目方案记录当前选择。导航关系不要求完全对应文件夹关系。

# 5. 文件夹按维护职责划分

文件夹用于降低浏览成本，不承担知识分类的全部工作。一个可选结构是：

```text
00_总纲
10_工程专题
20_工程方法
30_具体技术对象
40_项目方案
90_参考与附录
99_历史规范
```

知识库规模较小时可以减少层级。双链已经能够清楚导航时，不为每个小分类继续建立子文件夹。

# 6. 主文与高频增长材料分开

以下内容增长速度和使用方式与主文不同，可以独立成页：

- 命令、API、配置和语法速查；
- 场景卡片和故障案例库；
- 大型术语表；
- 项目运行手册；
- 历史版本和冻结规范。

拆出后由主文提供入口。父子文档不长期复制同一段内容。

# 7. 内部标题为链接稳定性服务

标题表达稳定职责，例如「核心机制」「典型链路」「边界与取舍」。频繁修改标题会破坏章节级双链，因此重要链接目标改名时，同时检查反向链接。

文件内一级标题、二级标题和附录编号遵循《文档排版》。Obsidian 链接不反向决定正文层级。

# 8. 块级数学公式使用 `$$ ... $$`

当前 Obsidian 环境中的块级数学公式使用双美元符号定界：

```markdown
$$
E = mc^2
$$
```

不要使用 `\[ ... \]` 作为块级公式定界符，因为这种形式在当前环境中无法稳定渲染。行内公式继续使用 `$...$`。

# 9. Mermaid 配色是可选样式层

旧知识库使用过五类节点配色。继续沿用时，可以保持如下语义：

| 类名 | 默认颜色 | 语义 |
| --- | --- | --- |
| `native` | 草绿 | 业务代码、调用方、原生对象 |
| `concept` | 亮蓝 | 核心角色或机制 |
| `data` | 中紫 | 数据、状态、结果 |
| `contract` | 朱红 | 协议、契约、约束 |
| `lc` | 明黄 | 当前图的主角 |

```mermaid
flowchart LR
    A[调用方]:::native --> B[核心机制]:::concept
    B --> C[数据或状态]:::data
    C --> D[协议或约束]:::contract
    D --> E[当前主角]:::lc

    classDef native fill:#81c784,color:#000,stroke:#2e7d32
    classDef concept fill:#64b5f6,color:#000,stroke:#1565c0
    classDef data fill:#9575cd,color:#000,stroke:#4527a0
    classDef contract fill:#e57373,color:#000,stroke:#c62828
    classDef lc fill:#ffd54f,color:#000,stroke:#f57f17
```

配色只帮助识别，不定义事实。图已经能靠标签清楚表达时，可以不使用颜色。不同渲染器或主题影响可读性时，优先保证文字、边框和对比度。

# 10. 历史规范进入冻结区

完成迁移的旧规范可以移入「历史规范」目录，并在文件开头注明：

```markdown
**状态**：冻结，仅用于追溯和查漏
**现行替代**：《……》
```

冻结文档保留原貌，不再与现行规范双向同步。新增规则只进入现行上位规范或对应扩展。

# 11. 更新检查

1. 新文件是否真的承担独立职责，还是可以并入现有文档？
2. 文件名是否表达稳定对象，而不是短期状态；如果属于规范或插件，版本后缀是否与现行版本一致？
3. 双链是否用于真实导航、依赖或下探？
4. 总纲、专题、方法、对象和项目方案是否各自归位？
5. 拆出的参考页是否由主文提供明确入口？
6. 标题改动后，章节级双链是否仍然有效？
7. 块级数学公式是否使用 `$$ ... $$`，并避免使用当前环境无法稳定渲染的 `\[ ... \]`？
8. Mermaid 配色是否保持语义一致，并在当前主题下可读？
9. 已迁移的旧规范是否停止同步维护？
