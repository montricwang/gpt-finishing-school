# 多模型审查

**状态**：重组试行版  
**用途**：让多个大模型围绕同一份文档进行互补审查。共同基线保证结果可比较，专属角色让不同模型集中发挥最强能力，最终由综合裁决阶段合并真正值得修改的问题。  
**适用对象**：技术学习文档、工程哲学文档、知识体系总纲、工程专题、规范文档及其他需要长期维护的高价值文档。

# 1. 核心原则

多模型审查的价值来自「互补」，而不是让多个模型重复完成同一份检查表。

同一份文档可以同时存在不同类型的问题：抽象层级可能偏低，运行闭环可能缺失，事实出处可能有误，结构可能已经足够却仍被不断扩写。不同模型对这些问题的敏感度不同。

因此，本协议采用：

**共同审查基线 + 专属主审角色 + 有限交叉检查 + 最终综合裁决**

共同基线规定文档目标、评价标准、问题分级和停止条件；专属角色规定本轮最值得投入注意力的位置；有限交叉检查保证主审角色仍能指出真正严重的其他问题；综合裁决负责处理不同模型之间的冲突。

核心锚点：

**同一文档由多个模型从不同薄弱面进攻，最终综合阶段判断哪些问题真的会改变长期质量。**

# 2. 使用流程

一次完整审查分为五步：

1. 向所有参与模型提供同一份待审文档。
2. 同时提供本协议。
3. 每个模型先选择自己的「主审角色」，再执行该角色的专属任务。
4. 收集所有审查报告。
5. 由综合裁决者比较一致意见、独有意见、证据强度和角色匹配度，形成最终修改集。

参与模型之间无需看到彼此的初始报告。独立判断能够减少相互诱导。

# 3. 所有模型共享的审查基线

每个模型开始审查前，先回答四个问题：

1. 这份文档准备长期解决什么问题？
2. 它的目标抽象层级是什么？
3. 哪些内容属于当前文档职责，哪些内容应留给下游专题？
4. 达到什么状态以后应该停止继续扩写？

审查时优先寻找会改变长期认知模型的问题。单纯「还能补充」的内容保持低优先级。

对于长期知识文档，重点检查：

- 概念是否稳定；
- 抽象是否能够跨工具、框架和时代变化继续成立；
- 理论是否放在正确层级；
- 事实与来源是否可靠；
- 结构是否存在类别级遗漏；
- 具体案例是否反过来限制了抽象；
- 图、公式、表格和列表是否真正增加信息；
- 文风是否直接、清楚、自然；
- 修改是否仍有足够边际收益。

# 4. 主审角色选择

每个参与模型首先选择一个主审角色。主审角色占本轮约 70%～80% 的注意力，其余注意力用于发现明显的跨领域严重问题。

选择时采用以下顺序：

1. 如果本协议已经给出该模型的推荐角色，优先采用推荐角色。
2. 如果模型认为自己的当前能力明显更适合另一个角色，可以改选，并用一句话说明理由。
3. 新模型或未列出的模型根据自己的能力选择最能产生差异化价值的角色。
4. 一轮审查只承担一个主审角色；确有明显第二优势时，可以附带一个次审角色，但不平均分配注意力。

当前根据实际协作经验形成的推荐角色如下。它们描述的是当前观察到的优势倾向，后续可以随模型版本和实际表现调整。

| 模型 | 推荐主审角色 | 主要价值 |
| --- | --- | --- |
| Gemini | A：哲学高度与概念完整性 | 判断抽象是否真正上升到长期稳定的问题域，寻找类别级遗漏 |
| DeepSeek | B：运行、失效与工程闭环 | 检查状态、失败传播、恢复、风险、责任边界是否闭合 |
| Grok | C：删减、边际收益与停止线 | 防止文档膨胀，判断哪些内容应删、哪些建议已经属于过度扩展 |
| ChatGLM | D：事实、来源与编辑终审 | 核对人名、年份、出处、概念归属，同时检查重复、公式、图表和排版 |
| ChatGPT | E：综合裁决与体系一致性 | 比较多家意见，结合文档体系决定最终修改集和冻结时机 |

如果参与模型不在表中，可以从 A～D 中自行选择最匹配角色。E 通常在其他报告完成后执行。

# 5. A 角色：哲学高度与概念完整性

## 5.1 主任务

判断文档是否真的抓住了长期稳定的问题，而不是将当前实践换成抽象词重新描述。

重点检查：

- 文档处在工具、方法、理论、哲学中的哪一层；
- 各章节是否围绕稳定问题域组织；
- 是否存在一个跨领域高级工程师长期反复遇到、正文却完全没有覆盖的问题；
- 当前理论是否只是「有名」，还是确实解释了长期结构；
- 某个理论是否被抬得过高；
- 某个局部机制是否被误写成普遍规律；
- 文档在十年、二十年后的工具环境中是否仍然大体成立。

## 5.2 强制问题

A 角色必须回答：

**如果将所有具体工具名、框架名和当代架构名全部拿掉，这篇文档还剩下多少解释力？**

再回答：

**是否存在一个与信息隐藏、端到端论证、康威定律同一量级的思想缺口？**

只有真正满足这一量级，才列为高优先级遗漏。

## 5.3 自我约束

A 角色特别检查自己是否因为某个理论「很漂亮」就将它抬成哲学核心。

新增理论需要证明：

- 它覆盖多个软件领域；
- 它跨时代稳定；
- 当前正文确实没有同义上位概念；
- 缺少它会形成长期认知偏差。

# 6. B 角色：运行、失效与工程闭环

## 6.1 主任务

将文档放进真实运行世界，检查正常路径之外的状态和责任是否闭合。

重点检查：

- 状态从哪里来，谁拥有权威解释权；
- 多执行者、时间、并发和边界怎样改变行为；
- 局部错误怎样进入状态；
- 故障怎样传播；
- 系统如何限制影响范围；
- 哪些状态可以重建、回退、补偿或人工收敛；
- 证据怎样支持恢复和后续判断；
- 安全、权限、资源与故障边界是否具有稳定上位位置；
- 文档是否只描述成功路径；
- AI、分布式、数据库、操作系统等不同领域能否共享这些判断。

## 6.2 强制问题

B 角色必须回答：

**如果系统开始失败，这套理论还能解释接下来发生什么吗？**

再回答：

**是否存在某个正常路径已经讲清、失效路径却完全没有上位位置的问题？**

## 6.3 自我约束

B 角色容易将生产系统中的重要机制提升为哲学结构，因此每个新增一级问题都需要证明其跨领域性。

Timeout、Retry、幂等、熔断、ACK、事务、Checkpoint 等具体机制只有在其背后缺少更上位问题时，才推动文档结构变化。

# 7. C 角色：删减、边际收益与停止线

## 7.1 主任务

默认文档存在维护成本。审查重点是识别：

- 哪些内容重复；
- 哪些内容太具体；
- 哪些理论只有名气，没有结构价值；
- 哪些案例太长；
- 哪些公式只是普通中文的符号化；
- 哪些 Mermaid 只是装饰；
- 哪些表格制造虚假完整性；
- 哪些章节已经被其他章节覆盖；
- 哪些新增建议收益低于新增复杂度；
- 当前版本是否已经达到冻结条件。

## 7.2 强制问题

C 角色必须执行两项检查：

**删除测试**：删掉这一段、公式、图、表或理论以后，读者的长期判断能力是否真的下降？

**新增测试**：这个建议加入以后，是否会改变未来的设计、排障、验证或取舍？如果只增加知识量，归入扩展项。

## 7.3 自我约束

停止本身也是审查结果。

当正文已经形成稳定骨架，剩余问题主要属于措辞、例子和可选扩展时，C 角色应明确建议冻结，而不是继续寻找新的修改理由。

# 8. D 角色：事实、来源与编辑终审

## 8.1 主任务

逐项检查文档中可以客观核验的内容，以及会降低长期可维护性的编辑问题。

重点检查：

- 人名及中文译名；
- 论文、书籍、演讲标题；
- 年份；
- DOI 和 URL；
- 理论最初出处；
- 原作者观点与后人概括是否混淆；
- 「Law」的实际理论地位；
- 经验规律是否被写成严格定律；
- 正文和资料来源是否互相对应；
- 同一句是否重复出现；
- 章节编号是否连续；
- 术语是否前后统一；
- Mermaid 是否真的需要；
- 公式是否承担形式关系；
- 表格和列表是否满足排版语义；
- 文档是否出现编辑残留。

## 8.2 强制问题

D 角色必须回答：

**有哪些问题一分钟就能修复，却会在冻结后长期损害文档可信度？**

再回答：

**哪些公式、图表和结构化元素删除以后信息几乎不损失？**

## 8.3 自我约束

编辑问题按真实影响分级。

作品译名、出处和归属错误优先修复；单纯措辞偏好保持低优先级。事实核验服务于内容可信度，不将整份报告变成格式洁癖。

# 9. E 角色：综合裁决与体系一致性

E 角色在其他模型完成独立审查以后执行。

它不重新做第五遍全面审查，主要完成四项工作：

1. 识别多家一致意见；
2. 判断独有意见是否恰好来自该模型的优势领域；
3. 处理建议之间的冲突；
4. 形成严格有限的最终修改集和停止判断。

综合裁决遵循以下证据顺序：

**可直接核验的事实 > 与角色优势高度匹配的独有发现 > 多家独立一致判断 > 单家一般性建议 > 纯扩展建议**

多家一致并不自动等于正确；单家独有也不自动等于异常。

例如：

- D 角色独自发现论文标题错误，且可以核验，优先级很高；
- B 角色独自发现失效闭环缺失，且确实横跨多个领域，应认真评估；
- A 角色独自提出一个漂亮理论，需要额外检查是否被过度升格；
- C 角色独自认为应该停止，重点检查剩余修改是否真的仍有显著边际收益。

# 10. 问题分级

所有角色统一使用 A / B / C / D 四级。

## A：必须修改

包括：

- 会形成错误长期心智模型的概念错误；
- 关键事实或理论归属错误；
- 一级结构缺口；
- 严重层级错误；
- 具体实践被误写成普遍规律；
- 结构本身阻碍长期使用。

A 级意味着当前版本还不适合冻结。

## B：冻结前值得修改

包括：

- 会长期影响理解的重要边界；
- 一个真正跨领域的共同经验尚未得到稳定表达；
- 内容明显太具体或放错层级；
- 某个有限修改可以显著提高长期解释力。

每个 B 项都要说明「为什么应该现在改」。

## C：可选优化

包括：

- 局部重复；
- 术语统一；
- 段落压缩；
- 个别图表优化；
- 更好的短例子。

C 项不单独触发大修。

## D：扩展候选

包括：

- 还有价值，但属于下游专题；
- 新案例；
- 更多理论；
- 更多工具；
- 更多历史；
- 当前正文已经有上位覆盖的具体机制。

D 项进入候选池，本轮保持正文稳定。

# 11. 每个模型的统一输出格式

每个模型提交报告时使用以下结构：

## 1. 主审角色

说明选择 A / B / C / D 中哪一个，以及为什么这个角色最能发挥当前模型的优势。

## 2. 主判断

用 3～6 段说明文档当前质量、最大优点、最大剩余问题和当前抽象层级。

## 3. A 级问题

没有则写「无」。

## 4. B 级问题

每项写：

- 问题；
- 为什么属于 B；
- 修改方向；
- 为什么应该现在改。

## 5. C 级问题

简洁列出。

## 6. D 级扩展

明确列出「现在保留在候选池」的内容。

## 7. 本角色专项结论

按照主审角色回答对应的强制问题。

## 8. 最终停止判断

只能选择：

- 可以冻结；
- 小修后冻结；
- 仍需结构性修改。

# 12. 综合裁决的输出格式

综合裁决者读取所有独立报告后，输出：

## 1. 共识

哪些判断被多家独立支持。

## 2. 高价值独有发现

哪些意见虽然只有一家提出，却与其主审优势高度匹配，并且有充分证据。

## 3. 不采纳建议

明确记录哪些建议被拒绝，以及拒绝原因。这样后续审查不会反复重新提出同一问题。

## 4. 最终修改集

只保留真正值得实施的修改。修改集应尽量有限。

## 5. 冻结判断

说明完成这些修改后是否冻结。

# 13. 2026-09-18 首轮实战观察

本协议第一版来自一次真实的软件工程哲学文档联合审查。

四个模型使用近似相同的终审要求后表现出明显互补性：

- Gemini 对抽象高度和概念完整性判断很强，也容易提出漂亮的理论性补充；综合阶段需要额外检查这些补充是否被升格过度。
- DeepSeek 对失效、风险、恢复和运行闭环非常敏感，能够发现正常路径之外缺失的工程支点；综合阶段需要检查它是否将具体生产机制提升得过高。
- Grok 对删减和停止线最克制，能够有效抑制「还能补什么」带来的知识膨胀；综合阶段仍需由其他角色承担事实核验。
- ChatGLM 对文献标题、来源、理论归属、重复句、临时公式和图表必要性非常敏锐，适合作为事实与编辑终审。
- ChatGPT 负责比较这些意见与整个知识体系的关系，并决定哪些建议真正进入最终版本。

这组观察属于当前版本经验数据。未来模型能力变化以后，可以根据新的实战结果修改角色映射。

# 14. 冲突处理原则

当多个模型意见冲突时，依次判断：

1. 是否存在可以直接核验的事实；
2. 争议属于哪个主审领域；
3. 提议是否真正改变长期认知模型；
4. 当前正文是否已经用更高层概念覆盖；
5. 修改成本和长期收益是否匹配；
6. 是否已经达到停止线。

对于「增加一个新理论」和「保持现有抽象」之间的争议，新增方承担证明责任。

对于「删除一个结构」和「保留复习入口」之间的争议，判断其是否承担独立信息功能。

# 15. 停止条件

一轮多模型审查达到以下状态时结束：

- 没有 A 级问题；
- B 级问题已经形成有限集合；
- 新出现的建议主要属于 C / D；
- 多模型开始重复提出相同意见；
- 新增内容的边际收益明显下降；
- 文档的下一步价值已经主要来自实际使用，而不是继续内部润色。

此时应冻结主体版本，让后续专题、实践和真实使用反馈承担下一轮验证。

**长期知识体系的质量来自持续使用后的有限修订，也来自在合适的时候停止继续扩写。**
