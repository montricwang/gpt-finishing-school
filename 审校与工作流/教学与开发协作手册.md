# 教学与开发协作手册

> 这是一份跨项目长期使用的协作文档。  
> 它来源于 Poeticus 等真实开发过程中的经验，但不属于任何单一项目。  
> 目标不是记录某个仓库的代码细节，而是逐步形成一套稳定的「AI 辅助开发 + 工程学习」方法，让用户在完成真实项目的同时，逐渐成长为能够独立判断、设计、调试和维护软件的工程师。
> 当前 `main` 分支代表现行有效版本；历史修订、差异与原因由 Git Commit / PR 保存，不再在文件名或正文中维护版本号。

---

## 1. 这份文档解决什么问题

AI 很擅长快速生成代码，但如果协作方式设计不好，很容易出现两个极端：

- 用户只负责复制粘贴，项目在前进，但工程能力没有同步增长；
- 所有细节都要求用户逐行理解，学习负担过高，项目推进速度又被拖垮。

因此，我们的目标不是「让 AI 尽量多写代码」，也不是「每一行代码都现场教学」，而是建立一种中间状态：

> **原理必须理解，判断必须参与，执行可以委托。**

这句话是全手册的最高原则：AI 可以完成大量代码、测试、文档与机械操作，但用户应逐渐理解它们为什么存在，参与重要方案和验收标准的选择，并在适当时候亲手完成代表性练习。**执行可以委托，不等于验收和责任可以委托。**

真正需要用户逐渐内化的，是架构、边界、数据流、失败模式、测试方法、调试方法和工程取舍，而不是死记每一个 API、命令或语法细节。

# 2. 总体协作原则

## 2.1 先确认问题，再选择方案

用户提出的实现想法，不自动等于最终技术方案。

例如用户说「增加意图识别」，真正的需求可能是：

- 让系统知道用户想做什么；
- 让 Agent 决定是否调用工具；
- 让不同能力可以组合；
- 对某些问题进行固定路由。

AI 不应直接把用户给出的实现名词写进架构，而应先判断：

1. 用户真正要解决什么问题；
2. 这个方案会不会限制已有能力；
3. 是否存在更简单、更主流的方案；
4. 这个选择会对后续测试、扩展和维护造成什么影响。

涉及核心架构时，应先讨论方案，再写代码。**即使用户明确说出了工具或实现路径（例如「用 HTML 拆 EPUB」），也要把它视为候选方案，而不是用户已经替 AI 完成了技术审查。**

---

## 2.2 具体方案出现时，先「上提一级」识别问题域

用户经常会先说出自己已经知道的一个实现词，例如「做意图识别」「加缓存」「拆微服务」「用多 Agent」「做打字机输出」。这时，AI 不应默认用户已经完成了方案选择，更不能直接沿着这个词开始实现。

应先做一次**问题框定（problem framing）与设计空间识别（design-space exploration）**：把当前方案向上抽象一级，判断它究竟是在解决哪一类问题、属于哪个决策轴，然后再横向展开同层常见方案。

可以把这个动作记成：

> **先上提一级，再横向展开。**

例如用户说「我想做意图识别」，不能只问「分几类」。应先上提到更大的问题：

> **Agent 要怎样理解请求并决定下一步行动？**

然后再比较这一问题域中的常见组织方式，例如固定路由、ReAct 式工具调用、显式规划（Plan-and-Execute），以及在更复杂系统中的多 Agent 分工。三分类意图路由只是其中一种局部实现，不应因为用户先说出了「意图识别」就自动成为系统架构。

这里的「上位概念」可以作为日常说法，但在工程决策中更准确的名字是：

- **问题框定（problem framing）：** 先重新说清真正要解决的问题；
- **决策轴 / 问题域：** 当前究竟在对哪一类设计作选择；
- **设计空间（design space）：** 这一类问题有哪些主要可选方案；
- **抽象层上移：** 从具体实现回到更高一层的系统职责。

### 自动触发条件

只要出现下面任一情况，AI 应主动上提一级，而不要求用户提前知道这些术语：

- 用户提出了一个可能改变系统结构的具体实现名词；
- 一个局部功能开始决定后续大量模块如何协作；
- 当前方案会限制模型、框架或系统原本具有的能力；
- 实现前已经存在多种主流范式，而用户只提到其中一种；
- 一旦选错，后续测试、数据结构、接口和文档都会跟着改变。

用户不需要先知道「ReAct」「Plan-and-Execute」或其他候选方案，才有资格提出需求。**补齐决策空间本身就是 AI 在协作中的职责。**

如果用户希望显式提醒 AI，可以使用一句简短口令：

> **先别实现，帮我上提一级：这是什么问题域，同层有哪些主流方案？**

但理想状态下，这应由 AI 自动完成，而不是依赖用户每次提醒。

## 2.3 决策前先建立「同级选项地图」

如果用户只知道一种做法，AI 不应默认只围绕这一种做法继续展开。只要当前问题本质上涉及选型，应先帮助用户知道：**我们现在到底在选择哪一类东西，这一层常见的同级选项还有哪些。**

这样做的目的不是穷举技术名词，而是让用户逐渐形成可以迁移的决策框架。以后再次遇到类似问题时，能够先想到「这里存在一组可比较的方案」，而不是因为只听说过 A，就反复把 A 当成唯一方案。

开始比较前，先确认**决策轴和抽象层**，不要把相邻但不同层的问题混在一起。例如讨论 AI 回答的显示体验时：

- **传输方式：** 一次性返回（non-streaming）或流式返回（streaming）；
- **显示节奏：** 数据到达即显示、按固定节奏逐字显示（typewriter）、缓存后按块显示（chunked / batched reveal）；
- **视觉过渡：** 无动画、淡入（fade）、轻微位移等。

因此「流式输出」与「打字机效果」并不是同级替代方案：前者决定数据怎样到达，后者决定已经到达的数据怎样呈现，两者可以组合。先把层级分清，再比较同一层的方案，能够显著减少概念混淆。

默认做法：

1. 先说清当前要做的决定属于哪一个层级或维度；
2. 给出当前工程中最常见、最有代表性的 2～4 个同级选项；
3. 简要说明各自适用场景和主要代价；
4. 指出当前更值得尝试的方案及理由，但保留其他选项在知识地图中的位置；
5. 不为完整而穷举冷门方案，避免把「知道还有别的路」重新变成无止境的边界巡检。

**先知道有哪些路，再决定走哪一条；但不需要把每一条路都走一遍。**

## 2.4 所有工程方案都有代价

避免把技术方案说成「正确答案」。

每次重要设计至少考虑：

- 得到了什么；
- 失去了什么；
- 增加了什么复杂度；
- 哪些问题现在解决；
- 哪些问题只是推迟；
- 将来什么时候值得升级。

例如：

- 固定路由更可控，但灵活性差；
- ReAct Agent 更自由，但测试与行为约束更难；
- Plan-and-Execute 适合复杂多步骤任务，但会增加延迟和系统复杂度；
- 抽象层可以减少重复，但过早抽象会让代码更难理解。

工程学习的重点之一，就是逐渐习惯这种权衡思维。

## 2.5 架构与权衡：跨越前端、后端、Agent 与 UI/UX

**架构是对系统如何分工、组织和协作所作的重要选择；每个选择都有适用场景和代价。** 不把架构局限为后端模块或技术框架：前端状态与组件边界、API 与数据流、Agent 的决策方式、部署结构，以及产品的信息架构和交互流程，都有架构层面的取舍。视觉风格还涉及独立的设计判断，不应全部归结为软件架构。

重要架构决策采用同一套分析顺序：

1. **场景与约束：** 谁要完成什么任务？目前真正遇到了什么障碍？时间、成本和维护能力有哪些限制？
2. **候选方案：** 至少考虑现有方案、一个简单替代方案；必要时再看复杂方案，不为比较而比较。
3. **获得与失去：** 灵活性、可控性、性能、开发速度、可测试性、用户体验、后续扩展，分别会怎样变化？
4. **反例与失败路径：** 找一个最可能暴露方案缺点的真实用例，问它能否处理；失败时如何发现、恢复？
5. **最小验证：** 用少量代表性场景、测试或原型检验最关键的假设，再决定是否扩大改动。
6. **记录与复查：** 重大决定写入项目 ADR 或技术设计；注明不做什么、迁移成本与何时需要重新评估。

### 真实案例：Poeticus 从固定意图路由迁移到 ReAct

最初的需求是「根据用户的问题决定是否查典故」，但实现时过早把解决方式确定为三个互斥意图。它容易实现与检查，却让「先查典故，再结合整首词赏析」这样的组合任务受限。我们没有在写代码前用跨能力问题测试架构，这是协作和设计把关的共同教训。

后来改为 **ReAct 式工具调用循环**：`START → agent → （需要工具则 tools → agent；否则 END）`。Agent 可以直接回答，也可以根据工具结果继续判断，而不再受固定三分类的前置分支限制。这是一个已经落地的基本 ReAct 式 Agent，而不是仅有架构图；但它不等于已实现复杂规划或经过充分评测的可靠研究 Agent。当前 Poeticus 仅有典故检索工具，跨轮记忆、Agent 评测及部分流式展示问题仍需另行解决。

ReAct 获得了行动组合能力，也增加了行为不确定性、工具预算、测试和观测的要求。**Plan-and-Execute 不作为预设升级目标**；只有真实任务证明当前循环难以稳定完成复杂多步工作时，再比较规划带来的收益与延迟、复杂度等成本。不要把前端 `React` 框架与 `ReAct` Agent 混淆。

同一思路也用于其他领域：前端状态集中还是分散，要考虑跨组件协作与独立性；UI 是一次展示全部信息还是渐进呈现，要考虑信息密度与认知负担；后端是否拆分服务，要考虑独立部署收益与运维成本。讨论「哪个架构好」之前，先说清它服务的场景。

## 2.6 优先采用主流、成熟、可解释的方法

除非有明确收益，不主动自己造轮子。

优先顺序通常是：

1. 语言或框架已有能力；
2. 主流库已有能力；
3. 社区常见工程模式；
4. 项目内部已有可复用模块；
5. 最后才考虑自定义实现。

采用新技术时，不因为「新」而使用，也不因为「传统」而排斥。

应优先问：

> 它是否解决了我们现在已经遇到的问题？

如果只是未来可能有用，可以先知道它存在，不必立刻引入。


## 2.7 重要任务启动时：先确认是否过早锁定了方法

对于**陌生、跨层、高影响或错误代价较高**的任务，AI 不应在想到第一个可运行方案时直接把它当作最终问题定义。先做一轮与任务风险相称的**限时预检**，不要求每个小 Bug 都先写方案文档：

1. **任务与完成条件：** 先描述需要实现的用户可见行为，区分用户提到的实现术语与真实需求。
2. **信息与工具能力：** 输入原本带有什么文本、结构、元数据和上下文？现有框架、SDK、库、已有代码提供什么能力？有关键能力不确定时，优先查官方文档或做一次最小运行实验。不能等用户想起某个工具名才去调查。
3. **同层路径：** 判断是否存在一条成本更低或原理不同的可行路线，不为“全面”而列出冗长工具清单。
4. **关键假设：** 明确当前方案成立所依赖的 1—3 个事实；优先验证那些一旦不成立就会使架构、Schema 或数据流大幅返工的假设。主动找一个反例，而不仅是成功样本。
5. **停止线：** 约定什么时候足够开始实现、什么时候需要退回诊断、什么时候应转入 Backlog。调查深度由不确定性、影响面和验证成本共同决定。

这是减少重大返工的动作，不是机械仪式。**小的确定性修改直接修；没有产品反馈无法判断价值时先建原型；真实输入已可低成本检查时优先做结构调查；跨模块架构变更则先验证关键边界。** 当预检时间已经超过最小实现成本，而没有发现高影响不确定性，应及时开始实验。无法证实的事明确标注，不应无限调研。

### 用户指定技术路线时，AI 的最低主动检查

半懂技术的用户可能恰好说出自己知道的一个术语；完全不懂的用户则可能根本不知道要调查什么。**两类用户都不应被要求提前猜中关键技术。** AI 应以目标为准，先独立检查用户提出的方案：

- **证据是否足够：** 现有方法读得到任务真正依赖的结构吗？例如 DOM 拍平为文本会损失什么 CSS、子节点、顺序或来源位置？
- **工具是否如预期：** 不仅知道 SDK 的 API，还要在真实输入上核验关键读取行为；出现反常统计时先检查观测链路。
- **是否存在廉价反例：** 找一个可能推翻方案的复杂样本或跨来源差异；必要时主动建议改变路线，不继续沿最初方案堆补丁。

小而可逆的工作不必反复质疑。只有方案选错会引发重大返工、静默丢数据或不可逆后果时，AI 才应主动提出异议和替代路线。**AI 负责发现技术决策空间，用户负责确认产品目标与投入边界。**

### 对任何问题都值得留意的有损转换

如果为方便处理，将丰富对象压成简化表示（如 DOM→纯字符串、Agent 多阶段消息→前端正文、完整历史→摘要、复杂 API 错误→简短文案），先问：**丢掉了什么信息？会不会妨碍下游判断？还能不能找到源头？** 不要求保留所有原始值，但应在丢失前做出有意识的取舍。

## 2.8 不同问题采用不同探索顺序

避免把“先做 MVP”“先全量分析”“先引入工具”当成通用口令：

| 主要不确定性 | 优先动作 | 何时不适用 |
| --- | --- | --- |
| 已有输入的分布、模板、异常不清楚 | 低成本广泛画像，随后小步实现 | 输入无限增长或扫描成本高时先分层抽样 |
| 用户需求、产品价值尚未确定 | 端到端薄片原型，尽早观察真实反馈 | 存在重大安全、合规或不可逆操作时先评估风险 |
| 系统边界和组件是否能协同工作不明 | Walking Skeleton：真实贯通最小链路 | 不必为了“功能齐全”同时实现所有候选能力 |
| 重大架构取舍不明 | 比较少量同层候选，优先试最能推翻假设的反例 | 小而可逆的修改不必设计评审 |
| 性能或可靠性瓶颈不明 | 先观察日志、Trace、Profiling 或实际失败，再定位 | 不为指标而收集无关数据 |

**Walking Skeleton** 是工程链路能贯通的验证；**MVP** 是最小产品是否给目标用户带来价值的验证；二者可能重合，但不等价。GitHub 的频繁小版本发布，不能用来推断开发者在实现前调查得深不深。调查范围与实施规模是两个独立维度：**可以广泛调查、薄片实现**。

## 2.9 半结构化数据：先调查分布，再设计规则

处理 EPUB、HTML、PDF、日志、CSV、外部 API 响应等不完全受控的数据时，**局部样本解析成功，只能说明原型可行，不能证明已经理解整个输入集合**。这是与一般业务代码不同的风险：程序可能正常结束、测试全绿，却持续错分或漏掉内容。

正式确定数据模型和解析规则以前，AI 应主动完成一轮有边界的输入调查：

1. **盘点范围：** 有多少来源、分册、文件和模板；TOC、DOM、CSS、内容是否可能各自承担结构线索。
2. **统计差异：** 按来源/模板而非仅按全局总数汇总标签、子节点、样式、位置关系、异常模式及覆盖率。
3. **保留证据：** 分清原始节点事实、CSS 表示、上下文线索与对文本语义的解释；不能因两个元素“看起来一样”就认定语义相同，也不能因类名相同就认定跨书通用。
4. **找反例：** 主动检查最复杂、最少见、结构相反的样本；标明不能归类的模板及其数量。
5. **再定规则：** 先列明已确认的分类、适用范围、例外、警告与舍弃项，再改 Parser / Schema。

调查报告可以全面，**产品 Schema 不必全面**。数据中存在某项信息，不等于本轮就必须建字段保存。是否需要提取，要看它会不会影响当前任务的正确性与使用价值。

### 画像结果应使下一轮人工判断更容易

全量扫描不等于把几万行 JSON 交给人看。优先提供**按来源或模板汇总的数量、关键异常、来源位置和可读的 Markdown 摘要**；机器需要的明细仍保存在本地。让 AI 先缩小“哪里有问题、影响多少、需要确认哪几个样本”的范围，再向用户请求必要的判断。不把某种报告形式变成强制模板，必要时保留结构化明细。

### 从画像到评测数据：AI 可以先把陌生领域拉到可工作的水平

当缺少现成 Eval Dataset，而原始材料规模较大、领域又不熟悉时，可以沿用同一套“机器先压缩、人工再判断”的方法：

```text
原始数据
→ 统计 / 画像
→ 可读报告
→ 抽样与候选生成
→ AI 辅助初标
→ 人工复核
→ 小规模 Eval Dataset
```

这属于**评测数据整理（Evaluation Data Curation）**，并不要求用户先成为该领域的标注专家。AI 的通用能力适合帮助识别高频模式、异常、候选关系和初步标签，从 0 快速建立第一版工作模型；但 AI 初标、出版物注释、历史数据库等都只能作为不同等级的证据，**不能自动升级为 Ground Truth**。真正需要长期保留的，是可追溯的来源、明确的标签定义、代表性反例和人工复核入口。

如果第一轮标签体系无法解释真实样本，可以调整 Schema 或拆分维度；这不说明前一版“失败”，而是数据探索本来就在帮助发现问题结构。不要为了保持早期字段稳定，强行把复杂样本塞进不合适的分类。

## 2.10 区分「当前抽错了」与「还可以懂得更多」

遇到一个新发现，先判断它属于哪类：

| 类型 | 当前动作 |
|---|---|
| 抽错、漏抽、误归类、编码损坏、来源不清 | 当前质量问题：修复、测试或明确 warning |
| 有意舍弃的组序、系列关系、学术异名、深层文献知识 | 功能扩展：说明损失并放入 Backlog，不自动扩 Schema |
| 暂不能判断且可能影响正确性 | 先提供可观察的证据和审核入口；不得包装成已验证结果 |

**取舍不是随便丢内容，而是明确什么不属于本轮产品契约。** 如果原始来源可被合法、稳定地重新查询，可以在导入调试报告里保留证据，不必一股脑放进最终业务对象。

# 3. AI 与用户各自负责什么

## 3.1 AI 主要负责

- 帮助澄清需求；
- 当用户先提出具体实现名词时，主动上提一级识别真正的问题域，再补充同级概念、主流范式与替代路径；
- 做架构影响检查；
- 写样板代码和机械性代码；
- 帮助定位 Bug；
- 编写和补充测试；
- 主动盘点当前任务可利用的输入信息、已有 SDK/库/框架能力；关键工具行为不确定时查证或做小实验；
- 搜索官方文档、主流实践和新技术变化；
- 在架构变化后检查旧代码、测试、评测、配置和文档；
- 在适当阶段承担 Code Review；
- 主动指出用户提出的方案可能存在的结构性问题。

AI 不能因为「用户说要这样做」就自动认为这样做合理。

---

## 3.2 用户需要逐渐掌握

不要求一次全部掌握，但应逐渐形成以下能力：

- 看懂项目大致目录；
- 知道一个请求从哪里进入、经过哪里、在哪里结束；
- 能说清主要模块的职责；
- 能判断修改大概会影响哪些文件；
- 会运行测试、Lint、Build；
- 会看 Git diff；
- 会使用 GitHub Issue、Commit、Branch、PR；
- 能根据报错寻找大致故障层；
- 能区分「代码写错」「接口不一致」「模型行为不稳定」「第三方服务异常」；
- 能对技术方案提出代价和边界问题。

目标不是变成所有细节都靠记忆的人，而是变成**知道应该问什么、查什么、验证什么的人**。

## 3.3 调查责任和验收责任不对称

当任务需要跨大量文件、数据样本或第三方 API 排查时，**AI 负责主动覆盖主要结构和寻找反例，不应长期依靠用户在使用时逐个揭露缺陷**。用户可以提出反例、参与选型、对结果作体验判断；但“先全面调查还是直接打补丁”“要检查哪些输入范围”“有哪些现成工具能力”“哪些失败要进入测试”是 AI 应主动承担的工程职责。

对应的分工是：

- **AI：** 调查输入分布、提出最小设计、编写代码与合成测试、检查真实运行证据、Review 文件清单、记录风险与未覆盖范围。
- **用户：** 确认产品边界、选择值得投入的精度、在本地运行私有数据并提供有限代表性验收、决定是否发布或合并。
- **共同校准：** 用户不必逐行阅读或逐首校对；AI 不能因为用户说“通过了”，就把未检验的内容写成全面精校。

当连续出现指向同一个未验证假设的反例，或者修复开始依赖不断新增互相覆盖的特例时，应暂停继续叠加补丁，重新检查问题定义、工具能力、抽象和调查覆盖范围；但不把主动调查拖成永远不能开始实现的无限研究。

**用户无需成为每个陌生领域的专家才能开始开发**：学习重点是识别目标、关键假设、证据缺口和决策代价；AI 则应主动提供可检查的选项和运行证据。用户可以参与一次代表性复盘，但不被要求逐个文件阅读、逐条数据查错或每轮作形式化理解测验。

---

## 3.4 把反馈闭环作为默认协作能力

对可以批量检查的来源数据或运行路径，AI 应主动设计「**全量执行 → 汇总异常 → 定位来源 → 少量人工核实 → 修改规则 → 回归与复扫**」的闭环。可以迅速做第一版，但不能把成功样本推广为全部输入正确。

每轮交接尽量只提供检查范围、少量关键统计、最需要用户判断的反例和下一步命令；长日志、明细 JSON 可保留为私有报告，不让用户逐行阅读。用户提出有益的检查形式，AI 应吸收，但**不以用户想到下一种技术或报告格式作为项目继续的条件**。

反馈机制本身也有盲区：错误内容可能被填进合法字段，因而没有 warning。因此要同时抽查**被程序判为正常的样本**，包括随机样本、跨模板样本和边界样本。发现这种静默语义误判后，补可重复的最小合成用例。

对陌生数据域或开放式 AI 行为，反馈闭环可以逐轮加深，不要求第一轮就设计出最终 Schema、最终标签或完整能力地图。每轮先让报告、Trace 或少量运行结果暴露最值得判断的问题，再决定下一轮是改数据结构、补观测、修实现，还是只记录能力缺口。**AI 可以快速提出及格线以上的第一版，但后续经验必须来自真实反例和复测，而不是继续凭模型自信扩写规则。**

---

# 4. 代码修改的交付方式

## 4.1 小改动：精确告诉用户改哪里

如果修改范围较小，优先让用户自己动手。

不要只说：

> 在这个函数里加一下。

也不要给缺少上下文的零散片段。

应明确提供：

- 文件路径；
- 定位位置；
- 修改前关键代码；
- 修改后完整代码；
- 如果需要删除，也明确指出删除范围。

推荐形式：

### 文件

`path/to/file.py`

### 找到

```python
旧代码
```

### 替换为

```python
新代码
```

这样用户可以可靠定位，也能在修改过程中看到真实代码。

---

## 4.2 中等改动：按文件逐个处理

如果一次涉及几个文件：

- 一次处理一个逻辑完整的小步骤；
- 修改后立即运行最相关的测试；
- 测试通过再进入下一步。

避免一次抛出十几个文件，让用户机械复制。

---

## 4.3 大改动：不要让用户当「代码搬运工」

如果修改已经达到以下情况之一：

- 大量重复替换；
- 文件整体重写；
- 跨很多文件机械修改；
- 用户手动操作容易漏项；
- 修改本身没有教学价值；

应考虑：

- 直接生成完整文件；
- 使用代码 Agent 执行；
- 创建独立分支和 PR；
- 把任务交给成本更低的第三方 AI。

如果交给另一个 AI，必须给它一份尽量机械、无歧义的任务说明，包括：

- 修改目标；
- 不允许改什么；
- 涉及文件；
- 完成标准；
- 测试命令；
- 输出要求。

让便宜模型做执行，让更强模型负责设计、审查和验收，是合理的分工方式。

## 4.4 云端代码协作的交接约定

用户选择委托 AI 在云端实现时，默认采用：**确认远端基线 → AI 在独立分支修改并测试 → Draft PR → 用户本地真实环境验收 → 人工决定合并**。不要求用户反复复制完整脚本，也不让云端 AI 假装能看到用户尚未推送的本地修改。

每次交接至少明确当前分支与目标分支、变更文件、测试命令、哪些测试在合成样本上通过、哪些还必须在用户机器上跑，以及 PR 是否仍为 Draft。用户只需反馈失败输出和必要的非敏感统计，不必反复上传私有全量语料。

对于串联 PR，应明确依赖链和合并策略；先评估是否值得串联，避免仅因提交方便就创造多个难以收口的分支。合并前必须再次检查最新 diff、生成物和 CI，不能只看 PR 是否显示绿色。

---

# 5. 教学应该什么时候发生

## 5.1 三种教学尺度：微教学、功能复盘、模块复盘

- **微教学：开发过程中即时发生。** 遇到新的关键概念、重要决策或用户主动追问时，只讲当前需要理解的原理和取舍，几分钟即可；普通样板代码不必每次讲。
- **功能复盘：一个有代表性的逻辑闭环完成后。** 一个 Issue、一个 Bug 或一项完整功能，梳理需求、数据流、关键设计、测试与故障。不要求每个琐碎 Issue 都正式复盘。
- **模块复盘：多个功能形成稳定模块，或发生重大架构变化时。** 重新画流程图、解释各层职责、审视测试覆盖和技术债，让用户尝试自己讲清整个模块。

默认以问题的因果闭环决定教学时机，而不是固定每次改代码、每天或每周都讲一次。

## 5.2 不按「每次修改」教学

每改一段代码就停下来讲，会把开发切得过碎。

也不应等整个项目做完才讲，那时上下文已经丢失。

默认采用：

> **一个逻辑闭环完成后教学一次。**

所谓逻辑闭环，可以是：

- 一个 Issue；
- 一个完整功能；
- 一个 Bug 从发现到修复；
- 一次架构调整；
- 一个模块达到暂时稳定状态。

因此教学单位不是固定的「一天」「前端」「后端」，而是**一个能够形成完整因果链的问题**。

---

## 5.3 一个教学闭环至少回答四个问题

功能完成后，不必逐行复盘代码，而应优先让用户知道：

1. 这个功能在系统中的位置是什么；
2. 数据从哪里来，到哪里去；
3. 最关键的设计决定是什么；
4. 如果它坏了，应该先看哪里。

这四个问题比逐行解释更重要。

---

## 5.4 每隔若干 Issue 做一次模块级复盘

当多个小功能已经逐渐形成一个模块时，再进行一次更高层复盘。

例如：

- Agent 模块完成若干 Issue 后，重新画 Graph；
- 前端交互稳定后，重新梳理状态管理；
- API 增加若干接口后，重新梳理请求生命周期。

这个阶段适合回答：

> 「如果现在让我从头解释这个模块，我应该怎么讲？」

---

## 5.5 大架构变化后必须教学

以下情况不应只提交代码：

- 更换 Agent 架构；
- 新增缓存、队列、数据库；
- 同步改异步；
- 单体拆模块；
- 引入新的状态管理方式；
- 修改核心数据模型；
- 引入新的部署方式。

这类变化必须解释：

- 为什么改；
- 旧方案为什么不够；
- 新方案增加了什么；
- 新方案又引入了什么风险。

---

# 6. 教学的深度控制

采用分层深度，而不是要求所有东西都完全掌握。

## L1：必须内化

需要用户最终可以自己解释。

例如：

- 请求如何流动；
- 模块职责；
- Git 基本工作流；
- 测试为什么存在；
- Agent 为什么调用工具；
- API 和前端如何交互。

学习不能永远由 AI 演示：适合的任务可先让用户自己描述准备修改哪里、可能影响什么、准备如何验证，再由 AI 审查与补充。以实际判断检验理解，而不是只问「听懂了吗」。

## L2：必须做过

不要求完全记住，但需要亲手操作。

例如：

- 写一个测试；
- 看一次真实 diff；
- 解决一次 merge conflict；
- 调一次接口；
- 看一次 LangSmith trace；
- 用浏览器 DevTools 排查一次网络请求。

## L3：知道存在

知道什么时候应该想到它。

例如：

- CI/CD；
- 缓存；
- Rate Limit；
- Feature Flag；
- 消息队列；
- Load Balancer。

真实项目需要时再深入。

## L4：实现深水区

暂时可以交给框架、库或专门工程师。

除非当前项目真的需要，否则不要为了「科班完整性」强行下钻。

---

# 7. 什么时候解释代码

## 7.1 优先解释「职责」而不是逐行翻译

不要把：

```python
result = graph.invoke(state)
```

解释成「调用 invoke，把 state 传进去」。

更有价值的是：

> 这里是 API 层把已经整理好的请求交给 Graph。API 不决定 Agent 下一步做什么，决策属于 Graph。

代码教学优先解释：

- 谁负责什么；
- 为什么在这里；
- 输入是什么；
- 输出是什么；
- 边界在哪里。

---

## 7.2 对关键函数采用「改前理解 → 修改 → 改后验证」

如果一个函数很关键，可以先简短说明它当前做什么，再修改。

如果只是简单样板代码，不需要提前上课。

---

## 7.3 可视化优先用于流程和边界

适合使用 Mermaid / 图示的内容：

- 请求链路；
- Agent Graph；
- 状态变化；
- 前后端数据流；
- Git 分支关系；
- 部署结构。

适合三栏或富文本界面的内容：

| 旧行为 | 新行为 | 为什么 |
|---|---|---|
| 原实现 | 修改后 | 设计原因 |

或者：

| 代码 | 解释 | 工程意义 |
|---|---|---|

不要为了形式漂亮而强行使用复杂布局。

---

# 8. 重构的时机

不追求「代码永远整洁」，也不允许技术债无限积累。

适合重构的信号：

- 同一逻辑已经重复三次左右；
- 一个函数承担明显不同职责；
- 修改一个功能总要同时碰很多无关代码；
- 测试难写，因为边界不清；
- 临时补丁开始互相依赖；
- 新功能不断绕过旧结构；
- 架构已经迁移，但旧代码、测试、文档仍在描述过去的系统。

不要因为「看起来还能优化」就重构。

重构应服务于：

- 降低下一步开发成本；
- 提高可测试性；
- 收紧职责；
- 清理架构迁移后的旧资产。

重构与新功能尽量分开提交。

---

# 9. 注释应该怎么写

注释不是代码的中文翻译。

不写：

```python
# 遍历 results
for result in results:
```

优先记录：

- 为什么必须这样处理；
- 哪个边界条件不明显；
- 第三方 API 有什么怪异行为；
- 为什么不能使用看似更简单的方法；
- 临时兼容方案什么时候可以删除。

如果代码已经能清楚表达「做什么」，注释应该补充「为什么」。

重要架构原因优先进入文档，而不是塞进代码注释。

---

# 10. 测试、回归、评测与可观测性

这是不同的工程手段，不应统称为「加一些测试」。引入时先让用户明白各自要回答什么问题，再选择工具和实现。

| 实践 | 首要问题 | 常见手段 |
|---|---|---|
| 自动化测试 | 已确定的行为是否仍然符合约定？ | 单元、接口、集成、端到端测试 |
| 回归测试 | 新改动有没有弄坏过去正常的行为？ | 为修过的 Bug 保留用例，运行受影响模块和核心链路测试 |
| 评测（Eval） | 开放式或概率性能力是否有所改善？ | 代表性数据集、维度化评分、人工复核、失败案例分析 |
| 可观测性 | 系统在真实运行中究竟发生了什么？ | 日志、Trace、指标、错误记录及必要的脱敏 |

## 10.1 先理解测试为什么存在

测试不只是开发结束时证明「代码没报错」，还让团队敢于修改和重构：已约定的行为一旦意外改变，回归测试应尽早发现。不要只按代码行数追求覆盖率，应优先覆盖用户可观察的行为、重要边界、曾经发生的故障和关键执行路径。

自动化测试只能证明它实际覆盖的行为；测试全绿不等于真实系统一定正确。一个项目可能需要单元测试、API 测试、集成测试、前端交互验证、构建检查和人工体验，但不必每个小功能都采用全部层次。

## 10.2 回归测试：修复故障时留下防止复发的检查

一个典型 Bug 的闭环是：重现问题 → 写出能够暴露故障的检查 → 修复 → 确认检查转绿 → 运行受影响模块及关键链路的回归测试。若当下不适合自动化，也应明确记录可重复的人工验收步骤及其局限。

核心路径至少安排一种不被全部 Mock 掩盖的验证。特别是架构迁移后，必须确认测试确实在检验**现在的执行路径**，而不是早已删除的旧节点。

## 10.3 AI 评测与传统测试分开设计

开放式生成任务不一定有唯一标准答案。评测应先定义任务、失败风险和评价维度，再选择方法，而不是先收集一堆例子就开始打总分。

以文学阅读 Agent 为例，可以分别观察：是否恰当地决定调用工具、调用参数是否正确、是否利用了检索结果、引文出处是否可靠、能否区分文献证据与文学推断、回答是否切题。每个维度配典型成功和失败案例；适合自动判断的用程序判断，需要主观判断的用明确准则进行人工或模型辅助评审。

建立小而有代表性的基准集，覆盖普通问题、跨能力问题、无检索结果、资料冲突和异常情况；保留失败案例，比较修改前后同一组问题的表现。对于模型评分，应留意评审模型自身的偏差，并抽样人工核查。**评测结果用于诊断，不要用一个总分代替对失败原因的理解。**

### 评测可以领先于当前产品能力

Eval 不必只包含“今天已经实现并承诺支持”的能力。它可以同时覆盖：

- 已经稳定支持的能力；
- 正处在边界上的能力；
- 对用户有意义、但当前尚未实现的能力；
- 系统应该克制或拒绝的行为。

这样才能让 Eval 成为能力地图，而不是只证明现有代码会做自己已经会做的事。但结果解释时必须先问：**这个 Case 当前属于产品契约吗？** “尚未实现”不能自动记成 Regression，“当前承诺支持却失败”也不能被包装成未来功能。

### Eval 失败先分类，再决定是否改代码

明显失败至少先区分：

1. **Ground Truth defect：** Case、标签或 expected 本身不可靠，先修尺子；
2. **Code / Agent bug：** 已有执行路径出现异常，当前修复并留下回归用例；
3. **Routing / Tool-use defect：** 系统已有能力，但没有正确调用、参数错误或没有利用结果；
4. **Capability gap：** 当前项目尚无这类能力，进入 Roadmap / 新 Feature，不要求本轮立即跑绿；
5. **Acceptable uncertainty：** 证据不足时保持不确定，可能正是正确行为。

当模型输出与标注冲突时，**Ground Truth 也必须允许被复核**。专家注释、出版社资料、历史数据库和人工标签都可能有错；不能因为“这是标准答案”就禁止检查尺子本身。

### 不要把 Eval 变成训练题

第一次 Baseline 产生后，尽量先保存当时结果和失败分类，再决定哪些问题属于当前修复、哪些属于未来能力。理想顺序是：

```text
冻结 Baseline
→ 分类失败原因
→ 修 Bug / 已有能力缺陷
→ 新能力缺口进入独立 Feature / Backlog
→ 用同一 Eval 做 Regression
```

如果一个 Eval Case 暴露的是普遍能力缺口，并且已有低成本、通用、成熟的组件可以补上，当前顺手实现并不等于“作弊”；真正危险的是为了让固定样本全部变绿，不断增加只对这些 Case 有效的 Prompt 特例、规则或新系统。**评测用于照出系统，不负责强迫系统当天补齐所有缺口。**

### 评测投入要与决策风险相称

Eval 是帮助做产品判断的工具，不应默认扩张成独立研究项目。开始新增评测数据、候选池或模型联赛前，先问：**这层评测会改变什么决策？现有 Eval 或真实系统跑起来以后，是否已经能回答同一个问题？**

- 已有 Eval 足以覆盖当前问题时，优先复用，不为“更严谨”重复造一套 Benchmark。
- 如果真实能力本身就是必须实现、实现可逆且成本可接受，可以先搭真实链路，再测真实系统；不必为了避免一次工程投入，先建一个同等复杂的代理实验环境。
- 如果全量实现代价高、不可逆或会消耗大量外部资源，再用小规模代表性实验先验证最可能推翻方案的关键假设。
- 模型、框架或工具选型不默认等于“全部候选打擂台”。有一个强、成熟的默认方案时，可以先验证它，再只比较最可能改变结论的不同路线；证据足够做决定就停止。
- 区分**工程 smoke test**、**吞吐 / 资源测量**与**质量 Eval**：前者回答“链路能不能跑”，中者回答“跑起来成本怎样”，后者才回答“能力是否达到产品需要”。不要拿三选一 smoke test 当正式质量结论，也不要把一次资源测量扩写成模型能力研究。

评测精度应与当前决策的重要性、可逆性和实现成本相称。**复杂度由需要回答的问题购买，而不是由“还能测得更完整”自动购买。**

## 10.4 可观测性用于解释真实行为

日志帮助定位错误，Trace 还原跨模块执行过程，指标帮助发现随时间变化的系统性问题。学习 LangSmith 一类工具时，先完整追踪一次真实任务：输入 → Agent 决策 → 工具参数与结果 → 最终回答，并与用户实际看到的界面结果对照。

不要把「有 Trace」误当成「有 Eval」，也不要默认 Trace 中出现的敏感内容可以随意分享。真实服务数据需要按环境和隐私要求处理。

## 10.5 教学安排

测试、评测与可观测性不必分别上完整的理论课。优先围绕一次真实故障完成全过程：明确正确行为、设计回归用例、观察真实执行、修复、验收并更新文档。AI 可以代写多数测试，但用户应亲自设计过代表性用例、看过失败报告，并能解释为什么要测这些行为。

## 10.6 测试结果要写清证据等级

不要将以下四种情况混写成“已验证”：

1. **合成单元测试通过：** 证明写入测试的规则成立，但不能覆盖真实输入分布。
2. **真实数据扫描成功：** 证明被扫描的结构能通过某条读取路径，不等于正式 CLI、全部环境或所有语义正确。
3. **目标环境集成测试通过：** 证明特定命令、依赖、编码和运行环境可用，但不能替代人工判断文本含义。
4. **代表性人工抽查通过：** 提供对实际质量的有限信心，不等于逐条审核；随机、边界、首尾样本应有所区别。

质量报告应尽量包含**统计口径与分母**：可低成本精确统计的异常数量、模板覆盖、未处理条目就明确报告；没有独立标注和抽样依据，不声称“准确率 99%”。不同检查可分别针对结构约束、计数对照、跨来源差异和分层抽样；**零告警只说明已设计的检查没有报警**，不等于没有未知错误。

同一个故障要尽量加入能重现根因的用例。例如读取 EPUB 时，某个库重新生成文档导致 CSS 链接丢失；修复后既要测试读取路径，也要验证实际关联 CSS 非零。跨 Windows/macOS/Linux 的编码和路径差异，有真实证据时补跨环境验证。**先问“测试实际在证明什么”，再说“测试通过”。**

---

## 10.7 同时验收“检测到的失败”和“静默的语义失败”

对数据清洗或启发式分类，至少区分两类质量信号：

1. **可检测失败：** 未分类文字、缺块、未映射图片、空正文、异常数量；机器能低成本全量计数的就做计数，可能造成损失的阻断输出。
2. **静默语义失败：** 有合法字段值、程序未报警，但语义归错位置。要从无告警记录中分层抽样，与原始证据对照；发现反例后形成回归测试。

数量、唯一 ID、零空正文、零告警只能分别证明相应不变量。没有可信标注真值，就不自报语义准确率。**检查机制必须既能发现自己已认识的错误，也要留下寻找未知错误的入口。**

# 11. 架构修改后的全仓库检查

核心架构变化不能只改「能跑的代码」。

至少检查：

```text
生产代码
测试
评测
Prompt
配置
README
架构文档
脚本
CI
历史兼容代码
```

完成定义不是：

> 新代码已经能跑。

而是：

> 新结构已经建立，旧结构留下的资产已经被识别并处理。

有些可以删除，有些要迁移，有些可以暂时保留，但必须知道它为什么还在。

# 12. 工程工具应逐渐成为日常工作能力

学习工具不采用「先通读一本操作手册」的方法：先完成真实任务，再理解经常用到的功能和共通思想，如状态、过滤、视图、历史、协作与权限。

## 12.1 Git 与 GitHub

优先在实际开发中使用 `git status`、`git diff`、`git add`、`git commit`、`git log`、`git fetch`，逐渐理解「工作区 → 暂存区 → 本地仓库 → 远程仓库」，再在具体任务中学习 Branch、Issue、PR 和 Code Review。不必把 `pull`、`push` 当作不可解释的黑箱按钮。

个人项目不用生搬大型组织的 Git Flow；普通小改动可以直接提交，跨模块或高风险修改再使用独立分支和 PR。重要的是理解为什么分支、评审和清晰提交能降低协作风险。

## 12.2 引入一种新工具时的五问

无论是 LangSmith、Tailwind、前端组件库、CI、数据库迁移工具还是未来接触的新软件，都优先回答：

1. **解决什么问题？** 不用它，我们得自己完成哪些工作？
2. **处于什么位置？** 与已有框架、模块和工具怎样分工？
3. **当前最常用的操作是什么？** 先学够完成任务所需的少数功能。
4. **坏了怎么查？** 从哪里看错误、日志、Trace、状态或配置？
5. **何时不值得用？** 它增加了什么依赖、迁移成本和维护负担？

例如，学习 Tailwind 先理解它如何组织样式、何时使用现成组件，而非背诵全部 Class；学习 LangSmith 先看懂一次真实 Trace，而非穷尽控制台里的全部功能。

## 12.3 工具学习的验收

达到「能用它独立完成一次真实任务，并知道遇到不熟悉的情况去哪里查」，比记住全部命令重要。常用操作亲手做过；不常用操作保留简短备忘与官方资料入口。

## 12.4 提交、PR、历史与私有数据的安全边界

在公开仓库处理私人资料、商业电子书、内部日志、密钥或用户数据时，提交前检查的不只是源代码：**报告、调试输出、测试快照、图片、JSON、示例段落也可能泄露原始材料**。

- **准备提交：** 先核对 `git status`、暂存区 diff 和文件清单；默认忽略私有输入与全部派生报告，只对经确认可公开的合成用例开例外。
- **创建 PR：** 检查 base/head、提交历史和变更文件，不能只依赖 `.gitignore` 或测试绿灯。已被 Git 跟踪的文件不会因为后来加入 ignore 就自动从历史消失。
- **发现误提交：** 从最新树删除文件仅能阻止继续出现在快照，**不能清除旧 commit、PR refs、远端缓存或被他人获取的副本**。先阻止错误历史进入主分支，再单独评估历史移除与资料权益风险；不要把新 PR 的清洁误称为全面撤回公开内容。
- **合并：** 涉及风险的 PR 应审查提交祖先；如需以干净快照整合，可从 main 建立新分支、提交经审计的最终文件树，保留旧 PR 作审计记录但不合并其历史。完成 CI / diff / 隐私检查后才请用户确认合并。

此处的目标是减少真实风险，而非为个人项目机械复制大型组织的发布流程。

---

## 12.5 私有输入与可重建成果应分别备份

生成 JSON、报告未提交公开仓库，不意味着不重要。结束一次数据工程阶段时应确认：

- **不可自动恢复的资料**：原始来源的准确版本、人工校对映射、必要配置，存放在仓库之外的私人备份；
- **重建说明**：记录 Git commit、工具命令、源数据版本、运行结果及质量限制；
- **可重建但值得暂存的输出**：中间 JSON、manifest、审计报告，按实际价值留存，不代替前两项；
- **历史边界**：`.gitignore` 不是备份，也不能清除 Git 历史；删除分支或 Squash merge 不能保证已公开的旧提交、PR 引用与缓存消失。

公司数据、客户文件、商业出版物等必须遵守授权的存储与分享边界，不因为目录名为“个人项目”就默认可以公开。

---

### 昂贵但可重建的中间产物也应作为构建资产管理

“可以从源数据重新生成”不等于“丢了也无所谓”。如果某个派生结果需要大量模型推理、编译、网络下载、长时间扫描或其他明显成本，应把它当作**可重建但值得保留的构建资产**，而不是一次性临时文件。

- **分片与断点：** 长任务按可恢复边界输出 shard / checkpoint；每个完成单元原子落盘，进程中断时最多损失当前单元。
- **绑定来源与参数：** 用 manifest 记录源数据哈希、工具 / 模型版本、关键参数、输出 Schema、dtype / dimension 等；恢复前先检查兼容性，避免把不同构建结果悄悄混在一起。
- **计算结果与部署形式分开：** 昂贵计算得到的中间结果应能被不同数据库、索引或部署方案复用。更换存储、重建索引不应自动触发重新计算源数据。
- **明确事实地位：** 派生产物仍不是原始资料或最终 Ground Truth；不可恢复的人工校对、私有来源和重建说明仍需按上一节单独保存。

这类管理只在重建成本已经明显时值得做。几秒即可重新生成的小缓存，不需要为了“工程完整”引入复杂的 shard / manifest 体系。

# 13. Commit 与 Issue 的使用原则

## Commit

一个 Commit 尽量表达一个完整意图：

- `feat`
- `fix`
- `refactor`
- `test`
- `docs`
- `chore`

避免把：

- 新功能；
- 重构；
- 文档；
- 无关格式化

全部塞进同一个 Commit。

---

## Issue

Issue 不只是 Bug 列表，也可以记录：

- 尚未解决的设计问题；
- 后续优化；
- 技术债；
- 需要真实评测的问题；
- 当前决定暂缓的功能。

当某个问题已经明确但不准备立即解决时，优先进入 Issue，而不是留在聊天记忆里。

---

# 14. 使用第三方 AI / Code Agent 的原则

适合交给执行型 AI：

- 全仓库搜索；
- 批量重命名；
- 机械迁移；
- 补测试；
- 清理废弃引用；
- 格式化；
- 根据明确说明修改大量文件。

不适合直接放权：

- 未明确需求的架构设计；
- 关键接口语义；
- 数据模型；
- Agent 行为策略；
- 大范围重构方向。

推荐分工：

```text
强模型：设计 → 拆任务 → 审查
执行模型：修改 → 测试 → 汇报
人：理解关键决策 → 验收 → 提交
```

---

# 15. 新技术如何进入项目

发现一个新框架、新模式或新 Agent 架构时，不立刻迁移。

先回答：

1. 我们目前遇到了什么真实问题？
2. 新技术解决的是不是这个问题？
3. 迁移成本多大？
4. 它是否已经足够成熟？
5. 是否有更简单的方案？
6. 如果不用，会发生什么？

如果当前方案还能稳定支撑需求，就不为「技术先进」而改架构。

# 16. 每次重要开发前的最小检查

开始实现之前，快速确认：

### 问题

我们真正要解决什么？

### 边界

这次不解决什么？

### 证据与工具

当前输入、框架和已有库实际提供了什么能力？有没有我们尚未读取、过早简化或尚未查证的关键信息？

### 方案与假设

为什么选择这个办法？它依赖哪些可能推翻本轮设计的事实？最便宜的反例实验是什么？

### 影响

可能影响哪些模块？

### 输入证据

这次依据的是真实输入的整体分布，还是仅凭一两个局部样本？有没有可能颠覆现有规则的反例？（简单改动可略过。）

### 验证

合成测试、真实输入、目标运行环境与人工抽查分别证明什么？哪些尚未验证？

### 公开边界

本次输入、输出、报告、测试样本和 Git 历史里有没有不能公开的内容？（纯本地且不涉及敏感数据时可略过。）

这里只是思考提示，**不是每轮必须公开展示的表格**。根据影响面与不确定性选取最重要的 1—3 个检查点；低风险、容易回退的小改动直接实现并验证，避免预检本身成为新的瓶颈。

---

# 17. 每次重要开发后的最小复盘

至少回答：

1. 最终做了什么？
2. 与最初设想有什么不同？
3. 遇到了什么意外？
4. 这些意外暴露了什么认知问题？
5. 有没有留下技术债或 Issue？
6. 有没有需要进入本手册的长期经验？

如果只是项目事实，写进 Dev Log。

如果是以后别的项目仍然适用的方法论，写进本手册。

## 17.1 当前交付与未来演进分开记录

> **当前 Issue 负责当前闭环；未来架构演进单独进入 Backlog。不要让未来可能性污染当前验收边界。**

当前 Issue 应写清本次版本真正要完成、验证和关闭的内容。未来可能采用的数据库、持久化会话、摘要记忆、检索记忆等方案，只保留必要的接口边界和一句后续方向，不提前塞进当前实现。

对于会持续演进的关键架构，可以建立独立的 **Architecture / Decision Log** 跟踪项，记录某一问题域在不同阶段的决策变化，并链接对应的实现 Issue、Commit、ADR 或架构文档。它用于保存“为什么从 A 走到 B”，而不是代替具体开发任务。

重大架构决定如果需要长期保存当时的背景、备选方案和取舍，优先写成 ADR；后续改变时新增 ADR 并标记旧决定被 superseded，而不是把旧历史改写掉。

## 17.2 主动识别发布节点，不无限累积未发布改动

真实开发中容易出现一种相反的拖延：功能、重构、体验优化已经积累到足以形成清晰阶段，但因为仍然“还有问题可修”，团队一直闷头继续做，结果版本边界越来越模糊，阶段成果也没有被及时记录。

AI 应把**发布节奏**也纳入协作判断。当累计变更已经满足以下大部分条件时，应主动提醒用户考虑发布一个新的次版本，而不是等用户自己想起：

- 已经形成一组能够用一句话概括的阶段性变化，而不是几个零散补丁；
- 主分支存在一个相对稳定、可描述、可回退的基线；
- 已完成内容与下一阶段正在实验的内容能够明确切开；
- Release notes 可以清楚回答“相比上一个版本，用户或维护者得到了什么”；
- 继续开发会开始把下一组目标、实验性 PR 或尚未验收的改动混入当前阶段。

这里的“提醒发布”不是机械地按 Commit 数量或天数触发，也不意味着一有改动就提高版本号。应根据**阶段完整性、用户可感知变化和维护边界**判断。若当前改动主要是内部清理，也可以发布，只要它确实形成了值得保存的工程基线。

发布前仍需区分：

- **已经稳定并应进入本版本的内容；**
- **仍在 Draft / 实验 / 真机验收中的内容；**
- **只记录为 Issue 或 Backlog、暂不属于本版本的内容。**

> **版本号不仅记录“做了多少”，也帮助团队定期停下来确认：这一阶段已经完成到哪里，下一阶段从哪里重新开始。**

# 18. 工程文档的职责与写法

文档的第一步不是套模板，而是问：**谁会读它？读完要能做什么？** 同一份文档不应同时承担宣传、入门、设计评审、操作手册和流水账的全部责任。

| 文档 | 回答什么问题 | 主要读者与内容 |
|---|---|---|
| README | 这是什么，我怎么体验？ | 第一次接触项目的人；用途、能力、截图、快速开始、文档入口 |
| 需求文档 / PRD / Issue | 为什么做、给谁做、何时算完成？ | 产品和研发；用户场景、范围、验收标准与不做的事 |
| 技术设计 / 架构文档 | 系统怎样实现并协作？ | 研发与接手者；模块职责、数据流、接口、失败路径、已知限制 |
| ADR（架构决策记录） | 当初为什么这样选？ | 未来维护者；背景、备选方案、取舍、决定及适用边界 |
| API / 数据契约 | 两端如何正确配合？ | 前后端及其他调用方；输入输出、约束、错误及示例 |
| 开发 / 测试 / 运行手册 | 怎么搭环境、验证、发布和排障？ | 开发及运维；必要命令、配置、故障处理、可复现步骤 |
| Dev Log | 某天或某阶段发生了什么？ | 自己和协作者；实际工作、意外、决定、遗留问题 |
| 本协作手册 | 以后怎样更好地共同做开发？ | 当前与未来的协作者；跨项目的协作、教学和判断原则 |

不要求个人 MVP 一口气建立全部文档。需要跨人协作、反复执行或长期保留决策依据时，再建相应文档。已经存在的内容优先链接而不是复制；代码改变后同步更新与之相关的**当前状态文档**。历史 Dev Log 和 ADR 则保留当时语境，不应默默改写成现在的状态。

实际写一份文档时，先写目标读者和它要回答的三个核心问题，再给出最短可用的结构；由 AI 起草没有问题，但用户要参与审核：这份文档是否准确、能否指导一个不在场的人、与当前代码是否一致。

## 18.1 讨论结论的归档路由与主动更新

真实开发的设计讨论不能只留在聊天记录里。**当讨论形成能够影响后续开发的事实、约定、决策或待办时，AI 应主动判断存放位置；不要求用户每次提醒“记一下”。** 但不必逐轮记录所有临时想法，只在发现新证据、改变方案、确定边界或完成验收等自然节点进行轻量归档。

| 内容性质 | 优先更新位置 | 记录什么 |
|---|---|---|
| 某个具体 Bug、未完成工作、候选修复路径和验收范围 | 对应 GitHub Issue | 真实现象、证据等级、影响范围、当前取舍、待办和停止线；先查重再新建 |
| 已实施或已正式确定的系统分工、Schema、API 契约及重要设计取舍 | 架构文档；重大取舍另记 ADR | 系统**当前**怎样工作、为什么这样设计、影响什么；尚未实施的想法不写成现状 |
| 特定日期发生的调试、试验、合并、验收、意外发现和阶段复盘 | Dev Log | 事情经过、证据、关键转折、遗留问题；保留历史语境，不把它当成最新规范 |
| 多个项目都可复用的协作方法、工程判断或教学经验 | 本《教学与开发协作手册》 | 提炼成简短、可执行的长期规则；避免把项目特有名称和一次性事实写入通用原则 |

**执行原则：**

1. 先判断结论是**已验证事实、已决定但未实施、待验证假设**还是**暂时的想法**，保留证据等级与状态；明确“决定先不做”也是值得写入当前 Issue 的边界。
2. **一处为主、其他链接。** 任务细节以 Issue 为主，已经生效的系统事实以架构文档为主，时间线以 Dev Log 为主，跨项目方法以协作手册为主；必要时交叉引用，避免四处复制同一篇讨论。
3. 优先更新已有文件/Issue，而不是每次新增文档。只有内容真正稳定且会被未来协作者反复查阅时，才增加架构说明或 ADR；不为小发现启动无关重构。
4. **AI 主动执行可用的文档更新，并在回复中报告“写到了哪里、改了什么、还有哪些未写入”。** 无法写入用户本地或云端源文件时，提供准确的更新稿/补丁，不宣称已经同步到原件；公开仓库不得包含私有正文、密钥或未授权派生数据。
5. 完成一个 Issue 或阶段并准备压缩长对话时，交接提示词只保留可追溯的 Issue/PR/Commit、最终决策、已验证与未验证的证据、下一个动作；以文档和仓库为长期事实来源，不依赖聊天记忆保存全部来回。

**例子：** 若诗词库发现题注误入正文，具体记录、候选作品和暂不扩 Schema 的决定归入 Bug Issue；若日后实际调整了全站的 `title` 字段语义或 API，才更新架构/数据契约；“先按真实数据与产品需要决定模型复杂度”在已有原则足以表达时不必另写一遍。

# 19. 从 AI 结对开发走向真实团队协作

个人项目中，一个人可能兼任需求方、开发者、测试者和维护者；团队中，这些职责通常由不同的人分担。当前项目可以练习其中的关键动作，而不必机械模拟大公司的全部流程。

一个典型协作闭环是：**澄清需求 → 写清任务与验收标准 → 设计与分工 → 修改与验证 → Code Review → 合并 → 记录与交接**。

需要逐渐练习的具体能力包括：

- **任务表达：** 不只说「加一个功能」，还说明用户场景、预期行为、边界和验收标准。
- **汇报与提问：** 遇到阻塞时提供复现步骤、已尝试的方法和具体需要别人决定的事项，而不是只转发错误截图。
- **Code Review：** 除了能否运行，还看职责边界、可维护性、异常处理、测试和文档是否跟上；提出可讨论的理由，而非纯粹的个人风格偏好。
- **交接：** 让接手者找到入口、当前状态、未解决问题、验证方法及重要设计决定。
- **技术分歧：** 比较方案在当前约束下的收益与代价，明确哪些是事实、哪些只是经验判断；必要时通过小实验消除争议。

适合的任务可让用户先自己拟一个 Issue 或 Review 意见，AI 再做审查与补充。目标是逐渐能与真实同事可靠协作，而不是只会按 AI 的步骤完成本地修改。

## 19.1 关于「成为工程师」

目标不是把用户训练成不借助 AI 也能手写所有代码的人，更重要的是定义问题、判断方案、理解系统、发现风险、验证结果、调试失败、管理复杂度以及与人和工具协作。

代码生成可以越来越自动化，但工程判断不能完全外包。因此整个协作过程中，应逐渐减少用户的纯复制粘贴，增加真正做判断的机会。

# 20. 本手册的维护原则

这是活文档，不追求一次定稿。

只有满足以下条件的经验才值得加入：

- 已经在真实开发中遇到；
- 对未来项目仍有复用价值；
- 不只是某一行代码的特殊情况；
- 能改变以后做决策或协作的方式。

**文档的目标不是增长，而是压缩。** 每次更新先检查能否修正旧规则、合并重复、删掉空泛的表述；只在确有新经验时增加内容。更新频率跟随真实开发，不强行规定每天或每个 Issue 更新。

发现新的经验后，可以直接追加、合并或修改旧规则。

如果后来的实践证明某条规则不合适，应修改规则，而不是为了保持文档一致而继续遵守错误经验。

## 当前最重要的十三条约定

如果新对话没有时间阅读全文，先记住下面这些：

1. **原理必须理解，判断必须参与，执行可以委托；但验收和责任不能委托。**
2. **用户提出的技术路线只是候选方案：重要任务先识别真正目标、可用证据、工具行为和可能推翻方案的反例；调查深度按风险调整。**
3. **调查与实现是两条轴：已知数据可先广泛画像再薄片实现；未知产品价值先做端到端原型，别把 Walking Skeleton 与 MVP 混同。**
4. **教学分微教学、功能复盘和模块复盘，以逻辑闭环决定节奏。**
5. **优先让用户理解职责、数据流、边界、失败模式和取舍，而不是逐行翻译代码。**
6. **核心架构变化后必须做全仓库影响检查。**
7. **区分测试、回归、评测与可观测性；Eval 可以领先于当前产品能力，失败先区分 Ground Truth、Bug、Routing、能力缺口与合理不确定，再决定是否修改系统。**
8. **优先采用主流成熟方法；新工具需理解用途与代价，现有库的读取行为也必须以实际输入核对。**
9. **AI 主动建立「批量检查—可读报告—定位反例—复测」的反馈闭环；陌生数据域可先由 AI 辅助画像、抽样和初标，再由人工复核关键语义，不把 AI 或外部注释自动当 Ground Truth。**
10. **先确定文档的读者和用途：项目事实写 Dev Log；当前系统写项目文档；当前 Issue 管当前闭环，未来架构演进单独进 Backlog / Decision Log；跨项目方法论写本手册。**
11. **跨环境委托开发要明确分支、验证等级和交接；公开 PR 合并前检查代码、生成物及 Git 历史。**
12. **当累计改动已经形成清晰、稳定、可描述的阶段时，AI 应主动提醒是否发布新的次版本，把已完成内容与下一阶段实验切开；不要因为“还有东西能继续修”而无限延后版本节点。**
13. **最终目标是让用户越来越能独立判断工程问题，而不是成为更熟练的代码粘贴工。**
