# 术语审校

**版本**：v0.1.1（首次缩写锚点规则修订）

**状态**：可增长审校手册  
**用途**：在技术文档冻结前检查正式术语、普通词、伪术语、中英文主称和局部歧义。  
**依赖**：《中文表达》《技术文档》  
**来源**：检查项由旧 07C 重组；旧 07C 的领域词表、反例和完整说明保留在检查表之后。

# 1. 使用方式

本手册不是禁词表，也不执行机械替换。检查项使用 `T` 编号；遇到新领域或新误用时，可以直接增加检查项或词条。

| 级别 | 含义 | 处理原则 |
| --- | --- | --- |
| A | 术语被误用、定义被偷换或技术对象被混淆 | 必须修改 |
| B | 容易制造稳定误解、伪术语或局部歧义 | 冻结前优先修改 |
| C | 主称、空格和一致性问题 | 全文统一即可 |

# 2. 检查项

## 2.1 正式术语与普通意思

- **T001 · A**：当前词是否真的在使用其正式技术含义？若是，是否被 Plain 化错误地隐藏或替换？
- **T002 · B**：`调用`、`映射`、`接口`、`绑定`、`路由`、`调度`、`驱动`、`挂载`、`回滚` 等词是否只是借来表达普通使用、对应、关系、安排或恢复？
- **T003 · B**：一个泛化技术词是否同时掩盖了多个不同事实，无法通过单个同义词安全替换？
- **T004 · B**：改写前是否先还原「谁在什么条件下，对什么做了什么，结果怎样」？
- **T005 · A**：指针、引用、句柄、事务、View、Socket、Workload 等正式概念是否被近似但不同的普通词替代？

## 2.2 伪术语与抽象包装

- **T020 · B**：连续名词组合本身是否真的是当前需要学习和复用的正式名称？
- **T021 · B**：`语言功能`、`系统能力`、`资源关系`、`状态模型`、`执行机制`、`知识承重关系` 等组合是否让读者误以为多了一个新概念？
- **T022 · B**：拆开名词组合时，是否只是机械增加「的」，而没有恢复真实动作和关系？
- **T023 · B**：删除技术词以后，是否又使用 `机制`、`体系`、`能力`、`维度`、`支撑`、`承载` 等抽象词将意思重新包装？
- **T024 · B**：某个临时名称是否真的需要反复使用；若只出现一次，是否可以直接写关系？

## 2.3 局部歧义

- **T040 · B**：同一小节中，一个词是否在技术义与普通义之间频繁切换？
- **T041 · B**：Git 章节中的「提交」、数据库章节中的「视图」、网络章节中的「连接」、AI 章节中的「推理」「训练」「对齐」是否可能产生局部歧义？
- **T042 · B**：`上下文`、`模型`、`状态`、`对象`、`资源`、`环境` 是否已经说明所属系统或具体对象？
- **T043 · B**：跨领域同名词是否通过限定语完成消歧，例如进程上下文、请求上下文和 LLM 上下文窗口？

## 2.4 中英文主称与首次锚点

- **T060 · B**：重要陌生术语第一次出现时，是否先说明其意义，再建立必要的中文、英文或缩写锚点？
- **T061 · C**：存在成熟自然中文且中文社区普遍使用时，后文是否无必要地长期保留英文主称？
- **T062 · C**：中文译名生硬、社区通常直接使用英文时，是否为了形式统一而强行中文化？
- **T063 · C**：缩写已经成为常用主称时，首次锚定后是否仍然反复写全称？
- **T064 · C**：同一章节选定主称后，中文、英文和缩写是否前后摇摆？
- **T065 · C**：英文概念是否仅因使用英文就误加代码格式？
- **T066 · C**：Token、Tokenizer、Checkpoint、KV Cache、Batch、dtype、Benchmark、Serving、Kernel、LoRA、MoE、Prefill、Decode 等社区常用英文是否按具体语境决定主称，而不是机械翻译？
- **T067 · B**：以英文缩写为社区主称、且有可靠英文全称与稳定中文名称的正式术语，首次正式引入时是否同时给出两者，例如「ASGI（Asynchronous Server Gateway Interface，异步服务器网关接口）」？
- **T068 · B**：无稳定中文译名时，是否将中文解释作为释义，而不是创造一个看似官方的固定译名？
- **T069 · C**：如果缩写先出现在标题、代码或章首总图中，是否在紧随其后的首次解释性正文中建立完整锚点，而不是为了避免长标签放弃解释？
- **T070 · C**：后文是否保留社区通行主称，且未将 FastAPI、Uvicorn 等专有名称强行拆成不存在的英文全称？

## 2.5 词表维护

- **T080 · B**：新增词条是否记录了技术语境、常见误用、改写时应追问的问题和跨领域歧义？
- **T081 · B**：词条是否被误写成「某词永远不能使用」的禁词规则？
- **T082 · C**：新发现是否只是既有检查项的例子；若是，是否只补例子而不新造原则？
- **T083 · C**：多个词条长期反复指向同一稳定规律时，是否应将规律上提到《中文表达》或《技术文档》？

# 计算机技术词使用边界与术语形态规范（旧 07C 原文）

本规范与《07A 技术学习笔记 Markdown 排版与结构规范》《07B 技术学习笔记 Plain Chinese 行文规范》配套使用。

07A 负责标题、正文、表格、数学、Mermaid、术语锚点和 Markdown 结构；07B 负责把中文写得直接、自然；本规范负责另一类问题：

> **已经具有技术含义的词，不随意借来表达普通意思；普通词也不要无意拼成一个看起来像新术语的名词。**

技术术语本身没有问题。真正学到一个技术概念时，应正常使用正式名称，并把它解释清楚。本规范要避免的是：正文原本只想表达「使用、需要、放在、先做、后做、从这一点看」，却写成「调用、依赖、承载、映射、调度、视图」；或者把几个普通词直接压在一起，形成「语言功能、资源关系、执行机制、系统能力」之类似乎需要额外定义的表达。

> **术语回到术语的位置；普通解释保持普通中文。**

---

# 1. 三类不同的问题

技术笔记中需要分别检查三类语言问题。

| 问题 | 典型现象 | 处理位置 |
| --- | --- | --- |
| 技术词泛化 | 用「调用」表示普通使用，用「映射」表示普通对应 | 本规范 |
| 无意制造伪术语 | 「语言功能」「状态关系」「资源模型」等名词直接拼接 | 本规范 |
| 普通中文仍然过度抽象 | 「机制、体系、能力、维度、承载、支撑」等大量出现 | 07B，同时受本规范约束 |

三类问题可以连续发生。例如：

> 上层通过接口调用下层提供的能力。

这里同时出现：

- 「接口」可能被泛化；
- 「调用」可能被泛化；
- 「提供能力」又属于抽象说明书式表达。

因此不能只做一次同义词替换。

---

# 2. 第一原则：真正的术语正常使用

如果当前确实在讲某个正式技术概念，不要因为它容易产生技术联想就回避它。

例如：

> `main()` 调用 `foo()`。

这里确实发生函数调用（Function Call），「调用」必须保留。

又如：

> 链接器处理符号和重定位，把目标文件与需要的库组合成可执行文件。

这里讲的就是 Linking，「链接」属于正式术语。

同样：

- 数据库 View 正常称为「视图」；
- Kubernetes Node 正常称为「节点」；
- Python Object 正常称为「对象」；
- TCP Connection 正常称为「连接」；
- 文件描述符（File Descriptor, fd）正常称为「文件描述符」；
- Runtime、Socket、Hook 等如果中文技术社区通常直接使用英文，也按 07A 的术语规则处理。

> **Plain Chinese 负责解释术语，不负责隐藏术语。**

---

# 3. 第二原则：普通意思不用技术词包装

如果当前并没有在讲对应技术概念，就优先使用普通中文。

例如：

不推荐：

> 学习这一节时，可以调用上一层的模型。

推荐：

> 学习这一节时，可以直接使用上一层已经学过的模型。

不推荐：

> 把这个概念映射回前面的知识。

推荐：

> 看看这个概念和前面哪些知识对应。

不推荐：

> 从另一个视图看这个问题。

推荐：

> 从另一个角度看这个问题。

不推荐：

> 下层为上层提供能力。

推荐：

> 上层可以直接使用下层已经规定好的对象和操作。

如果已经知道具体是什么，应进一步点名：

> 用户程序通过系统调用请求内核读文件。

通常比：

> 用户程序通过内核提供的接口调用文件能力。

更清楚。

---

# 4. 不建立机械替换表

本规范不规定：

$$
\text{接口}\rightarrow\text{入口}
$$

或：

$$
\text{依赖}\rightarrow\text{支撑}
$$

因为同一个泛化词可能掩盖完全不同的事实。

例如：

> 上层使用下层提供的接口。

如果这里真正说的是系统调用，可以写：

> 用户程序通过系统调用请求内核完成工作。

如果这里说的是 ISA，可以写：

> ISA 规定软件可以使用哪些指令、寄存器和机器状态。

如果这里只是在说明人为划出的上下层关系，可以写：

> 上一层只需要知道这一层允许它做什么，以及结果应该是什么。

三种情况没有一个统一的「接口替代词」。

因此，遇到泛化词时先问：

1. 这里有哪些具体对象？
2. 谁在做什么？
3. 什么条件下发生？
4. 做完以后发生什么变化？
5. 这层关系真的需要单独命名吗？

如果第五题答案是否定的，就直接写事情本身。

---

# 5. 技术词占用分级

本规范按写作风险把词分成三类。这个分级只是编辑工具，不是计算机科学中的正式分类。

| 类型 | 含义 | 默认处理 |
| --- | --- | --- |
| **A：技术意味较强** | 容易让读者立即联想到已有技术概念 | 普通叙述尽量避开；真正讲该概念时正常使用 |
| **B：技术中常见，但普通中文也常见** | 技术含义较多，日常中文也自然 | 可以使用，但尽量具体，并注意同一段中的歧义 |
| **P：抽象写作触发词** | 不一定是技术术语，但很容易产生说明书腔 | 出现时按 07B 再检查一次 |

例如：

- 「链接、调用、接口、映射」通常属于 A；
- 「状态、对象、环境、关系」通常属于 B；
- 「机制、能力、体系、承载」属于 P。

---

# 6. A 类：普通叙述中优先避开的技术词

## 6.1 跨层与软件结构

| 中文词 | 常见技术语境 | 普通叙述中需要检查什么 |
| --- | --- | --- |
| **接口** | API、ABI、硬件接口、语言 Interface | 是否真的存在明确的交互边界和规定 |
| **协议** | TCP、HTTP、TLS 等 | 是否真的规定了通信双方交换信息的方式 |
| **依赖** | 包依赖、模块依赖、构建依赖、服务依赖 | 是否真的表示「缺少 B，A 就不能正常工作」 |
| **调用** | 函数调用、方法调用、系统调用、RPC | 是否真的发生一次 Call |
| **链接** | 编译链接、硬链接、符号链接、网络 Link | 是否真的属于这些具体连接关系 |
| **映射** | 地址映射、文件映射、ORM、数学 Mapping | 是否真的存在明确对应规则 |
| **绑定** | 名称绑定、端口绑定、数据绑定、Kubernetes Binding | 是否真的发生 Binding |
| **路由** | 网络路由、Web 路由、请求路由 | 是否真的根据规则选择目标 |
| **调度** | CPU、线程、任务、协程调度 | 是否真的存在调度者选择下一项 |
| **上下文** | CPU Context、线程上下文、请求上下文、Docker Context | 是否可以直接说明当前保存了哪些信息 |
| **视图** | 数据库 View、MVC View、前端 View | 普通「角度」不要写成视图 |
| **框架** | Spring、Vue、Web Framework 等 | 普通文章结构、理解方式不要写成框架 |
| **平台** | OS 平台、云平台、开发平台 | 能否直接点名具体系统 |
| **组件** | 软件组件、前端组件、Kubernetes Component | 是否真的指一个正式组件 |
| **实例** | OOP、数据库实例、云实例 | 普通「一个具体的……」优先直接点名 |
| **服务** | 系统服务、微服务、Kubernetes Service、云服务 | 当前究竟是哪一种 Service |
| **端点** | API Endpoint、网络 Endpoint、安全 Endpoint | 能否直接说 URL、主机、进程或接收方 |
| **代理** | 网络 Proxy、Proxy Pattern | 普通中介关系不自动称为代理 |
| **控制器** | 硬件 Controller、MVC Controller、Kubernetes Controller | 必须确认具体领域 |
| **适配器** | Adapter Pattern、硬件 Adapter | 普通「转换一下」不要自动命名为适配器 |

## 6.2 编程语言与 Runtime

以下词真正进入相应章节以后正常使用：

`对象、类、实例、成员、属性、字段、方法、参数、返回值、指针、引用、作用域、绑定、闭包、继承、多态、封装、重载、重写、泛型、模块、包、导入、解释、求值、回调、钩子、生成器、迭代器、协程、事件循环、异常、任务`

普通叙述特别注意：

- 普通「东西」不要全部叫「对象」；
- 普通「种类」不要写成「类」；
- 普通「一个例子」不要写成「实例」；
- 普通「沿用」不要写成「继承」；
- 普通「包起来」不要写成「封装」；
- 普通「后续处理」不要自动写成「回调」；
- 普通「插入一步处理」不要自动写成「钩子」；
- 普通「指定给」不要自动写成「绑定」。

真正讲 Pointer、Reference、Coroutine 等概念时，不能为了 Plain 把正式名称删掉。

---

## 6.3 编译、链接与构建

正式技术词包括：

`预处理、编译、汇编、链接、装载、目标文件、符号、重定位、中间表示、优化、构建、构建目标、构件 / 制品、阶段、流水线`

尤其注意：

- 普通「把两个知识联系起来」不要写「链接」；
- 普通「最终想达到什么」可以说「目标」，但在 Build Target 附近应避免歧义；
- 普通「按步骤处理」不要自动写成「流水线」；
- 普通「产生一个东西」不要因为技术文章就写成「生成构件」。

---

## 6.4 操作系统、Linux 与硬件

技术含义较强的词包括：

`进程、线程、调度、上下文、中断、异常、陷阱、信号、页、帧、段、地址映射、缓存、端口、通道、控制器、驱动、文件描述符、句柄、Socket、管道、挂载、Namespace、Daemon`

特别注意：

- 普通「打断」不要写成「中断」；
- 普通「迹象」不要写成「信号」；
- 普通「推动某事」尽量不要写「驱动」；
- 普通「渠道」不要随意写「通道」；
- 普通「接到某处」不要写「挂载」；
- 普通「流程」不要写「管道」。

---

## 6.5 网络与分布式系统

技术词包括：

`连接、会话、协议、链路、路由、转发、交换、包、帧、流、通道、消息、队列、主题、发布、订阅、代理、网关、端点、端口、节点、主机、客户端、服务端、请求、响应、负载、负载均衡、握手、心跳、超时、重试、熔断、背压、副本、选举、共识、一致性、分区、故障转移、幂等、偏移量`

普通叙述尤其避免：

- 「打通链路」；
- 「路由到下一部分」；
- 「形成闭环」；
- 「产生背压」；
- 「上下游」泛化到没有真实数据流的关系；
- 「心跳」泛指普通确认。

---

## 6.6 数据库

技术词包括：

`关系、表、行、列、字段、记录、元组、视图、模式、索引、键、主键、外键、约束、查询、事务、提交、回滚、保存点、隔离、一致性、持久性、锁、游标、会话、连接、触发器、存储过程、分区、副本、日志、检查点、快照`

普通技术文章尤其注意：

- 「从这个视图看」→「从这个角度看」；
- 「回滚到旧理解」→「恢复到之前的理解」；
- 「提交观点」在 Git / 数据库密集章节附近尽量改成「交出」「写下」「确认」等更明确表达；
- 「模式」如果只是普通方式，优先写「方式」。

---

## 6.7 Web 与前端

常见正式词包括：

`模型、视图、控制器、路由、组件、实例、属性、状态、上下文、钩子、生命周期、挂载、卸载、渲染、模板、插槽、指令、事件、监听器、处理器、节点、文档、元素`

避免：

> 把知识挂载到旧模型。

> 从另一个视图看。

> 给这一章设计生命周期。

> 把问题路由到下一层。

如果只是普通中文，直接写真实动作。

---

## 6.8 云原生与 Kubernetes

常见正式词包括：

`集群、节点、容器、镜像、层、卷、服务、工作负载、控制器、控制平面、名字空间、资源、对象、规约、状态、标签、注解、污点、容忍、驱逐、绑定、副本、部署、作业、定时作业、入口、网关、代理、侧车、编排、调度、伸缩、弹性、可观测性、指标、追踪、探针、健康检查、配额、策略`

普通说明中尤其避免：

- 「编排知识」；
- 「调度内容」；
- 「挂载配置」；
- 「工作负载很高」用于普通工作压力；
- 「控制平面」作为普通管理层比喻；
- 「侧车」作为一般旁路组件比喻。

## 6.9 Git、CI/CD 与工程工具

常见正式词包括：

`仓库、分支、提交、合并、冲突、变基、检出、暂存区、索引、引用、标签、远程、推送、拉取、获取、工作区、钩子、子模块、构建、构件 / 制品、流水线、工作流、阶段、作业、步骤、运行器、触发器、部署、发布、环境、缓存、任务、目标`

这些词很多也属于普通中文，因此技术密集章节中要注意一词多义。

例如在 Git 章节附近：

> 提交一个想法。

可以根据上下文改成：

> 写下一个想法。

避免与 Commit 紧邻使用。

`身份、主体、认证、授权、权限、特权、角色、策略、令牌、凭据、证书、密钥、公钥、私钥、信任、会话、签名、摘要、哈希、盐、挑战、响应、漏洞、威胁、攻击面、沙箱、隔离、审计`

普通叙述中尤其注意：

- 「授权某个模块做事」；
- 「隔离两个概念」；
- 「审计知识漏洞」；
- 「攻击面」作为普通风险比喻。

真正处于安全章节时则正常使用。

## 6.11 AI 与数据

常见正式词包括：

`模型、训练、推理、参数、权重、层、网络、节点、激活、损失、优化、梯度、张量、向量、嵌入、注意力、头、上下文、窗口、Token、Prompt、Agent、工具、调用、记忆、检索、排序、生成、采样、温度、幻觉、微调、对齐、路由、专家、检查点、批次、Epoch、样本、标签、特征、评估、基准`

这里尤其注意：

- 「推理」在 AI 中已经有具体含义，普通 reasoning 可以根据上下文写「判断」「推导」；
- 「训练」可以正常表示人的学习训练，但 AI 教程附近容易产生歧义；
- 「对齐」不要泛指一切「保持一致」；
- 「上下文」「记忆」「工具」「调用」在 Agent 文章中技术含义尤其强；
- Token 在不同领域含义不同，不能机械翻译成同一个中文词。

# 7. B 类：可以使用，但优先具体

以下词既属于普通中文，又大量出现在计算机技术中。完全禁止会破坏正常中文，因此不作为默认禁用词。

| 中文词 | 使用原则 |
| --- | --- |
| **状态** | 尽量说明是谁的状态 |
| **对象** | 能点名进程、文件、模块时优先具体 |
| **环境** | 尽量说明是哪一种环境 |
| **资源** | 能写 CPU、内存、文件、连接时直接写具体内容 |
| **关系** | 不要用它代替本来可以直接写出的动作 |
| **连接** | 普通连接可以用；网络章节注意 TCP Connection |
| **事件** | 最好说明发生了什么事件 |
| **规则** | 可以正常使用，但能把规则本身写出来时更好 |
| **过程** | 不要让「处理过程」掩盖具体动作 |
| **层** | 可以正常用于分层；注意和神经网络层、镜像层等局部歧义 |
| **节点** | 图论、网络、DOM、Kubernetes 中技术意味很强，其他场合谨慎泛用 |
| **路径** | 文件、网络等领域有技术含义；普通叙述可直接写实际路线或步骤 |
| **模型** | 真正指简化现实、用于解释和预测的表示时可以保留 |
| **工具** | 可以正常使用；能点名程序时直接点名 |
| **系统** | 可以使用，但不要把一切东西都升级成「系统」 |
| **结构** | 普通中文，可以用；如果能直接说包含哪些部分则更好 |
| **功能** | 可以用，但优先说明具体能做什么 |

# 8. 普通名词不要无意拼成新术语

这是本规范的核心检查之一。

中文技术写作中，大量正式术语本身就是「名词 + 名词」：

- 系统调用；
- 文件描述符；
- 虚拟内存；
- 线程调度；
- 执行状态；
- 模块搜索路径。

因此，两个或多个普通名词直接压在一起时，也很容易让读者误以为它们是一个需要学习的新术语。

例如：

`语言功能、系统能力、资源关系、状态模型、模块边界、执行机制、运行规则、模型恢复路径、知识承重关系`

其中有些组合并不是错误，但如果正文没有准备正式定义它们，就容易产生额外的术语感。

## 8.1 先判断它是不是正式名称

遇到连续名词时先问：

> **这个组合本身是不是当前需要学习的正式术语？**

如果是，正常保留：

- 系统调用；
- 文件描述符；
- 虚拟内存；
- 线程状态；
- 事件循环。

如果不是，再问：

> **直接把几个名词压在一起，会不会让人误以为这里多了一个固定概念？**

如果会，就拆开。

## 8.2 拆开不等于机械加「的」

不要把：

> 语言对象

机械改成：

> 语言的对象。

后者可能仍然生硬。

应根据真实意思选择更自然的句法。例如：

> Runtime 维护这种语言中的对象。

又如：

原句：

> Runtime 提供语言功能。

不建议只改成：

> Runtime 提供语言的功能。

更好的写法是直接说明：

> Runtime 负责执行这种语言的代码，并维护程序运行时需要的对象和状态。

## 8.3 常见改写方向

| 容易形成伪术语的组合 | 更自然的方向 |
| --- | --- |
| 语言功能 | 这种语言可以做什么；直接写具体功能 |
| 系统能力 | 系统允许程序做什么 |
| 资源关系 | 这些资源之间是什么关系；直接写具体关系 |
| 状态关系 | 哪个对象是什么状态；状态怎样变化 |
| 模块边界 | 两个模块各负责什么，在哪里分开 |
| 执行机制 | 代码由谁执行、具体怎样执行 |
| 运行规则 | 程序运行时需要遵守哪些具体规则 |
| 环境配置 | 当前使用哪些环境变量或配置文件 |
| 模型恢复 | 怎样重新想起这个模型 |
| 支撑关系 | A 具体给 B 什么；没有 A 时 B 会怎样 |
| 能力边界 | 这个对象能做什么、不能做什么 |
| 处理链路 | 哪几步按什么顺序发生 |
| 状态管理 | 谁保存状态、什么时候修改状态 |

> **正式术语可以紧密命名；普通解释尽量让关系通过句子表达。**

# 9. P 类：替换以后仍需复核的抽象词

下面这些词不一定是正式计算机术语，但非常容易让技术中文变成说明书。

`机制、体系、能力、维度、形态、承载、支撑、赋予、提供、实现、关联、相应、场景、层面、范式、协同、交互、处理、过程、构建、形成、达成、统一、抽象、链路、闭环、驱动、沉淀、赋能、抓手`

这些词不是禁词。每次出现只检查一件事：

> **它有没有比更普通、更具体的说法多表达信息？**

例如：

不推荐：

> 下层为上层提供运行能力。

推荐：

> 上层程序运行时直接使用下层已经规定好的对象和操作。

不推荐：

> 这一机制实现了资源保护。

推荐：

> 系统限制同时进入的请求数量，避免连接全部被占满。

不推荐：

> 这个结构承载程序状态。

推荐：

> 程序当前的状态保存在这里。

不推荐：

> 两个模块通过该机制进行协同。

推荐：

> A 把结果交给 B，B 收到以后继续处理。

---

# 10. 不要用另一种抽象词替换技术词

以下修改看似 Plain，实际上只是换了一层包装。

| 原句 | 不充分的修改 | 应继续问 |
| --- | --- | --- |
| A 依赖 B | B 支撑 A | 没有 B 时 A 具体不能做什么？ |
| A 调用 B | A 驱动 B | 实际是使用、请求，还是确实发生 Call？ |
| A 映射到 B | A 与 B 建立关联 | 它们具体怎样对应？ |
| A 承载 B | A 为 B 提供载体 | B 是运行在 A 中、保存在 A 中，还是属于 A？ |
| A 提供能力 | A 赋予 B 能力 | B 因此具体能做什么？ |
| A 建立机制 | A 构建处理体系 | 到底增加了哪些规则、对象或步骤？ |
| 从这个维度看 | 从这个视角分析 | 能否写「只看内存时」「只看运行阶段时」？ |
| 在这个场景下 | 在当前应用场景中 | 具体什么条件发生了？ |
| 形成闭环 | 建立完整链路 | 最后一件事到底回到了哪里？ |
| 实现解耦 | 降低耦合 | A 现在具体不需要知道 B 的什么？ |

---

# 11. 同一章节中的局部歧义

有些词普通中文完全可以使用，但当本章正在教授它的正式技术含义时，应尽量减少同一个词同时承担两个意思。

例如 Git 章节正在讲 Commit 时：

> 提交一个想法。

可以根据上下文改成：

> 写下一个想法。

数据库正在讲 View 时：

> 从这个视图来看。

改成：

> 从这个角度看。

网络正在讲 Connection 时：

> 把两个概念连接起来。

可以改成：

> 把两个概念联系起来。

这不是永久禁止普通含义，而是避免**同一小段里一个词不断切换技术义与普通义**。

# 12. 正式术语第一次出现时怎样处理

当一个词真正属于当前主干时，仍按 07A 与 07B：

$$
\text{Plain 解释}
\rightarrow
\text{正式术语}
\rightarrow
\text{必要定义}
\rightarrow
\text{最小例子}
$$

例如：

> 程序打开文件以后，需要保存一个以后还能找到这个文件的整数编号。Linux 把这个编号称为文件描述符（File Descriptor, fd）。

之后正常使用「文件描述符」和 `fd`。

不要因为「描述符」字面不直观，就永远只写「编号」。

同理：

- 指针不能永久改成「地址」；
- 引用不能永久改成「指针」；
- 句柄不能永久改成「凭证」；
- Socket 不能因为中文译名生硬就被隐藏；
- 事务不能只剩「一组操作」；
- View 不能只剩「查询结果」；
- Kubernetes Workload 也不能因为不好懂就把正式名称删掉。

> **普通解释负责进入，正式术语负责以后继续学习、搜索和交流。**

# 13. 编辑时的六步检查

## 13.1 第一步：找到技术意味强的词

扫 A 类词。

问：

> 这里真的在讲这个技术概念吗？

是：保留。

否：继续。

## 13.2 第二步：还原实际事情

不要立即找同义词。

问：

> 谁，在什么时候，对什么做了什么？

尽量先写出这个句子。

## 13.3 第三步：检查名词拼接

寻找连续的普通名词，例如：

`系统能力、语言功能、资源关系、执行机制、状态模型`

问：

> 这是正式术语吗？

如果不是，检查是否可以拆成普通句子。

## 13.4 第四步：检查替换词

扫描 P 类词。

如果删除「接口」以后出现「公开能力」，删除「依赖」以后出现「支撑关系」，删除「映射」以后出现「关联机制」，继续修改。

## 13.5 第五步：检查正式术语有没有被误删

确认：

- 当前真正需要学习的术语仍然存在；
- Plain 解释没有偷换定义；
- 没有把 Pointer、Reference、fd、Transaction 等概念改成近似但不同的词。

## 13.6 第六步：检查读者是否需要猜

最后问：

> 一个还没学这一节的人，看到这句话，会不会突然怀疑某个词是一个尚未解释的新术语？

如果会，而它又不是当前真正要学的内容，就继续修改。

# 14. 几组完整示例

## 14.1 跨层关系

不推荐：

> 上层通过下层提供的接口调用其能力。

较好：

> 上层按照下层已经规定好的方式使用它。

如果能够具体：

> 用户程序通过系统调用请求内核读文件。

优先使用最后一种。

## 14.2 学习关系

不推荐：

> 新知识需要映射回已有认知框架。

推荐：

> 学到新概念以后，要知道它和前面哪些知识对应。

## 14.3 Runtime

不推荐：

> Runtime 承载语言级机制，并向框架提供运行能力。

推荐：

> Runtime 在进程中维护这种语言中的对象和程序当前的执行状态，并负责执行这种语言的代码。框架再直接使用这些对象和运行规则。

如果后文已经能说得更具体，则继续具体化，不必保留「运行规则」这一概括词。

## 14.4 内核

不推荐：

> 内核封装硬件能力，对用户态暴露统一接口。

第一次建立模型时可以写：

> 内核管理 CPU、内存和设备，并把它们组织成进程、文件等程序可以直接使用的对象。

真正进入系统调用以后，再正式写：

> 用户程序通过系统调用进入内核，请求内核完成文件、进程和网络等操作。

## 14.5 Kubernetes

第一次解释 Controller 时，不推荐：

> Kubernetes 通过控制器机制编排工作负载资源。

可以先写：

> 用户声明希望运行多少个 Pod。控制器不断检查实际运行数量；数量不对时，它会创建或删除 Pod，使实际情况逐渐接近用户声明的状态。

随后正式学习 Controller、Workload 等术语。

# 15. 与 07A、07B 的分工

三份规范不重复承担同一职责。

| 文件 | 主要负责 |
| --- | --- |
| **07A** | Markdown、标题、表格、数学、Mermaid、术语锚点、代码字体 |
| **07B** | 句法、普通中文、动词、名词化、说明书腔、阅读阻力 |
| **07C** | 技术词泛化、技术词局部歧义、无意制造伪术语、替代词二次检查 |

例如：

> 通过该接口实现资源能力的统一承载。

07C 先检查「接口」是否真的是技术 Interface；再检查「资源能力」是否属于无意拼出的名词；07B 再处理「实现、统一承载」等抽象表达。

最后可能恢复成：

> 程序通过 `read()` 等系统调用读取文件。具体文件和设备由内核管理。

# 16. 维护方式

这份规范不追求一次收完所有计算机术语。

以后出现以下情况时，可以继续增加词条：

1. 某个词让读者误以为是正式术语，后来发现作者只是借来表达普通意思；
2. 学到某个技术概念以后，发现这个中文词过去经常被泛化使用；
3. 两个普通词反复组合成一个似乎需要定义的新名词；
4. 同一个中文词在多个技术领域拥有不同正式含义，容易在跨层笔记中混淆。

新增时优先记录：

- 常见技术语境；
- 普通叙述中容易怎样误用；
- 改写时先问什么；
- 是否容易和其他领域中的同名词混淆。

不要把词典做成机械替换字典。

# 17. 最终检查表

| 检查项 | 通过标准 |
| --- | --- |
| 正式术语 | 当前真正要学的术语没有被隐藏 |
| 技术词泛化 | 没有借其他领域术语表达普通关系 |
| 名词拼接 | 没有无意制造看似正式的新名词 |
| 替换词 | 没有用「机制、能力、体系、支撑」等抽象词完成机械替换 |
| 对象 | 能看见具体是谁 |
| 动作 | 能看见具体做什么 |
| 条件 | 必要时能看见什么时候发生 |
| 结果 | 必要时能看见动作以后发生什么 |
| 一词多义 | 同一小节里技术义与普通义没有频繁切换 |
| 术语教学 | 第一次出现的重要术语有 Plain 解释和正式名称 |
| 阅读体验 | 读者不用猜某个普通词是不是尚未讲解的新术语 |

最终压成五条：

> **真正学到术语时，正常使用术语。**  
> **没有在讲那个技术概念时，不借术语表达普通意思。**  
> **普通名词不要无意压成一个看起来像新术语的组合。**  
> **删除技术词以后，不用另一批抽象词把意思重新包起来。**  
> **能直接写谁做了什么，就不要再给这层关系起名字。**
