# 行文审校

**状态**：可增长审校手册  
**用途**：在正文完成后逐句检查自然中文、主体、动作、对象、信息顺序、抽象程度和个人表达偏好。普通生成阶段只依赖《中文表达》，无需完整加载本手册。  
**依赖**：《中文表达》  
**来源**：检查项由旧 07B 重组；为避免迁移时丢失细节，原始细则手册完整保留在检查表之后。

# 1. 使用方式

检查项使用 `W` 编号，并按照真实影响分成 A、B、C 三级。新增 Bad Case 时，直接在相应编号区间增加一条；只有多条检查项反复指向同一稳定原则时，才将原则上提到《中文表达》。

| 级别 | 含义 | 处理原则 |
| --- | --- | --- |
| A | 改变事实、定义、断言范围或因果 | 必须修改 |
| B | 明显阻碍理解或形成稳定误解 | 冻结前优先修改 |
| C | 语体、节奏和个人偏好 | 保持全文一致 |

# 2. 检查项

## 2.1 当前问题与中心判断

- **W001 · B**：是否先回答当前真正的问题，而不是先补完整背景？
- **W002 · B**：中心判断是否足够早出现？
- **W003 · B**：多个问题是否先寻找共同前提或共同机制，而不是平均铺开？
- **W004 · B**：用户已经明确掌握的内容是否又被重新教学？
- **W005 · B**：达到足够理解、行动或继续追问的程度后，回答是否已经停止？
- **W006 · C**：结尾是否只是将正文换一套抽象措辞重复一次？

## 2.2 Plain 解释与正式内容

- **W020 · A**：Plain 化是否删掉、偷换或模糊了正式定义、条件和边界？
- **W021 · B**：重要陌生概念第一次出现时，是否先说明它处理什么问题、对象或关系？
- **W022 · B**：是否使用一个尚未解释的新抽象词解释另一个新词？
- **W023 · B**：同一句第一次引入的新正式概念是否过多？
- **W024 · B**：类比是否承担了本应由事实或机制完成的证明？
- **W025 · C**：类比在直接解释已经足够时是否仍然占用篇幅？
- **W026 · B**：一节重要内容是否能找到一句安全、普通、可恢复主干的中心句？

## 2.3 主体、动作与对象

- **W040 · B**：一句话能否直接看见谁在做什么？
- **W041 · B**：「底层」「系统」「内部」「环境」「平台」「机制」是否代替了真正动作主体？
- **W042 · B**：`请求`、`处理`、`提供`、`支持`、`管理`、`完成`、`执行` 等动词是否缺少具体对象或结果？
- **W043 · B**：施事者明确且重要时，是否无必要地改成被动句？
- **W044 · B**：受事者才是当前主题时，是否又机械排斥被动句？
- **W045 · B**：真实动作是否被抽象名词抢走主语位置？
- **W046 · B**：句子是否使用「弱动词 + 抽象名词」，而本可直接使用一个动词？

## 2.4 名词化、抽象词与句法

- **W060 · B**：一件事情或一次变化是否被硬改成「……的……」式抽象名词？
- **W061 · B**：是否存在连续多个「的」，使中心名词出现得过晚？
- **W062 · B**：长前置修饰语是否可以后置或拆句，让对象先出现？
- **W063 · B**：一个句子是否同时承担范围、条件、原因、结果和例外，需要拆开？
- **W064 · B**：读者是否必须读到句尾，再回头寻找主语、动词或条件？
- **W065 · B**：信息顺序是否接近真实动作或理解发生的顺序？
- **W066 · B**：`由于……因此……`、`对于……而言`、`基于……` 等连接结构是否只是制造严谨感？
- **W067 · B**：`机制`、`体系`、`能力`、`维度`、`形态`、`承载`、`场景` 等词是否比更具体的说法多表达了信息？

## 2.5 段落与阅读节奏

- **W080 · B**：多个属于同一推理动作的短句是否被拆成大量短段？
- **W081 · B**：一段是否机械拼接多个独立判断，缺少关系说明？
- **W082 · B**：正文是否先建立正面模型，再处理真正会改变理解的误区？
- **W083 · B**：是否长期依赖「不是、不要、不需要、不能」说明边界，却没有先说明对象怎样工作？
- **W084 · C**：断言范围是否已经在段首或章节开头说明，却仍在每句话重复「通常、可能、某种意义上」？
- **W085 · C**：例子是否进入推理过程，而不是作为正文结束后的装饰？

## 2.6 语体与个人偏好

- **W100 · C**：正文是否正式、平实，而不是聊天腔、论文摘要腔或说明书腔？
- **W101 · C**：在正式回答和文档中，能够自然使用「将」时，是否误用了用户不偏好的「把」字句？
- **W102 · C**：描述方法、工具和操作时，能够自然使用「使用」时，是否无必要地写成用户不偏好的单字「用」？
- **W103 · C**：同义选择是否优先采用稳定、自然的双音节词，而不是为了追求所谓 Plain 一律压缩成单音节词？
- **W104 · C**：上述偏好是否被机械执行，反而产生生硬的「将」字句、重复的「使用」或官样表达？
- **W105 · C**：现成成语、固定搭配和已经自然进入现代汉语的表达是否被无必要地「纯化」？
- **W106 · C**：代词、所有格和复数标记是否只在消除歧义时保留？

## 2.7 最终检查

- **W120 · A**：知识事实、因果、定义和正式术语是否仍然准确？
- **W121 · B**：暂时将所有术语看作普通名词时，句子本身是否仍然自然？
- **W122 · B**：读者是否需要猜普通解释中的某个词其实是尚未定义的新概念？
- **W123 · B**：删除某段后答案仍然完整吗？若完整，这段是否应压缩、后置或删除？
- **W124 · C**：全文的语体、称呼、句式密度和断言强度是否稳定？

# 技术学习笔记 Plain Chinese 行文规范（旧 07B 原文）

本规范与《07A 技术学习笔记 Markdown 排版与结构规范》《07C 计算机技术词使用边界与术语形态规范》配套使用。07A 负责标题、正文、表格、LaTeX、Mermaid、术语锚点和 Markdown 结构；07C 负责技术词泛化、局部歧义和伪术语形态；本规范负责正文中文本身是否自然、清楚、顺畅。

本规范的核心目标是：**在不降低知识精度的前提下，让目标读者先顺着正常中文读懂句子，再理解其中的知识和术语。**

默认假定读者受过一般中高等教育，但不假定已经掌握当前领域。核心术语正常保留；解释术语时，优先使用普通、稳定、不会让读者猜测含义的中文。即使一段话包含大量正规术语，也不能因此降低对句法、主语、动作和信息顺序的要求。

> **该学的难，是知识本身的难；不要再让中文额外增加一层难。**

---

# 1. Plain Chinese 的目标

Plain Chinese 不是把文章写成口语，也不是只准使用少量常用词。它追求的是：读者把注意力放在知识本身，而不是先判断一句话里哪些普通词可能暗藏术语、哪些抽象词需要重新解释、一个长句到底怎样拆。

本规范把写作难度分成三个相互独立的问题：

| 问题 | 关注点 | 本规范的处理 |
| --- | --- | --- |
| 专业难度 | 这个领域本身有多少新知识 | 不回避，必要术语和正式定义保留 |
| 正式程度 | 文章像聊天、教材还是论文 | 默认正式、平实，不写成聊天记录，也不写成论文摘要 |
| 阅读阻力 | 读者是否要先拆句、猜词、还原动作 | 尽量降低 |

因此，专业程度可以很高，语言仍然可以很清楚。Plain 不等于浅薄，正式也不等于生硬。

## 1.1 默认读者的阅读能力

默认假定读者：

- 能理解一般高中和大学通识中文；
- 可以学习新术语，但不应被迫靠上下文猜术语；
- 不假定已经掌握当前领域的前置行话；
- 愿意读正式定义、公式和专业例子，但希望先知道它们在说什么。

正文需要同时满足两件事：

- 没学过这个领域的人，至少能够顺着句子继续往下读；
- 真正需要学习的专业词明确保留，不用白话把正式术语藏掉。

Plain Chinese 处理的是进入理解之前的语言阻力，不负责降低专业内容本身的难度。

## 1.2 Plain 不等于 Simple，也不等于口语

本规范不采用受控词表，不限制只能使用几百个常用词。技术、数学、经济、法律等知识必须逐步获得自己的术语。

同时也不追求聊天腔。例如：

| 写法 | 例句 | 判断 |
| --- | --- | --- |
| 太口语 | 下游吃不下了，上游就慢一点。 | 适合口头辅助理解，不宜作为默认手册语体 |
| 目标语体 | 下游处理不过来时，上游需要减少继续发送的速度或数量。 | 正式、直接、容易理解 |
| 过度学术化 | 当下游处理能力达到容量上限时，应通过反向压力传导机制实现上游生产速率的动态调节。 | 抽象词太多，普通动作被包装成术语式表达 |

默认目标可以概括为：**正式，但说正常中文。**

## 1.3 行文检查的优先级

技术文章很容易出现一种偏差：术语都正确，句子却不像正常中文。尤其在术语密集的段落中，编辑者容易把注意力全部放在概念是否准确、术语有没有误用，却放过主语悬空、动词生硬、对象缺失和信息顺序不自然的问题。

本规范要求按下面的优先级检查正文：

$$
\text{先把句子写顺}
\rightarrow
\text{再确认谁做什么、对什么做}
\rightarrow
\text{再处理名词化和抽象表达}
\rightarrow
\text{再交给 07C 检查术语泛化和伪术语}
\rightarrow
\text{最后确认正式术语仍然准确}
$$

其中「写顺」不是追求文采，而是让一句话符合普通中文的阅读顺序。**术语正确，只能说明知识名词没有错；不能说明这句话已经写好。**

例如：

> 程序开始运行以后，不会把所有功能都直接写成系统调用。大量功能会先通过库函数完成。

术语没有明显错误，但句子不自然。「把功能写成系统调用」容易让人误解成一种编码方式，「通过库函数完成」也没有说明在哪里完成。

更适合写成：

> 程序运行以后，并不是所有操作都需要进入内核。很多工作直接由库函数在用户态完成。

后一句先把真实区别说清：有些工作留在用户态，有些工作需要进入内核。

# 2. Plain 解释与正式定义同时保留

正式定义负责精确，Plain 解释负责让读者先知道「它到底在说什么」。二者不是二选一。

重要概念第一次出现时，优先采用：

$$
\text{问题}
\rightarrow
\text{Plain 解释}
\rightarrow
\text{正式术语}
\rightarrow
\text{必要的正式定义}
\rightarrow
\text{最小例子}
$$

不是每个概念都必须机械走完五步，但不要用正式定义替代第一次解释，也不要用一句白话口号替代正式定义。

## 2.1 先把意思说出来

如果一个概念能够安全地压缩成一句普通中文，先给这句话。

例如，极限的 $\varepsilon-\delta$ 语言可以先理解为：

> **要多近有多近。**

随后再给正式量词定义。Plain 句负责抓住核心，数学定义负责说明「任意近」到底意味着什么。

同态也可以先说：

> 换一种表示以后，原来的运算关系还要成立。

随后再写正式条件：

$$
\varphi(a*b)=\varphi(a)*\varphi(b)
$$

## 2.2 类比排在 Plain 解释之后

类比不是默认工具。类比需要读者熟悉另一个对象，而且总有不完全对应的地方。

优先顺序是：

$$
\boxed{
\text{直接的 Plain 解释}
\rightarrow
\text{正式定义}
\rightarrow
\text{最小例子}
\rightarrow
\text{必要时再类比}
}
$$

如果不用类比已经能直接说明对象、关系、变化和条件，就不额外引入比喻。

# 3. 不让读者猜哪个词是术语

学习材料应该明确区分「需要学习的新词」和「只是拿来解释的普通中文」。

例如：

> 一个事务能看到另一个事务哪些修改，称为可见性（Visibility）。

这里真正的新概念只有「可见性」。读者不需要同时猜「并发语义」「状态关系」「一致性语义」分别是不是新术语。

## 3.1 新概念不要依赖另一个尚未解释的新概念

避免：

> Socket 是一种内核对象。

如果「内核对象」还没有建立，这句话只是把一个问题换成另一个问题。

可以先写：

> Socket 是操作系统提供给程序的网络通信入口。程序通过它建立连接、发送数据和接收数据。

等「内核资源」已经建立以后，再补：

> 在 Linux 中，Socket 也是一种由内核维护的资源，进程通常通过文件描述符访问它。

原则是：**不要用尚未解释的抽象词，去节省一句本来可以直接说清的话。**

## 3.2 同一句第一次引入的新正式概念不要太多

默认一条解释句只引入一个新的正式概念。两个概念必须直接互相定义时可以一起出现，但不要在一句话里连续抛出三四个新词。

例如，不宜写：

> 并发事务之间通过隔离机制形成的状态可见性关系会影响一致性语义。

更适合拆开：

> 多个事务可以同时运行。一个事务能看到另一个事务哪些修改，由隔离规则决定。这里「能看到哪些修改」称为可见性（Visibility）。

## 3.3 正式术语正常保留

Plain Chinese 不负责藏掉术语。`事务`、`Socket`、`MVCC`、`同态`、`理想` 等如果属于当前主干，就应明确出现并完成术语锚定。

真正要减少的是：为了显得专业而额外生成的半术语表达。

## 3.4 术语密集的段落仍然先按正常中文组织

一段话中即使同时出现 `libc`、系统调用、`fd`、虚拟内存、线程、Page Fault 等正式术语，也不能因此把普通中文写成技术说明书式的连接句。

例如：

> `printf()` 会先做格式化和缓冲，真正输出字节时底层才可能进入 I/O 系统调用。

问题不在「I/O 系统调用」是不是术语，而在「底层才可能进入」没有明确主体。「底层」只是位置词，不知道究竟是谁执行了什么。

可以改成：

> `printf()` 会先在用户态完成格式化和缓冲。真正需要把字节写到 `fd` 对应的对象时，才可能通过系统调用进入内核。

又如：

> `malloc()` 只有需要更多底层内存时才请求操作系统。

「请求操作系统」缺少请求内容，也没有说明「底层内存」具体指什么。更适合写成：

> `malloc()` 会先管理已经取得的堆空间。现有空间不够时，才可能通过系统调用向内核申请更多虚拟内存。

原则是：

> **正式术语可以密集，普通中文不能因此变得含糊。**

# 4. 普通意思优先使用普通词

普通词已经准确时，不主动升级成更抽象、更书面的表达。

例如：

| 直接写法 | 不必要的升级 |
| --- | --- |
| 不同 | 差异性 |
| 变了 | 发生变更 |
| 分开 | 进行区隔 |
| 为什么 | 成因机制 |
| 怎样发生 | 作用过程 |
| 很容易找到 | 信息获取成本较低 |
| 读起来费劲 | 认知负担较高 |
| 不容易懂 | 存在理解障碍 |

右侧词语并非禁用。如果它们在当前领域具有明确、稳定、需要保留的含义，可以正常使用。问题只在于：**它有没有比左侧普通说法多表达信息。**

## 4.1 优先使用普通而明确的动词

`看、找、等、改、放、拿、给、变、保留、丢失、重复、同时、先、后` 等普通词，不因为太白话就自动替换。

例如：

> 一个事务什么时候能看到另一个事务的修改？

比：

> 并发事务之间的数据可见性关系如何形成？

更适合第一次解释。

又如：

> Python 到哪里找模块？

可以比：

> Python 如何完成模块检索？

更自然。只有当「检索」本身是需要讨论的正式机制时，才有必要升级。

## 4.2 触发复核的宽泛词

下列词（以及类似的词）不是禁词，但出现时应检查一次它是否真的增加信息：

`机制`、`体系`、`能力`、`形态`、`范式`、`维度`、`承载`、`相关`、`相应`、`场景`、`实现`、`进行`、`提供`、`存在`、`作出`、`产生`。

例如：

> 通过该机制实现对有限资源的保护能力。

通常可以直接写：

> 系统限制同时使用资源的请求数量，避免资源被占满。

如果「机制」是本章正式讨论对象，当然可以保留；如果只是占位词，就换成真正的对象和动作。

---

# 5. 让真正做事的东西尽早出现

一句话优先回答：**谁在做什么？**

不要让抽象名词先占据主语位置，再用空泛动词把真正动作藏起来。

例如：

> 连接资源的耗尽会导致后续请求进入等待状态。

更适合写成：

> 没有空闲连接以后，新的请求只能等待。

前一句并非看不懂，但「连接资源」「耗尽」「进入等待状态」都会让读者怀疑它们是否另有严格定义。后一句直接说明发生了什么。

## 5.1 优先主动句，但不机械排斥被动句

如果知道谁在做事，通常让它直接做主语：

> 调度器选择下一条要运行的线程。

比：

> 下一条待运行线程由调度器进行选择。

更直接。

但被动句在「施事者未知、不重要，或受事者才是当前主题」时完全可以使用。本规范不做机械语法禁令。

## 5.2 动词必须尽量有明确的发出者

技术文章里常见「底层进入」「系统完成」「内部处理」「机制负责」之类表达。它们有时可以成立，但也很容易让位置、范围或抽象名词代替真正的动作主体。

看到下面这些句式时，应继续追问：

- 谁进入？
- 谁读取？
- 谁保存？
- 谁发送？
- 谁申请？
- 谁修改？
- 谁等待？
- 谁决定？

例如：

> 真正输出字节时，底层才可能进入 I/O 系统调用。

应继续问「谁进入」。如果实际是库代码最终发起系统调用，就直接写出来。

又如：

> 规则不满足时，系统重新决策。

如果这里真正做决定的是内核，可以写：

> 当前访问无法继续时，CPU 进入内核，由内核决定怎样处理。

不要为了简洁，让「底层」「系统」「内部」「环境」「平台」自动充当万能主语。

## 5.3 动作对象也要说完整

只有主语和动词还不够。很多技术句子的问题在于动作没有对象，读者知道「请求了」「处理了」「提供了」，却不知道具体请求什么、处理什么、提供什么。

例如：

> 只有需要更多内存时才请求操作系统。

应继续写清：

> 现有空间不够时，才可能向内核申请更多虚拟内存。

又如：

> 发生异常后交给系统处理。

应根据实际情况写：

> CPU 进入内核以后，内核检查这次异常的原因，再决定恢复执行、终止进程或采取其他处理。

常见需要复核的悬空动词包括：

`请求`、`处理`、`管理`、`提供`、`支持`、`完成`、`执行`、`建立`、`更新`、`恢复`、`返回`、`交给`。

检查标准是：

> **读者能不能从句子里直接看出「谁对什么做了什么」？**

## 5.4 不要把技术词当成句法骨架

术语负责命名对象和动作，不负责替代中文句子的骨架。

例如：

> 程序开始运行以后，不会把所有功能都直接写成系统调用。大量功能会先通过库函数完成。

问题不在「系统调用」「库函数」这些术语，而在两个动作之间没有用自然中文说明关系。

更适合写成：

> 程序运行以后，并不是所有操作都需要进入内核。很多工作直接由库函数在用户态完成。

先把普通句子写顺，再把术语放进去。不要因为段落里已经出现很多技术名词，就默认它已经具有技术文章应有的清晰度。

---

# 6. 动作能直接用动词，就不要拆成「弱动词 + 抽象名词」

看到「进行 / 实现 / 作出 / 完成 / 提供 + 名词」时，先检查是否可以恢复成一个直接动词。

| 冗长写法 | 优先检查的直接写法 |
| --- | --- |
| 进行分析 | 分析 |
| 进行修改 | 修改 |
| 作出判断 | 判断 |
| 进行讨论 | 讨论 |
| 实现保护 | 保护 / 限制 / 隔离，按实际动作选择 |
| 提供支持 | 支持，或直接写支持的具体动作 |

不是见到这些词就删除。例如「完成迁移」中的「完成」可以真正表示迁移已经结束；软件工程里的「实现接口」也有正式含义。

判断方法只有一个：**删掉这个辅助动词，会不会丢失信息？**

---

# 7. 少把动作和事情硬改成抽象名词

中文可以直接用一件事进入句子，不必先把动作名词化。

例如：

> 他因为收入减少而改变生活方式。

通常比：

> 他的收入的减少改变了他的生活方式。

更自然。

技术写作中也一样。

不要优先写：

> 对数据一致性的保证依赖于事务隔离机制的正确使用。

可以先问真正发生什么：

> 多个事务同时读写时，需要用隔离级别限制它们彼此能看到哪些修改，避免结果出错。

如果后文确实需要把「一致性」提升为正式概念，再明确给它命名。

## 7.1 流程名和术语名尽量放在具体动作之后

有些词本身是正规技术用语，但第一次出现时如果直接拿来概括一整段过程，仍然会增加理解难度。优先先把事情说清，再告诉读者这件事通常叫什么。

例如，操作系统里常说「回收子进程」。第一次解释时，不宜只写：

> 在通常的父进程回收流程中……

更适合先写：

> 子进程退出以后，内核会暂时保留它的 PID、退出状态等少量信息。父进程调用 `wait()` 或 `waitpid()` 取得这些信息以后，内核就可以清理剩余记录。这个过程通常称为**回收子进程**。

这里「回收」可以作为技术语境中稳定的用法保留，但不必进一步制造「父进程回收流程」「生命周期回收机制」之类名词组合。

原则仍然是：

> **先说发生了什么，再给这件事命名。**

---

# 8. 一个句子尽量只承担一个主要关系

「句子短」不是字数少，而是不要让读者同时维护太多从属关系。

如果一句话同时塞入范围、条件、原因、结果和补充说明，优先拆开。

例如：

> 当多个事务在高并发情况下同时对共享数据进行修改时，由于不同事务之间存在数据可见性的差异，因此可能导致最终业务状态发生不一致。

可以拆成：

> 多个事务可能同时修改同一份数据。不同事务在同一时刻看到的数据不一定相同，最终结果可能因此出错。

需要术语时再补：

> 一个事务能看到另一个事务哪些修改，称为事务之间的可见性（Visibility）。

## 8.1 不设机械字数上限

中文可以有长句。只要主干清楚、关系顺着读者的理解次序展开，长句并非问题。

真正需要拆的是：读者必须读到句尾以后，再回头重新寻找主语、动词和条件的句子。

## 8.2 信息按动作发生顺序展开

技术文章经常为了「概括」而先写一个抽象结论，再补谁做了什么。第一次解释时，通常更适合按照实际动作顺序写。

例如：

> 大量功能会先通过库函数完成。

可以展开成：

> 程序先执行库函数。能在用户态完成的工作就在这里完成；真正需要文件、网络或其他内核操作时，再发起系统调用。

又如：

> 父进程也可以提前调用等待函数，在那里等子进程结束。

这里「在那里」没有必要。更自然的是：

> 父进程也可以先调用 `wait()`，如果子进程还没有退出，就在那里等待；子进程退出后再取得结果。

如果一句话里的先后关系本来就很重要，优先让句序本身反映这个顺序。

---

# 9. 长修饰语尽量后置

中文容易把修饰语全部压在名词前面。修饰一长，读者必须先记住一串条件，等最后才知道它们在修饰什么。

例如：

> 一个能够在下游服务恢复后自动由打开状态转换回半开状态并允许少量探测请求进入的熔断器……

更适合写：

> 熔断器打开以后，会暂时拒绝请求。过一段时间，它可以进入半开状态，先放少量请求过去，检查下游是否恢复。

原则是：**先把对象放到桌上，再逐项说明它。**

看到 `[很长的一串内容] 的 [名词]` 时，优先检查能否拆句或后置。

---

# 10. 不要把逻辑关系全部写在连接词里

中文经常可以通过句序直接表达先后和因果。不要机械添加：

`由于……因此……`、`基于上述原因……`、`在……的情况下……`、`对于……而言……`、`从……的角度来看……`。

例如：

> 队列越来越长，说明生产速度已经超过消费速度。继续这样下去，等待时间和内存占用都会上升。

通常比：

> 由于生产者的生产速率高于消费者的消费速率，因此会导致队列长度出现持续增长的情况，并进一步造成……

更清楚。

连接词不是禁用。关系容易误读、转折明显、条件需要精确限定时，应正常使用。

---

# 11. 模型范围说一次，正文直接说

准确不等于每句话都加「一般来说」「通常情况下」「某种意义上」「可能」「也许」。

先把当前范围说明清楚：

> 这一节只看进程的用户态虚拟地址空间。

随后可以直接写：

> 里面有几类常见区域，例如代码、静态数据、堆和栈。

不需要每句话重新提醒世界还有例外。

断言应采用当前范围内的最强安全说法：既不说得过强，也不堆免责声明。

---

# 12. 正面模型优先，纠偏只在必要时出现

先说「它是什么、怎样工作、为什么需要」，再处理真正会影响理解的误区。

不要让正文长期依赖：

> 不是……而是……

> 严格来说……

> 实际上还……

> 这里千万不要理解成……

如果一个错误理解确实高频，而且会改变当前操作、预测或设计，可以简短纠偏一次。之后回到正面模型。

---

# 13. 每一节都应能找到一句普通中文的中心句

写完一个重要概念以后，问：

> **如果暂时不能使用这个正式名称，我能不能用一句普通中文说出它到底在处理什么？**

例如：

| 概念 | Plain 中心句 |
| --- | --- |
| 极限 | 要多近有多近。 |
| 幂等 | 同一件事再来一次，也不会多做一遍。 |
| 缓存 | 已经取得过的结果先留一份，下次不必重新取。 |
| 背压 | 下游处理不过来时，上游要减少继续发送的速度或数量。 |
| 同态 | 换一种表示以后，原来的运算关系还要成立。 |

这些中心句不是正式定义。它们负责把一节知识折叠成可以重新提取的主干。

如果怎么都压不出一句安全的普通话，不强求金句。宁可多解释，也不要为了简短制造错误口号。

---

# 14. 段落按读者理解顺序推进

一段正文通常优先遵循：

$$
\text{当前问题}
\rightarrow
\text{直接回答}
\rightarrow
\text{必要术语}
\rightarrow
\text{关系或原因}
\rightarrow
\text{例子 / 边界}
$$

不要一上来先交代所有限定、历史、例外和术语，再把真正答案放到段尾。

例如介绍事务隔离，可以先写：

> 多个事务同时运行时，需要规定它们彼此什么时候能看到对方的修改。这组规则叫隔离级别（Isolation Level）。不同隔离级别允许看到的数据不同，因此能避免的问题也不同。

然后再进入各级别的正式区别。

---

# 15. 数学、科学与其他正式领域

数学、逻辑、法律、经济学等领域不能为了 Plain 而删掉正式定义、条件和限定。

默认保留两层：

1. **Plain 层**：告诉读者这个定义在抓什么；
2. **Formal 层**：用定义、公式、定理条件或规范语言把边界钉牢。

例如：

> 连续可以先理解为：输入只要足够近，输出就能保证足够近。

然后再给正式定义。

一致连续可以先说：

> 同一个「足够近」的标准，到处都管用。

再说明其中的量词顺序。

Plain 层不能替代 Formal 层；Formal 层也不能被当成第一次解释。

---

# 16. 普通解释不依赖读者猜测

这是本规范的硬检查之一：

> **除正式术语外，解释正文原则上不应要求目标读者靠猜来理解词义。**

例如：

> 并发事务可能导致数据一致性问题。

读者也许能猜个大概，但学习材料没有必要让他猜。

可以先写：

> 两个事务同时修改同一份数据时，一个事务的结果可能覆盖另一个；它们也可能读到不同阶段的数据。

然后再把这些问题归到正式概念下。

这并不意味着每个普通词都要解释。`空闲`、`等待`、`看到`、`修改` 等在当前语境中没有特殊含义时，就让它们保持普通词的身份。

---

# 17. 编辑时的六轮检查

Plain Chinese 不适合靠自动同义词替换完成。尤其不要先扫术语词表，再把剩下的句子默认视为合格。推荐按下面顺序检查：

## 17.1 第一轮：知识检查

先确认模型、事实、因果、范围和正式术语没有问题。不要在事实尚未稳定时先追求文句。

## 17.2 第二轮：自然中文检查

先暂时不管术语是否漂亮，只读整句话：

- 这像不像正常中文？
- 主干是不是一遍就能读出来？
- 信息顺序是否自然？
- 有没有读到句尾还要回头找主语和动词？
- 如果把正式术语暂时当作普通名词占位，这句话本身还顺不顺？

这一轮优先级高于术语美化。**术语正确但句子不顺，仍然必须重写。**

## 17.3 第三轮：主体、动作与对象检查

逐句问：

- 谁在做什么？
- 对什么做？
- 请求谁做什么？
- 什么东西发生了变化？
- 谁保存、读取、修改、等待或决定？
- 「底层」「系统」「内部」「环境」是不是代替了真正主体？
- `请求 / 处理 / 提供 / 支持 / 完成 / 管理` 后面有没有把动作对象说完整？

如果这些问题答不出来，先补全事实关系，不要立即换词。

## 17.4 第四轮：Plain 与名词化检查

再检查：

- 真正动作是不是被抽象名词藏起来了？
- 有没有「弱动词 + 抽象名词」？
- 有没有很长的前置修饰语？
- 一个句子是不是承担了太多关系？
- 有没有可以直接使用的普通动词？
- 有没有宽泛词只是为了让句子显得更技术化？

## 17.5 第五轮：07C 术语检查

中文已经写顺以后，再按 07C 检查：

- 技术词是否被借来表达普通意思；
- 多个普通名词是否无意拼成伪术语；
- 同一段中技术义和普通义是否互相干扰；
- 删除一个技术词以后，是否又换成了另一批抽象词。

07C 不替代前面的中文检查。即使一个词完全符合技术定义，句子仍然可能因为主语、动作或顺序不自然而需要重写。

## 17.6 第六轮：正式性与术语保真

最后确认：

- Plain 化以后没有写成聊天腔；
- 正式术语没有被白话替代掉；
- 定义、条件和范围仍然准确；
- 真正需要学习的术语仍然明确出现。

推荐顺序可以压成：

$$
\text{知识正确}
\rightarrow
\text{中文先顺}
\rightarrow
\text{动作完整}
\rightarrow
\text{去掉抽象包装}
\rightarrow
\text{07C 查术语}
\rightarrow
\text{Formal 保真}
$$

---

# 18. 触发复核，不机械禁词

下列结构出现时值得检查，但不自动判错：

- 「进行 + 名词」；
- 「实现 + 抽象名词」；
- 「提供……能力」；
- 「存在……问题」；
- 「作出……判断 / 反应 / 决策」；
- 「对于……而言」；
- 「基于……」；
- 「由于……因此……」；
- 连续多个「的」；
- 很长的 `[修饰语] 的 [名词]`；
- 一句话连续出现多个首次术语；
- 「底层 / 上层 / 内部 / 系统 / 环境 / 平台」直接充当含糊动作主体；
- 「请求 / 处理 / 提供 / 支持 / 管理 / 完成」没有明确动作对象；
- 术语全部正确，但整句话仍需要读者自己补全谁做什么；
- `机制 / 体系 / 能力 / 形态 / 范式 / 维度 / 承载 / 相关 / 相应 / 场景` 等宽泛词。

复核问题不是「这个词能不能用」，而是：

> **它是否比更普通的说法多表达了真实信息？**

如果没有，优先使用更直接的中文。

---

# 19. 最终行文检查表

完成一段知识型正文后，可以快速检查：

| 检查项 | 通过标准 |
| --- | --- |
| 读者前提 | 没有偷偷假设读者已经掌握尚未讲过的领域词 |
| Plain 核心 | 重要概念能先用普通中文说明在处理什么 |
| 正式定义 | 需要精度的地方仍保留术语、公式、条件或定义 |
| 术语密度 | 新词逐个进入，不让读者一次猜一串 |
| 主语 | 能看见谁在做事，不让「底层」「系统」「机制」长期充当万能主体 |
| 动词 | 真正动作没有被大量名词化和弱动词掩盖 |
| 动作对象 | 请求、处理、提供、管理等动作说明了具体对象和结果 |
| 句法 | 即使术语很多，整句话仍符合自然中文的阅读顺序 |
| 信息顺序 | 先说谁做什么，再补原因、条件、术语和边界 |
| 逻辑 | 不靠堆连接词制造「严谨感」 |
| 07C | 中文写顺以后，再检查术语泛化、伪术语和局部歧义 |
| 语体 | 正式、平实，不聊天，也不论文腔 |
| 范围 | 断言在当前问题域内足够强，但不过界 |
| 复习 | 一节结束后能找到一句可以重新提取主干的话 |

最后压成六条：

> **先把句子写成正常中文，再检查它像不像技术文章。**  
> **先说事情，再给事情命名。**  
> **谁做什么、对什么做，尽量直接写出来。**  
> **专业术语可以专业，解释它的中文不必跟着专业化。**  
> **中文已经写顺以后，再用 07C 检查技术词泛化和伪术语。**  
> **Plain 负责进入理解，Formal 负责站稳。**
