# 工程专题

**状态：重组试行版**  
**用途**：用于缓存、数据与持久化、异步任务等模块 / 问题域，以及可观测性、稳定性、安全、质量评估、成本治理等横切能力。  
**依赖**：《技术文档》  
**被依赖**：工程专题笔记、工程知识地图和项目方案  
**替代**：旧《工程模块专题设计规范》和旧《工程横切能力知识设计规范》中的稳定知识设计规则。  
**适用边界**：本扩展负责一个工程问题域怎样组织机制、方法和工具。单个框架、库、服务或协议使用《技术对象》；单一可复用做法使用《工程方法》；当前项目的技术选型、参数和落地步骤使用项目方案。

# 1. 工程专题有两种主要形态

| 形态 | 观察角度 | 例子 |
| --- | --- | --- |
| 模块 / 问题域型 | 围绕一类相对集中的系统职责组织知识 | 缓存、数据与持久化、异步任务、认证授权、前端状态管理 |
| 横切能力型 | 观察同一种工程能力怎样贯穿多个模块和生命周期 | 可观测性、稳定性治理、安全、质量评估、负载与扩展、成本治理 |

二者共享问题域、机制、工具、边界和停止线等基础结构。差异稳定出现时在同一规范内使用两个分支模板，不立即拆成两套大规范。

# 2. 判断专题边界

专题的主语应该是工程问题，而不是工具名。Redis 是缓存专题中的一种工具，OpenTelemetry 是可观测性专题中的一种实现入口。

一个专题至少应满足：

- 能说出它反复解决的真实问题；
- 内部包含两个以上彼此相关的机制、方法或实现角色；
- 有清楚的边界，能够说明哪些问题属于相邻专题；
- 形成独立学习价值，而不是当前项目目录的机械镜像。

如果内容只围绕一个对象内部的抽象和 API，写对象文档；如果只围绕一种做法的前提和步骤，写方法文档。

# 3. 共用结构

工程专题通常从以下内容中选择需要的部分：

```text
定位与边界
存在动机
核心机制
典型过程或系统位置
主要形态 / 观察维度
方法与工具层
最小实践或观察方案
反复出现的工程问题
边界、取舍与相邻专题
当前完成标准
附录：术语、场景和参考入口
```

专题不必固定成十一章。主要形态、场景卡片和最小实践都按内容需要出现；没有内容的章节直接省去。

# 4. 模块 / 问题域型专题

模块型专题围绕一类相对集中的职责建立纵向理解。例如缓存专题可以从重复计算和访问距离进入，解释命中、失效、TTL、一致性、击穿等机制，再连接本地缓存、Redis 和 CDN。

模块型专题优先回答：

1. 这个问题域在系统中处于什么位置？
2. 没有这一层时，系统会遇到什么麻烦？
3. 哪些核心机制共同解决问题？
4. 一次典型过程怎样穿过这些机制？
5. 是否存在本质不同的实现形态？
6. 哪些方法和工具实现各部分能力？
7. 常见失败怎样从表象下探到机制？
8. 它与相邻问题域怎样划界？

## 4.1 主要形态只在真实分型时出现

当专题内部存在本质不同的实现方向时，使用同维度比较：

| 形态 | 解决什么 | 优点 | 代价 | 适合场景 |
| --- | --- | --- | --- | --- |

本地缓存、分布式缓存和边缘缓存属于不同位置与边界；关系型与非关系型存储属于不同数据模型和取舍。Logs、Metrics、Traces 更常是互补观察方式，不宜强写成互斥形态。

## 4.2 工具层服从机制

工具表只回答实际工程中常用什么以及它承担哪部分：

| 工具 | 技术形态 | 在专题中的角色 | 当前学习深度 |
| --- | --- | --- | --- |

工具内部的 API、配置和生命周期进入对应对象文档。

# 5. 横切能力型专题

横切能力不是一个单独模块，而是在多个模块中反复出现的工程要求。它优先回答：

1. 这项能力为什么必须跨越多个模块？
2. 它由哪些互补的观察维度、方法或控制点组成？
3. 信息、标识、策略或证据怎样沿调用链传播？
4. 各模块在哪些位置承担责任？
5. 哪些工具分别覆盖采集、传输、存储、分析或执行？
6. 最小可用方案是什么，怎样逐步提高成熟度？
7. 它与项目方案之间怎样分工？

## 5.1 模块落点矩阵

横切能力需要显示「同一能力在不同模块怎样落地」。模块较多且维度稳定时，使用矩阵：

| 模块 | 需要产生或接收什么 | 关键标识或状态 | 验证方式 |
| --- | --- | --- | --- |
| API 层 | 请求事件与响应结果 | request_id | 按一次请求检索完整记录 |
| 异步任务 | 入队、执行、失败与完成事件 | task_id | 从提交追到最终状态 |
| 数据层 | 查询耗时、事务结果 | trace_id / transaction id | 关联慢请求与具体查询 |

矩阵只有在确实存在跨模块映射时使用。两个落点用自然段更清楚时，不额外造表。

## 5.2 方法、工具与项目方案分层

```text
横切能力
→ 可复用方法
→ 工具实现
→ 当前项目方案
```

例如可观测性专题连接结构化日志、指标和追踪方法；方法文档解释各自机制；工具文档解释 OpenTelemetry、Prometheus 等对象；项目方案记录当前采集哪些字段、保留多久、怎样告警。

# 6. 核心机制从「为什么能解决」展开

机制不是功能清单。推荐使用：

```markdown
## 机制名

**问题**：没有它时会发生什么。

**机制**：它怎样改变信息、状态、时序或资源流动。

**例子**：用一个具体过程展示机制。

**边界**：它依赖什么，不能解决什么。
```

例如「缓存支持字符串、哈希、列表」描述的是工具能力；「将可复用结果保存到更近、更快的位置，命中后跳过原始计算」才解释缓存为何加速。

# 7. 典型过程连接各个局部机制

专题容易被写成一组并列概念。典型过程用于将机制串回同一个系统行为。

模块型专题可以选一次请求、一次任务或一次状态变化；横切能力可以选一个事件、请求标识、权限决策或评估样本怎样贯穿多个模块。

主路径先建立整体模型，再展开异常、并发、恢复和规模化问题。图只在分支、多主体、状态或拓扑关系明显时使用。

# 8. 工程母题用于归纳反复问题

同一种问题在项目、面试和学习中反复出现时，可以提炼为工程母题。母题包含：

- 典型症状；
- 从表象到机制的下探路径；
- 可选择的应对策略；
- 验证结果的方法；
- 适用边界。

例如：

```text
接口变慢
→ 数据库查询变慢
→ 查询形状与索引不匹配
→ 执行计划扫描范围过大
→ 调整查询或索引并重新验证
```

母题只在能够覆盖多个真实场景时进入主文。一次性问题留在场景记录或项目文档。

# 9. 场景卡片记录真实触发

面试题、项目故障或学习中暴露的盲区，可以作为场景卡片附在相应母题之后：

```markdown
## 具体问题

**归属母题**：……

**问题本质**：……

**核心策略**：……

**验证方式**：……

**简短回答**：……
```

场景卡片记录真实触发，不提前穷举题库。卡片数量增多并形成独立检索需求时，迁入单独案例库，专题主文只保留入口和代表性案例。

# 10. 最小实践与最小观察方案

模块型专题适合用最小 demo 证明闭环；横切能力有时更适合最小观察方案。

| 专题 | 合适的最小验证 |
| --- | --- |
| 缓存 | 制造命中、未命中和过期，观察原始查询次数 |
| 异步任务 | 提交任务，观察排队、执行、失败和结果状态 |
| 可观测性 | 用同一 request_id 串联 API、任务和数据库事件 |
| 稳定性 | 制造超时或过载，观察限流、重试或降级行为 |
| 质量评估 | 固定样本和版本，比较变更前后指标与坏例 |

实践只覆盖当前学习目标。项目级部署、权限、成本和长期运维另写项目方案。

# 11. 完成标准按能力层次表达

专题可以采用三层停止线，但层级名称可以随用途调整：

| 层次 | 可观察能力 |
| --- | --- |
| 会定位和使用 | 能识别问题属于本专题，并跑通一个最小闭环 |
| 会解释和排查 | 能说明核心机制，从症状下探到方法和验证 |
| 会设计和取舍 | 能比较主要形态，组合方法和工具，说明边界与代价 |

暂缓内容明确保留入口，例如集群、高可用、跨区域复制或大规模成本治理，而不提前展开成百科。

# 12. 专题、总纲和项目方案分工

总纲负责展示多个专题在完整工程体系中的位置；专题负责本问题域的稳定知识；项目方案负责当前选择。

```text
工程知识地图
├─ 数据与持久化专题
├─ 缓存专题
├─ 异步任务专题
└─ 可观测性专题

项目方案
└─ 根据当前流量、预算和团队能力选择其中一部分落地
```

当前技术栈优先级、求职阶段、特定项目模块和短期任务进入学习地图或项目计划，不写入长期专题规范。

# 13. 拆分原则

以下内容通常留在同一专题：

- 共享同一问题域和典型过程的核心机制；
- 为理解边界所需的少量工具定位；
- 能帮助形成整体模型的代表性场景。

以下内容适合拆出：

- 单个工具内部的抽象、API 和配置；
- 能跨多个专题复用的完整方法；
- 高频增长的场景库、术语表和命令参考；
- 会随项目变化的选型、参数和部署方案。

拆分后保留明确入口，不在父子文档中维护同一段正文。

# 14. 最终检查

1. 专题主语是否是工程问题域或横切能力，而不是工具名？
2. 模块型与横切型是否已经判断，结构是否体现差异？
3. 定位、动机、核心机制、典型过程和边界是否清楚？
4. 主要形态是否确属不同实现方向，互补能力是否被误写成替代关系？
5. 工具是否服务于机制，对象细节是否回到对象文档？
6. 横切能力是否显示关键落点和传播关系？
7. 工程母题是否来自多个真实场景，场景卡片是否来自真实触发？
8. 最小实践或观察方案是否能证明专题中的关键机制？
9. 完成标准是否可观察，并明确当前暂缓内容？
10. 稳定专题知识、项目方案和学习路线是否分开维护？
