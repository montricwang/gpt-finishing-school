# 工程文档风格

**状态：试行**  
**用途**：统一工程学习文档的阅读入口、总图—局部图节奏、章节推进方式与收尾体验。  
**依赖**：《中文表达》《文档排版》《技术文档》  
**按知识类型配合**：《技术对象》《工程方法》《工程专题》  
**本规范不负责**：技术深度、课堂证据判定、API 清单完整性、Markdown 细枝末节审校。这些分别由 AI-3、《技术文档》和《文档排版》承担。

## 1. 这份规范只回答一个问题

> 同一套工程学习文档，应该怎样组织，才能让读者先看到整体，再沿真实问题逐步打开局部。

因此，本规范只处理三件事：

1. 章首入口怎样统一；
2. 总图、局部图、代码、表格和正文怎样协作；
3. 一章接一章时，怎样保持连续阅读的节奏。

## 1.1 标题与正文遵循上位规范

正式知识手册的标题句式由《文档排版》第 4 节统一规定：**默认使用名词短语或主题短语**，将完整判断、因果和解释放在正文中。正文的正面立论与例外说明由《中文表达》第 3 节规定：**先写成立的事实与关系，再按需集中辨析误解**。本规范只决定标题在整篇手册中的组织方式，不另维护一套标题、句法或反面措辞细则。

## 2. 统一阅读入口

较长正式手册默认采用以下入口：

1. **定位**：前文已建立什么，本文解决什么，当前打开到哪里；
2. **章首总图**：给出全文地图；
3. **读图**：说明怎样阅读总图，以及它没有表达什么；
4. **主线导言**：用一句主链或一小段导言压缩全文范围；
5. **正文**：从主链起点进入。

并非每篇都必须硬写成同样模板；但读者在开头应能迅速知道自己站在哪里、接下来要走哪条路。

## 3. 总图只承担地图职责

章首总图的职责，是帮助读者看到全文主要对象与主关系，而不是充当完整参考手册。

总图优先保留：

- 后文反复出现的核心对象；
- 决定正文顺序的主链；
- 必要的旁支机制、控制点或风险点。

不进入总图的内容：

- 低频参数；
- 大量例外；
- 完整 API 清单；
- 只在局部使用一次的细节。

图后必须说明：

- 从哪里开始读；
- 实线、虚线、分组或颜色各表示什么；
- 这张图不表示什么。

## 4. 局部图、表格、代码和正文怎样协作

### 4.1 连续阅读不等于连续自然段

自然的阅读节奏，可以是：

- 一句定义；
- 一张表区分对象；
- 一张图说明关系；
- 一段短代码说明实际写法；
- 一小段正文解释边界。

因此，连续阅读体验不是把所有内容都挤进自然段，而是让每种结构出现在最合适的位置。

### 4.2 组合表达的典型模式

| 需要表达的内容 | 更适合的组合 |
| --- | --- |
| 一组角色如何分工 | 定义 / 导言 + 对照表 + 必要说明 |
| 一次主路径如何运行 | 总图或局部流程图 + 简短读图 |
| 多主体怎样按时间交接 | 时序图 + 一段解释 |
| 某个 API 或框架点怎样写 | 最小代码 + 必要输出 + 一段解释 |
| 某类错误如何判断 | 分支图或诊断表 + 一段排障提示 |
| 生命周期与作用域 | 局部图 + 对照表 |

### 4.3 正文负责什么

正文主要承担以下工作：

- 建立概念；
- 解释为什么需要下一个对象或机制；
- 说明图表没有直接表达的边界、前提和取舍；
- 在章节之间做自然过渡。

不要在图表之后再逐项把图中的每条箭头翻译一遍，除非需要补充图中没有表达的判断。

## 5. 章节推进节奏

### 5.1 从前一问题自然进入下一问题

重要章节开始时，优先说明：前一步解决了什么，还留下什么，因此为什么现在需要引入下一机制或下一对象。

### 5.2 第一解释只服务当前主线

一个概念可能有很多背景。第一次出现时，只解释足以支撑当前主线的那一层；更深实现、历史和变体留到后文或相邻专题。

### 5.3 先建立运行模型，再挂接命令、API 和配置

尤其对运行型技术对象，读者应先知道：

- 当前在发生什么；
- 哪些对象在参与；
- 这条命令或这段代码改变了哪里；
- 为什么这个入口有用。

## 6. 局部图使用原则

### 6.1 哪些内容值得单独开图

优先给以下内容单独开局部图：

- 多主体交接；
- 重要的状态迁移；
- 生命周期与作用域；
- 排障链路；
- 容易在文字中混淆的对象关系。

### 6.2 不必为了完整性而画的图

以下情况通常不必硬画图：

- 一句定义已经足够清楚；
- 简单并列关系用表格更直观；
- 简单步骤用短列表即可；
- 图只会重复正文而不新增信息。

### 6.3 总图与局部图的关系

总图负责地图；局部图负责难以仅靠文字看清的局部结构。两者合起来覆盖正文的承重关系，而不是要求总图独自承担所有细节。

## 7. 统一收尾

正式手册结尾通常给出：

- 当前已经建立的完整模型；
- 本文停止在哪里；
- 哪些相邻问题留给后续专题；
- 必要时附上问题索引或速查附录入口。

结尾的目标不是重复全文目录，而是帮助读者判断：现在已经能解释什么、操作什么、还不用展开什么。

## 8. 使用路由

### 8.1 正式起草之前必须加载

- 《中文表达》：正面立论、主体与动作；
- 《文档排版》：章节标题、层级、段落、表格与附录；
- 《技术文档》：定义、图表、代码与自然段的表达选择；
- 本规范《工程文档风格》：章首入口、图文组合与全篇节奏
- AI-3（如果当前任务是课堂草稿整编）

### 8.2 冻结前按需追加

- 《排版审校》
- 《术语审校》
- 《行文审校》

这意味着：**《工程文档风格》是章首入口、图文节奏和阅读体验的主规范，不是全部 Markdown 细节的总手册。**
