# 工程方法

**状态：重组试行版**  
**用途**：用于幂等设计、重试与退避、Worker 模式、结构化日志、接口测试、RAG 评估等可跨工具和项目复用的工程方法。  
**依赖**：《技术文档》  
**被依赖**：工程方法笔记、工程专题和项目方案  
**替代**：旧《工程工具知识设计规范》中「工程模式 / 方法型」部分，以及旧工程专题规范中可独立复用的方法规则。  
**适用边界**：本扩展处理「遇到某类问题时，怎样设计和验证一种可复用做法」。具体产品或工具使用《技术对象》；覆盖多个方法和工具的问题域使用《工程专题》。

# 1. 工程方法位于问题与工具之间

工程方法通常不对应单一产品。它描述一组可以由不同工具实现的行为、约束或步骤。

```text
工程问题
→ 可复用方法
→ 一种或多种工具实现
→ 当前项目方案
```

例如「重试与退避」是方法，Tenacity 是一种实现工具，「模型接口超时后最多重试两次」是项目方案；「可观测性」则是包含结构化日志、指标、追踪等多种方法的工程专题。

# 2. 判断当前内容属于哪一层

| 层级 | 判断问题 | 示例 |
| --- | --- | --- |
| 机制 | 系统中客观发生了什么 | 请求失败、队列消费、状态转移 |
| 方法 | 面对一类问题，采用什么可复用做法 | 幂等、退避、检查点、结构化日志 |
| 工具 | 哪个具体实现提供这些能力 | Tenacity、Celery、OpenTelemetry |
| 专题 | 哪个问题域组织多种机制和方法 | 稳定性、异步任务、可观测性 |
| 项目方案 | 本项目选哪些方法与参数 | 重试两次后进入人工队列 |

一份方法文档可以引用工具和项目例子，但主语始终是方法本身。

# 3. 方法文档先定义问题形状

方法出现之前，先写清它反复面对的典型问题：

- 触发条件是什么；
- 哪些状态或参与者会受到影响；
- 失败后会造成什么后果；
- 哪些约束不能被破坏；
- 该问题是否值得引入额外复杂度。

例如幂等设计要先说明「同一个意图可能被执行多次」，重试要先说明「失败可能是暂时的」，结构化日志要先说明「系统需要将一次事件表达成可检索字段」。没有问题形状，方法容易退化成技巧清单。

# 4. 通用结构

工程方法笔记通常从以下结构中选取需要的部分：

```text
定位与适用问题
目标、保证与明确不保证的内容
前提条件
核心机制或步骤
状态、时序或决策点
主要变体
代价、风险与失败方式
实现选择与工具入口
最小实践和验证
当前完成标准
```

方法简单时可以压成短文；方法涉及状态、并发或失败恢复时，应明确状态和时序。

# 5. 目标与保证使用可验证语言

方法的目标要落到可观察结果。例如：

| 含糊说法 | 可验证说法 |
| --- | --- |
| 提高稳定性 | 暂时性失败时有限重试，持续失败时停止并暴露错误 |
| 防止重复 | 相同幂等键在有效期内只产生一次业务副作用 |
| 方便排查 | 每条日志包含请求标识、事件名和关键结果字段 |
| 做好评估 | 固定数据集、指标和版本后可以重复比较两次变更 |

同时写清方法不保证什么。重试不会修复确定性错误，幂等不等于事务原子性，结构化日志不自动等于完整可观测性。

# 6. 前提条件决定方法能否成立

很多工程方法只有在前提满足时才安全：

- 重试依赖失败分类、次数上限和副作用控制；
- 幂等依赖稳定的操作身份、结果保存或状态检查；
- 断点续跑依赖可恢复的中间状态；
- 缓存失效策略依赖数据新鲜度要求；
- RAG 评估依赖稳定数据集、评价维度和版本记录。

前提条件应该靠近方法定义出现。将前提埋到最后，会让读者先形成错误的普适印象。

# 7. 核心机制写成因果链或状态变化

方法涉及顺序时写清步骤，涉及状态时写清状态和迁移，涉及选择时写清决策条件。

例如有限重试可以概括为：

$$
\text{执行}
\rightarrow
\text{分类失败}
\rightarrow
\begin{cases}
\text{可重试且未达上限} & \rightarrow \text{等待后重试} \\
\text{不可重试或达到上限} & \rightarrow \text{返回失败}
\end{cases}
$$

如果并发参与者、超时和取消关系较多，使用时序图；如果状态集合明确，使用状态图。图只表达已经在正文确认的关系。

# 8. 变体按决策条件组织

方法的变体不按工具品牌排列，而按问题条件排列。例如重试可以按固定等待、指数退避、抖动和服务端提示组织；接口测试可以按单元、集成、契约和端到端的边界组织。

对比至少包含：

| 变体 | 适用条件 | 得到什么 | 付出什么 | 主要风险 |
| --- | --- | --- | --- | --- |

当多个做法能够组合时，说明组合关系；只有相互替代时才写成二选一。

# 9. 工具是实现入口

工具层回答「用什么实现」，不改写方法定义。工具表只保留定位所需信息：

| 工具或实现 | 承担哪一部分 | 适用环境 | 需要额外确认什么 |
| --- | --- | --- | --- |

工具 API、参数和版本差异链接到对象文档或参考页。项目采用的具体参数进入项目方案。

# 10. 最小实践验证失败与边界

方法型实践不能只跑通正常路径。至少选择一个能暴露方法价值的对照：

- 重复发送同一请求，观察幂等结果；
- 制造暂时性和确定性失败，比较重试行为；
- 中断 Worker 后恢复，观察任务状态；
- 删除关键日志字段，比较排查路径；
- 固定评估集后更换模型或 Prompt，比较指标变化。

实践记录运行条件、输入、预期观察和实际结果。当前只需建立概念位置时，可以省去实践，但应保留验证入口。

# 11. 方法进入专题和项目时保持边界

专题文档说明一种方法在整个问题域中的位置，并连接其他方法；方法文档解释它自己的前提、机制和取舍；项目方案记录实际选择。

例如：

```text
稳定性治理专题
├─ 超时控制
├─ 重试与退避方法
├─ 限流方法
└─ 熔断与降级方法

某项目稳定性方案
└─ 模型调用超时 20 秒，最多重试 2 次，指数退避并加抖动
```

项目案例可以进入方法文档作为例子，但不成为长期规则。

# 12. 完成标准

方法的停止线优先使用可执行能力：

- 能从真实症状判断是否适合使用该方法；
- 能说明方法依赖的前提和不保证的内容；
- 能画出或口述关键状态、步骤和失败分支；
- 能比较主要变体并说明选择条件；
- 能使用一种工具实现最小闭环；
- 能设计观察点验证方法确实生效；
- 能指出引入该方法后的新成本和风险。

# 13. 最终检查

1. 文档主语是否是一种可复用方法，而不是具体工具或整个专题？
2. 问题形状、目标、保证和不保证的内容是否明确？
3. 前提条件是否在方法展开前得到说明？
4. 核心机制是否表现为因果、步骤、状态或决策，而不是口号？
5. 变体是否按选择条件组织，互补关系和替代关系是否分清？
6. 工具 API 和项目参数是否留在各自层级？
7. 最小实践是否验证失败路径或边界，而不只验证成功路径？
8. 完成标准是否可观察、可操作？
