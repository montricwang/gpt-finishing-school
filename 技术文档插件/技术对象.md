# 技术对象

**状态：重组试行版**  
**用途**：用于框架、库、服务、中间件、平台、CLI、协议、测试工具、语言、DSL 和宿主扩展等具体技术对象的学习文档。  
**依赖**：《技术文档》  
**被依赖**：具体工具、语言、协议和平台学习笔记  
**替代**：旧《工程工具知识设计规范》中与具体技术对象有关的分类和模板部分。  
**适用边界**：本扩展处理「一个具体技术对象怎样工作」。幂等、重试、结构化日志等跨工具方法使用《工程方法》；缓存、异步任务、可观测性等问题域使用《工程专题》。

# 1. 先确认它是不是「具体技术对象」

具体技术对象通常有可识别的名称、实现边界和使用入口，例如 FastAPI、Pydantic、Redis、Docker Compose、HTTP、pytest、SQL、正则表达式、pgvector。

下面三类内容不在本扩展中展开：

| 内容 | 更合适的文档 |
| --- | --- |
| 幂等设计、重试退避、Worker 模式 | 工程方法文档 |
| 缓存、数据持久化、稳定性治理 | 工程专题文档 |
| 当前项目为什么选择 Redis、参数怎样配置 | 项目方案 |

对象既能作为独立工具学习，又能作为某个专题的实现时，可以保留两份文档：专题负责问题域和选择，工具文档负责该对象内部的抽象、机制和操作。两边通过引用连接，不复制整章内容。

# 2. 对象分类决定学习重点

| 类型 | 判断线索 | 主要学习单位 | 例子 |
| --- | --- | --- | --- |
| 框架 | 提供控制流和整体组织方式，应用代码嵌入其生命周期 | 生命周期、核心抽象、扩展点 | FastAPI、Celery |
| 库 | 由应用主动调用，通常嵌入当前进程 | 数据结构、函数 / 类、算法与边界 | Pydantic、FAISS、httpx |
| 服务 / 中间件 | 独立运行，通过网络、进程间通信或客户端连接 | 资源模型、协议、生命周期、部署边界 | Redis、PostgreSQL、RabbitMQ |
| 平台 / 声明式 / CLI | 通过命令或声明配置管理外部资源和运行环境 | 资源、配置、状态、执行计划 | Docker Compose、Kubernetes、Terraform |
| 协议 / 契约 | 规定参与者怎样交换信息或约束结构 | 角色、消息、字段、状态与兼容性 | HTTP、OpenAPI、gRPC |
| 测试 / 评测 / 压测工具 | 生成、执行、测量或判定结果 | 测试模型、夹具 / 场景、指标与判定 | pytest、Locust、k6 |
| 语言 / DSL | 通过语法表达计算、查询、匹配、配置或约束 | 语法、语义、执行模型、组合规则 | Python、SQL、Regex、PromQL |
| 宿主扩展 / 插件 | 依附宿主并通过扩展点增加能力 | 宿主边界、加载方式、扩展对象、版本耦合 | pgvector、PostGIS、RediSearch |

分类以主导使用方式为准。某个对象跨类时，先选最能解释其学习方式的一类，再说明次要身份。例如 SQL 既是标准也是 DSL，但学习主线通常从语法、语义和查询执行进入。

# 3. 共用完整性问题，不共用硬模板

一份具体对象笔记通常需要回答：

1. 它在系统中负责什么，边界在哪里？
2. 它要解决什么麻烦，替代了哪种原始做法？
3. 它提供哪些核心对象、资源、契约、语法对象或角色？
4. 这些对象怎样组合或运行？
5. 一次典型使用从输入到输出怎样发生？
6. 怎样用最小实践验证核心机制？
7. 它与相邻对象怎样区分，什么时候不适合使用？
8. 当前用途学到哪里可以停？

这些问题可以组织成章节，也可以融入连续正文。对象很小、当前只需建立位置感时，使用短文；对象复杂且会长期复用时，再形成完整专题。

# 4. 通用骨架

下面的骨架用于起草，不要求逐节保留：

```text
定位与边界
设计动机
核心对象 / 资源 / 契约 / 语法对象
工作机制 / 运行模型 / 语义模型
典型链路
最小实践与可观察结果
边界、取舍与相邻对象
当前完成标准
附录：命令、API、配置或语法速查
```

已经在前文得到回答的内容不再重复成章；没有实际内容的章节直接省去。

# 5. 不同类型的结构重心

| 类型 | 优先写清 | 常见误区 |
| --- | --- | --- |
| 框架 | 控制反转、生命周期、核心抽象、扩展点 | 写成 API 合集，忽略谁控制程序 |
| 库 | 输入输出、核心类型、组合方式、复杂度与边界 | 将库写成独立服务或完整架构 |
| 服务 / 中间件 | 资源模型、通信方式、持久性、并发与故障边界 | 只列客户端命令 |
| 平台 / 声明式 / CLI | 资源状态、声明与执行、幂等性、环境边界 | 只抄命令和配置文件 |
| 协议 / 契约 | 参与者、消息结构、状态、错误与兼容性 | 将实现细节误写成协议要求 |
| 测试 / 评测 / 压测工具 | 被测对象、场景、指标、判定和可重复性 | 只展示一次运行结果 |
| 语言 / DSL | 语法对象、语义、作用域、执行模型、组合规则 | 按命令清单学习，忽略表达能力 |
| 宿主扩展 / 插件 | 宿主前提、扩展点、加载链路、版本耦合 | 将插件当成完全独立的工具 |

# 6. 核心对象与机制分开写

「有什么」和「怎样工作」承担不同职责。

核心对象部分建立名词关系，例如 Redis 的 key、value、数据类型和过期时间；机制部分解释这些对象如何改变系统行为，例如过期检查、内存访问和持久化选择怎样影响结果。

对象表只在多个对象需要同维度比较时使用：

| 对象 | 负责什么 | 与谁关联 | 生命周期或约束 |
| --- | --- | --- | --- |

机制解释优先采用「问题—机制—例子—边界」：

```markdown
## 机制名

**问题**：没有这个机制时会出现什么麻烦。

**机制**：它怎样改变系统行为。

**例子**：用一个具体过程说明。

**边界**：它不能解决什么，依赖哪些前提。
```

# 7. 典型链路建立可运行的心智模型

典型链路选择最能代表对象工作方式的一条主路径。框架可以写请求生命周期，库可以写一次函数调用与数据转换，服务可以写客户端请求到资源状态变化，协议可以写消息交换，语言可以写源文本到求值结果。

链路中只保留理解所需的参与者和步骤。异常、重试、并发和扩展路径如果会遮蔽主线，先放到后续小节。

当链路同时涉及多个主体的时间顺序时使用时序图；涉及真实状态空间时使用状态图；只有一条短转换时直接使用正文或数学箭头。

# 8. 最小实践证明机制

实践应回答「我怎样知道它真的按上述机制工作」。除了运行成功，还应给出观察点。

例如：

- 修改 TTL 后观察缓存命中与过期；
- 去掉索引后比较查询计划；
- 修改协议字段后观察服务端响应；
- 改变 DSL 表达式后比较匹配或查询结果；
- 禁用插件后确认宿主能力的变化。

安装过程很长但与机制无关时，压缩为运行前提或移到附录。

# 9. API、命令和配置进入参考层

正文只保留教学所需的最小 API、命令、配置与语法。完整材料按对象类型进入相应参考层：

| 类型 | 参考层常见内容 |
| --- | --- |
| 框架 / 库 | 常用对象、函数、参数、异常 |
| 服务 / 中间件 | 命令、客户端调用、配置、运维入口 |
| 平台 / CLI | 命令、资源字段、配置样例 |
| 协议 / 契约 | 方法、状态码、字段、错误格式 |
| 测试工具 | 断言、夹具、场景参数、报告字段 |
| 语言 / DSL | 语法速查、运算符、函数、常见模式 |
| 宿主扩展 | 安装、启用、扩展对象、兼容版本 |

参考层帮助检索，正文帮助理解。参考层的存在不替代机制解释。

# 10. 相邻对象的边界通过真实选择说明

比较只选择可能造成误用的相邻对象，并使用同一维度：

| 对象 | 控制边界 | 运行位置 | 状态归属 | 适合场景 | 主要代价 |
| --- | --- | --- | --- | --- | --- |

「A 更强、B 更轻」之类评价需要落到可观察维度。版本、生态活跃度、价格和当前产品能力可能变化，写作时应标明时间或引用来源。

# 11. 拆分与合并

以下情形适合维持一份文档：

- 对象边界统一，读者需要连续理解；
- 命令和 API 仍可由短附录容纳；
- 各部分由同一生命周期或语义模型串联。

以下情形适合拆分：

- 主文已稳定，而速查材料高频变化；
- 某个子系统形成独立机制、独立实践和独立维护周期；
- 协议、客户端库、宿主和插件被混写后边界不清；
- 单篇文档同时服务入门、运维和 API 查询，导致三种阅读路径互相干扰。

拆分依据是职责和阅读路径，不使用固定字数作为唯一阈值。

# 12. 最终检查

1. 当前对象是否确实属于具体技术对象，而不是方法、专题或项目方案？
2. 类型判断是否解释了正文的结构重心？
3. 定位、动机、核心对象、机制、典型链路和停止线是否清楚？
4. 对象、机制和 API 清单是否分开承担职责？
5. 最小实践是否能验证机制，并提供可观察结果？
6. 工具是否被放回所属问题域，而没有被写成问题域本身？
7. 协议要求、实现选择和项目参数是否已经区分？
8. 宿主扩展是否说明宿主前提、扩展点和版本耦合？
9. 参考材料是否便于检索，又没有冲断主文？
10. 相邻对象的比较是否使用真实、稳定的维度？
