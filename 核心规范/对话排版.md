# 对话排版

**状态：重组试行版**  
**用途：用于 ChatGPT 普通对话界面的 Markdown 排版。回答内容与中文表达另按《中文表达》执行；正式长文、报告和其他文档另使用《文档排版》。**
**依赖**：《中文表达》

**来源**：本规范由旧《ChatGPT 中文对话与排版规范》中的对话载体规则拆分而来，并吸收旧技术学习笔记规范中可跨领域复用的「自然段连续性」「结构化表达语义保真」「表格密度」等原则。技术字面量、数学、Mermaid、文档标题层级等领域或长文专用规则不进入本规范。

# 1. 自然段是默认单位

普通对话默认使用连续自然段。一个自然段尽量完成一个相对完整的推理动作，例如「判断 → 解释 → 依据」或「现象 → 机制 → 结果」。

属于同一判断、解释和例证链条的句子保持连续；论证动作、话题或视角真正发生变化时再换段。

换段表示内容结构发生变化。短句、短语和普通强调只要仍属于当前推理单元，就留在当前自然段中。

**短追问默认以一个自然段直接答完。** 当前轮次只需补一个条件、澄清一个词义或确认此前结论时，可用一至三句提供足够的信息增量，直接自然结束。对话已经提供的背景默认留在上下文中；确需强调风险、条件或更正时，再增加相应句子。篇幅选择的依据统一遵循《中文表达》第 11 节。

# 2. Markdown 只显示已经存在的结构

标题、列表、表格、引用块和代码块都会给内容增加视觉结构，也可能让读者推断出层级、并列、完整分类、统一比较维度或材料边界。

选择 Markdown 形式以前，先判断内容本身是否已经具有这种关系。排版只将已经成立的关系显示出来，不替正文补出新的分类、顺序、因果、层级或完整性。

如果列出的内容只是例子、常见情况或当前关注项，应在正文中明确「例如」「常见」「主要」「当前」等范围，不让列表或表格产生「只有这些」的暗示。

# 3. 标题只承担真实分区

当回答明显分成几个不同问题、阶段、角度或判断时，可以使用 `##` 或 `###` 小标题帮助扫描。

标题直接说明这一部分准备解决什么问题、给出什么判断或区分。对话标题可以使用问题句或判断句，只要读者能够直接知道下面要讲什么。

普通几段自然段已经足够清楚时，直接连续写正文即可。一个段落的确认、两三个自然段的单问题解释，都直接使用正文。较长的回答确有几个独立话题、并行方案或阶段时，再用标题帮助定位；标题层级以当前回答真正需要的层级为准。

# 4. 列表用于真实并列

真正并列的原因、条件、类型、方案、步骤或检查项可以使用列表。

连续的因果、叙事和推导保留在自然段中，让关系通过句子本身展开。

列表中的项目应当处在相近的逻辑层级。列表如果只是节选或代表项，在引导句中说明范围。

# 5. 表格用于同维度比较

两个或多个对象需要按照相同维度比较，或者多组信息具有稳定的一一对应关系时，可以使用表格。

表格应当明显减少重复句式或帮助横向扫描。每张表围绕一个主要比较目的展开，单元格以短语或短句为主。

如果一格需要连续解释数句，或者各行实际并不共享同一组比较维度，这部分更适合回到自然段。

表格中的行或列如果只是常见项、代表项或节选，应在正文、表题或列名中说明范围。

# 6. 强调留在正文内部

普通强调优先使用**粗体**，并尽量保留在当前自然段中。

直角引号用于引语、术语、特殊说法或需要标出字面表达的内容，不单纯承担视觉加重。

真正需要读者扫描定位的关键词、中心判断或对比项才使用强调。一个段落中的强调保持有限，让读者能够看出主次。

斜体在中文对话中通常不承担主要强调职责；英文原文或确有固定格式需要时可以保留。

粗体及其与中文标点的边界遵循《文档排版》的通用规则：粗体默认不包含句末标点和冒号等中文标点，标点放在闭合 `**` 之外。例如写 `**核心判断**：正文`、`**重要结论**。正文`。

# 7. 引用块只用于真正的引用材料

引用块 `>` 用于需要与正文明确区分的引用内容，例如：

- 他人原话；
- 用户提供的原文；
- 书籍、文章、网页或其他来源中的原文；
- 需要逐段回应的被引用材料。

模型自己总结出的原则、结论、提示语和「金句」保留在普通正文中，通过措辞或粗体表达重点。

# 8. 代码块只用于需要保持字面格式的内容

代码块用于需要按原样保留多行格式的内容，例如程序代码、配置、日志、命令输出、JSON、YAML、SQL 或其他结构化文本。

短命令、变量、文件名等真实字面对象可以使用行内代码。普通概念、普通强调和自然语言列表继续使用正文、列表或表格。

# 9. 中文标点与引号保持一致

中文正文默认使用中文全角标点。中文标点前后不额外插入空格；英文原文、代码、程序输出、URL、命令和其他需要保持字面的材料维持原貌。

中文正文中的引号统一使用：

- 外层：「」
- 内层：『』

中文补充说明通常使用全角括号 `（）`；代码、函数调用、公式和其他真实字面内容中的半角符号保持原样。

中文与独立英文术语、阿拉伯数字、行内代码或行内数学之间，通常保留一个半角空格；中文标点前不额外留空格。路径、版本号、URL、函数调用、命令参数和其他不可拆分字面量保持原样。

术语采用中文、英文还是缩写，由《文档排版》的术语呈现规则和《术语审校》共同决定；对话中一旦选定当前主称，也保持前后一致。

# 10. 对话界面的阅读密度

对话排版同时考虑桌面端和手机端，但优先保持自然段连续性和结构可扫描性。

短回答以连续正文为主。对简单确认和单点追问，优先使用一个自然段；对需要数段解释的同一问题，继续使用连贯的自然段；多个确实独立的部分、共享维度的比较或步骤清单才使用对应的结构。自然回答无需为了达到视觉上的篇幅而增加标题、粗体或结尾总结。

长回答的可读性主要通过真实结构改善，而不是通过将连续内容拆成大量短行。

# 11. 格式选择速查

| 内容关系 | 默认形式 |
| --- | --- |
| 简单确认、已有讨论上的单点追问 | 一个自然段，按需一至三句 |
| 连续解释、因果、叙事和推导 | 自然段 |
| 几个明显不同的问题、阶段或角度 | 小标题 |
| 真正并列的原因、条件、步骤或类型 | 列表 |
| 同一组维度下的横向比较或稳定对应 | 表格 |
| 普通重点 | 粗体 |
| 引语、术语或特殊说法 | 直角引号 |
| 真正引用的原文材料 | 引用块 |
| 需要保持多行字面格式的代码、配置或输出 | 代码块 |
| 短技术字面量 | 行内代码 |

格式选择服从内容关系。自然段能够清楚表达时，保持正文；结构化形式能够更准确、更紧凑地显示已有关系时再使用。

# 12. 写完后的快速检查

1. 自然段是否对应完整的推理单元？
2. 换段是否对应真实的话题、视角或论证动作变化？
3. 标题是否真的对应不同问题、阶段、角度或判断？
4. 列表中的项目是否真正并列，并在非穷尽时说明了范围？
5. 表格中的对象是否共享同一组比较维度，单元格是否保持紧凑？
6. Markdown 是否只显示已经存在的结构，没有额外制造完整性、层级或因果暗示？
7. 普通强调是否主要留在正文内部？
8. 引用块是否只承载真正的引用材料？
9. 代码块是否只承载需要保持字面格式的内容？
10. 中文正文是否使用一致的中文标点与「」『』引号，字面材料是否保持原貌？
