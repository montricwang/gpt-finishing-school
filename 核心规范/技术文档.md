# 技术文档

**状态：试行修订版**  
**用途**：为技术学习文档提供通用的知识组织与表达结构规则。  
**依赖**：《中文表达》《文档排版》  
**被依赖**：《技术对象》《工程方法》《工程专题》《工程文档风格》  

## 1. 先判断知识对象，再选择结构

技术文档没有唯一骨架。写作前先判断当前主要对象：技术对象、工程方法、工程专题，还是项目方案。对象不同，结构重心也不同。

## 2. 技术学习文档要回答的稳定问题

无论对象类型如何变化，通常都要回答：

1. 它在系统中处于什么位置；
2. 为什么需要它；
3. 它依靠哪些对象与关系工作；
4. 一次典型过程怎样发生；
5. 当前用途学到哪里可以停。

这五项是检查维度，不是固定五章模板。

## 3. 机制先于清单

主线通常是：真实问题 → 约束与失败方式 → 核心机制 → 实现入口 → 验证与边界。

命令、API 和参数帮助操作工具，但不会自动形成机制理解。主文保留最小集合，完整清单进入附录或参考层。

## 4. 表达形式选择规则

### 4.1 一张总表

| 知识主任务 | 优先表达形式 |
| --- | --- |
| 建立概念 | 定义 + 简短解释 |
| 区分多个对象或角色 | 表格 |
| 说明明确步骤 | 短列表或流程图 |
| 说明多主体交接 | 时序图 |
| 说明状态、分支、生命周期 | 流程图 / 状态图 |
| 展示实际写法 | 最小代码 + 必要输出 |
| 比较错误与症状 | 诊断表 |
| 解释原因、边界、取舍 | 自然段 |

### 4.2 自然段不是默认终点

自然段负责连续解释，但并不覆盖所有知识。若对象职责、步骤、时序、状态或代码行为本应一眼可见，就不应只用自然段承载。

### 4.3 结构不能空转

采用表格、图、代码或公式时，必须比自然段更清楚；若某种结构不增加理解，就不要为了页面丰富而添加。

## 5. 组合表达

一个完整知识模块可以由多种结构合作表达。

### 5.1 常见组合

| 场景 | 建议组合 |
| --- | --- |
| 框架中的角色分工 | 定义 + 对照表 + 最小代码 |
| 协议或接口交接 | 对象表 + 时序图 + 一段解释 |
| 生命周期或作用域 | 局部图 + 对照表 |
| API 的日常写法 | 最小代码 + 关键输出/结果 + 一段解释 |
| 故障定位 | 现象 → 证据 → 下一步动作的诊断表 |
| 机制与变体验证 | 最小实践 + 可观察结果 + 一个变体实验 |

### 5.2 必要结构不得被压没

为了精简篇幅，可以删掉课堂故事和重复说明；但不得删掉：

- 第一次正式定义；
- 核心对象之间的关系；
- 关键步骤的顺序；
- 真正有用的最小代码；
- 判断机制是否成立所需的观察结果。

## 6. 代码、输出与实践

### 6.1 最小代码

代码示例应证明当前机制，而不是承担完整项目架构。优先保留能长期复用的最小例子。

### 6.2 关键输出

当读者需要知道「运行后应该看到什么」，输出、日志或响应样例与代码同等重要。只有代码而无观察点，学习闭环仍然不完整。

### 6.3 真实实践与教师示例分开

真实做过的实践、课堂示例代码、建议性的扩展实验，应在正式手册中清楚区分，不要混写。

## 7. 图形的职责

### 7.1 图只显式化已经成立的关系

图中的箭头、层级和位置会强化方向、先后、基数和完整性。只有在这些关系确已成立时才使用相应图形。

### 7.2 图形何时最有价值

以下情况优先考虑图：

- 多主体按时间交互；
- 生命周期、作用域或状态转换；
- 一段文字难以稳定恢复的对象关系；
- 诊断路径、排障链路。

### 7.3 图形不能取代一切

如果一句定义、一个表格或一段最小代码更清楚，就不要为形式而画图。

## 8. 正式术语的首次锚点与后续主称

### 8.1 常用英文缩写首次正式引入时，尽量同时给出英文全称与常用中文名称

如果技术社区通常直接使用英文缩写，而且该缩写有确定的英文全称和自然、稳定的中文译名，首次正式介绍时采用：

**英文缩写（English Full Name，常用中文名称）**。

例如：

- ASGI（Asynchronous Server Gateway Interface，异步服务器网关接口）；
- WSGI（Web Server Gateway Interface，Web 服务器网关接口）；
- HTTP（Hypertext Transfer Protocol，超文本传输协议）。

读者随后直接使用 ASGI、WSGI、HTTP 等社区常用主称，不机械重复全称，也不为了形式统一强迫后文改用中文译名。

### 8.2 根据实际主称，允许不同的首次锚定顺序

如果中文名称本来就是最常用的主称，可采用「中文名称（English Full Name，ABBR）」，例如「文件描述符（File Descriptor，fd）」。英文完整术语本来就是主称而不是缩写时，可写「Event Loop（事件循环）」，不虚构所谓的缩写展开。

产品、框架、库的专有名称，例如 FastAPI、Uvicorn、PyTorch，按官方名称书写；名称不是缩写时，不为了填满格式而编造英文全称或中文译名。

### 8.3 中文译名不稳定时，给释义，不造正式译名

确有多个流行译名、直译生硬或没有通行中文译名时，保留社区常用英文主称。首次出现时可在括号中给出简短中文释义，并按需注明它是解释而非固定译名；**不得为了满足三段式格式临时制造一个看似官方的中文术语**。

首次出现于标题、代码或章首总图时，可以在紧随其后的首次解释性正文中完整锚定；不必将冗长英文全称挤进每个图形节点。缩写本身不是代码标识时，不因为它是英文就使用行内代码格式。

## 9. 参考层与附录

完整命令、参数、字段、配置项、版本差异和大块样例，适合放入附录或独立参考层。正文负责连续理解，参考层负责检索。

## 10. 最终检查

1. 当前知识对象是否判断清楚；
2. 结构是否服从对象，而不是服从旧模板；
3. 是否先建立机制，再引入 API 或命令；
4. 是否为每个承重知识点选择了更合适的表达形式；
5. 是否存在本应一眼可见的关系被压进长段落；
6. 是否缺少最小代码、关键输出或诊断表；
7. 图、表、代码和正文是否各自承担独立职责，而不是重复翻译。
8. 常用英文缩写的首次正式引入，是否按需同时建立英文全称与稳定中文名称；中文译名不稳定时是否没有伪造正式译名？
