# 文档排版

**状态：重组试行版**  
**用途：适用于较长的 Markdown 文档、学习笔记、报告、说明文、专题文章及其他需要长期阅读和维护的结构化文本。正文语言默认遵循《中文表达》；本规范负责全文结构、章节关系与版式选择，具体领域的代码、公式、图表和术语格式由领域扩展另行规定。**  
**依赖**：《中文表达》
**编写依据**：《ChatGPT 规范编写元规范》  
**同级规范**：《对话排版》  
**替代范围**：承接旧《技术学习笔记 Markdown 排版与结构规范》中可跨领域复用的长文结构与排版原则；技术专用部分不进入本规范。

**来源**：本规范以旧《技术学习笔记 Markdown 排版与结构规范》的长文结构规则为主要基础，并吸收旧《ChatGPT 中文对话与排版规范》中的通用排版原则。旧技术学习笔记行文规范和术语规范仅用于迁移查漏；其中已经进入《中文表达》的内容不在本规范重复维护。

# 1. 文档先作为一个整体成立

长文不是若干独立回答的连续堆叠。写作时同时考虑当前段落、当前章节和整份文档三个层级。

每个章节承担明确职责，并与前后章节形成可解释的关系：前文建立后文需要的前提，后文在已有内容上继续推进。一个概念已经在前文完成定义时，后文直接使用；只有当前读者可能失去必要前提时，才做简短回接。

**全文优先按正面论证组织。** 开篇交代真实研究对象或问题，主体逐层建立事实、关系、论据与结果，再把有依据的反面观点放进确有争议或需要辨析的章节。读者阅读主线时应持续获得新的知识，不必每进入一节都先读一段假设性误解。具体句法与限定方式由《中文表达》第 3 节负责。

全文结构优先回答四个问题：

1. 这份文档主要给谁读，默认读者已经掌握什么？
2. 这份文档最终要让读者理解、判断或完成什么？
3. 为达到这个目标，哪些内容必须先出现？
4. 哪些内容只是补充、速查或延伸，可以放到后文或附录？

读者前提一旦确定，章节顺序、术语第一次出现的位置和解释深度都以这个前提为基准。章节数量、标题层级和篇幅服务于读者完成这份文档的主要任务。

较长文档首先应当能够从头到尾连续阅读。速查表、知识卡片、参数清单、问题索引和扩展案例属于第二层用途；它们可以帮助检索和复习，但不替代主文建立连续的理解或论证。

# 2. 文档结构只显示已经成立的关系

标题、列表、表格、编号、图、公式和其他结构化形式都会向读者暗示关系，例如层级、并列、顺序、完整分类、共同维度、因果或穷尽性。

结构化表达只压缩已经成立的内容关系。采用某种结构以前，先检查将它重新翻译成自然语言以后，是否仍然只得到正文已经支持的事实。

尤其注意：

- 分类树会暗示父子层级和分类范围；
- 编号会暗示稳定顺序或可引用结构；
- 表格会暗示各对象可以按同一组维度比较；
- 列表容易让读者理解为同一逻辑层级；
- 流程图、箭头和时间线会强化顺序、方向或因果；
- 集合式罗列容易产生「这些就是全部」的印象。

如果内容只是例子、常见情况、当前范围或节选，应在正文、标题或说明中明确范围。

> **结构负责显示关系，不替内容补出关系。**

# 3. 先确定全文骨架，再安排局部内容

较长文档优先先确定顶层章节，再进入小节和段落。

常见骨架可以包括：

- 问题或目的；
- 必要背景；
- 核心对象与概念；
- 机制、分析或论证；
- 结果、应用或影响；
- 边界、风险或例外；
- 总结、结论或后续工作；
- 附录与参考资料。

这些只是可选职责，不构成固定模板。文档根据内容选择真正需要的部分。

一个章节如果同时承担多个彼此独立的任务，可以继续拆分；一个章节只有少量内容时，优先检查它是否可以并入相邻章节。结构粒度以长期阅读和维护是否更清楚为准。

主文负责连续建立对象、关系、论证或叙事。高频速查信息、完整清单、扩展案例和个人问题记录如果会打断主线，就放到附录、索引或独立文件中。判断位置时先问：读者第一次连续读到这里，是否必须立刻知道这部分内容。

# 4. 标题表示文档的逻辑层级

标题用于定位内容在全文中的位置。标题层级越深，表示它越依赖上一级主题。

一般情况下：

| Markdown 层级 | 默认职责 |
| --- | --- |
| H1 `#` | 顶层章节或文档标题体系中的最高内容层 |
| H2 `##` | 顶层章节内部的主要主题 |
| H3 `###` | 机制、对象、论点或问题子块 |
| H4 `####` | H3 内确有长期维护价值的进一步拆分 |
| H5 `#####` | 少量复杂文档中的最后一级 |

当内容持续下钻到更深层级时，优先检查是否应该重组章节、拆分文件或将高密度信息移到附录。

标题本身直接说明这一节讨论什么。正式知识手册的章节标题默认使用稳定、可索引的**名词短语或主题短语**，例如「请求执行与并发」「应用组织与资源生命周期」。标题负责标明知识对象和范围，定义、判断、原因及结论由标题后的正文承担。

**不要将一整句解释、判断或带多个分句的结论直接当作常规章节标题**，也不把「为什么……」「……并不意味着……」作为正式手册的默认标题句式。问题驱动的课堂、FAQ 和确实以某一判断为论证对象的文章，可以按体裁使用问句或判断句；只有这种句式本身具有更高的定位、检索或辨析价值时才采用。

标题不承担普通强调。正文中的一个重点句保持在正文中，通过句法或粗体表达。

# 5. 文件名、文档标题与 H1 保持一致的层级关系

如果文件名已经清楚承担文档标题功能，正文可以直接从顶层章节开始；如果文档需要脱离文件名独立导出、打印或发布，可以在正文首部设置唯一的文档标题，再将后续章节整体下移一级。

同一份文档固定采用其中一种模式。

例如，文件名已经是「Python Runtime」时，可以直接写：

```markdown
# 1. Runtime 的定位
# 2. 程序怎样启动
```

需要独立发布时，可以改成：

```markdown
# Python Runtime

## 1. Runtime 的定位
## 2. 程序怎样启动
```

# 6. 编号用于定位，不作为装饰

章节编号适合需要长期维护、交叉引用或明确顺序的长文，例如手册、课程、规范和专题报告。

采用编号时保持同一体系，例如：

```markdown
# 1. 顶层章节
## 1.1 主要主题
### 1.1.1 子主题
```

较深层级只有在确有交叉引用价值时继续编号。短文、散文式文章、简单说明和不依赖编号定位的内容可以直接使用语义标题。

编号一旦成为文档定位系统，新增、删除或移动章节时同步检查引用关系。

# 7. 自然段承担连续解释

正文默认使用自然段。一个自然段完成一个相对完整的解释或论证动作，例如：

- 提出对象 → 解释作用 → 给出原因；
- 现象 → 机制 → 结果；
- 判断 → 依据 → 边界；
- 问题 → 回答 → 必要例子。

属于同一解释链条的句子保持连续；主题、论证动作或观察角度发生明显变化时再换段。

长文的可读性主要来自清楚的段落结构和章节关系，而不是将连续内容拆成大量短行。

正文措词、句法、术语进入方式和信息量默认遵循《中文表达》。

**论证段落优先采用「正面判断 → 具体依据 → 推出的关系或结果」的顺序。** 段首直接写本段新增的事实或判断；接着提供能够核查的对象、行动、数据或实例；末尾按需要交代适用范围或衔接下一段。比如写「系统论研究组成部分之间的相互作用。反馈使局部变化反过来影响后续过程……」，让读者先得到可用的知识。当文章的对象本身就是争议、误解或理论辨析时，可先准确陈述待讨论的观点，再按证据展开辨析。

# 8. 列表用于真实并列，正文负责连续关系

列表适合多个彼此独立、处于相近逻辑层级的项目，例如步骤、条件、类别、材料、检查项和行动项。

连续的因果、叙事、机制和论证保留在自然段中，让读者顺着句子理解关系。

如果列表只列常见项、代表项或当前关注项，在引导句中说明「例如」「常见」「主要」「当前」等范围。

列表项目较长、内部又出现多层解释时，优先检查是否已经需要改成小节、表格或正文。

# 9. 表格用于共享维度的比较和稳定对应

多个对象需要按照同一组维度比较，或者信息之间存在稳定的一一对应关系时，使用表格。

表格适合：

- 对象 × 属性；
- 状态 × 含义；
- 方案 × 条件；
- 时间 × 事件；
- 术语 × 定义；
- 问题 × 处理方式。

每张表围绕一个主要比较目的展开。列数和单元格长度以能够快速横向扫描为准。

如果某个单元格需要连续解释数句，或者不同行实际并不共享同一组维度，这部分回到正文会更清楚。

表格只展示当前范围。代表项、节选或非完整分类在表题、引导句或列名中明确说明。

# 10. 定义、术语和第一次出现的位置保持稳定

重要概念在全文中应有一个清楚的首次建立位置。

第一次正式引入时，根据内容需要完成：

1. 说明它在处理什么问题、对象或关系；
2. 给出正式名称；
3. 提供必要定义、公式、条件或最小例子；
4. 明确后文采用的主要称呼。

后文直接使用已经建立的名称。只有跨越较长篇幅、章节可以独立阅读或存在明显歧义时，再做简短回接。

同一概念在不同章节保持主要称呼一致。需要使用别名、缩写、译名或英文名称时，在首次出现处建立对应关系，后文按文档约定稳定使用。

# 11. 跨章节重复服务于导航，而不是重新讲一遍

长文允许有限重复，因为读者可能跨章节阅读，也可能在较长间隔后需要重新定位。

重复出现时承担明确功能，例如：

- 回接前文已经建立的前提；
- 在章节开头说明本节从哪里继续；
- 在结论中压缩全文真正得到的新判断；
- 在独立阅读的小节中补足最低必要上下文。

回接以最小充分为准。已经完整解释过的内容通过一句提醒、交叉引用或术语锚点恢复即可。

全文修改时检查同一结论是否在多个章节被分别完整解释；如果是，确定一个主要位置，其余位置改成引用、回接或删减。

# 12. 摘要、前言、导语和结论按文档用途选择

这些部分承担不同职责，不自动全部出现。

**摘要**用于让读者在不阅读全文时快速知道文档解决什么问题、采用什么范围或方法、得到什么主要结果。研究报告、分析报告和较长正式文档更常需要。

**前言或导语**用于说明写作目的、读者前提、范围和阅读方式。说明性文章的开头可直接使用「研究对象／观察到的现象 → 当前要解决的问题 → 本文的切入点」：例如「多个部件各自运行正常，组合后仍可能出现新的行为。本文讨论反馈关系怎样影响整体系统。」学习笔记或专题手册可以简短说明。

**结论**用于汇总全文真正得到的判断、结果、决策或后续动作。优先写本次研究实际支持的正面结论、证据仍存在的边界，以及确有必要的后续工作。正文已经自然收束、文档本身较短时，可以直接结束。

这些部分的内容与正文职责保持不同：摘要压缩全文，前言建立阅读条件，结论说明最终得到什么。

# 13. 章节开头和结尾只承担必要的导航

章节开头可以简短说明本节解决什么问题、承接哪个前提或为什么此时进入这一节。

章节结尾只有在需要：

- 压缩复杂论证；
- 明确得到的阶段性结论；
- 为下一章建立前提；
- 提供操作或决策结果

时再增加小结。

**段首与过渡承接已经取得的结果，再交代新增问题。** 例如上一节介绍了各个组件，本节研究它们之间的数据流，就可以从「组件之间通过以下接口交换数据」开始。需要引入不同观点时，先说明该观点由谁提出、依据是什么，再集中比较；真正出现错误理解时，可以在同一处使用明确的「A 与 B」对照。完成辨析以后，回到正面的事实、关系和后续论证。

长文的连贯主要由章节职责和内容顺序建立。章节结尾在确有阶段性成果时，用一句话给出已得到的新判断，并将它自然交给下一节。

# 14. 图、公式、代码和其他专业结构由领域规则补充

本规范只规定一个共同原则：专业结构应准确表达已经确认的关系，并与正文分工明确。

具体到：

- 代码与行内代码；
- LaTeX 公式；
- Mermaid；
- UML；
- 数据表；
- 引文格式；
- 脚注；
- 参考文献；
- 法律条文；
- 学术引用规范；

由相应领域扩展或任务规范决定。

正文负责说明这些结构为什么出现、读者应从中读出什么。专业结构负责压缩真正适合结构化表达的内容。

# 15. 引用、强调、标点和字面材料保持职责清楚

普通重点优先使用**粗体**，并保持在正文内部。

粗体默认不包含句末标点和冒号等中文标点，标点放在闭合 `**` 之外。写成 `**核心判断**：正文`、`**重要结论**。正文`，避免写成 `**核心判断：**正文`、`**重要结论。**正文`。这一规则同时作为 Markdown 渲染兼容性规则执行，不因粗体位于句首、句中或独立成句而改变。

中文正文中的引号统一使用：

- 外层：「」
- 内层：『』

真正引用他人原文、用户原文、书籍文章或其他来源材料时，可以使用引用块；引用范围和来源按任务需要标明。

代码块、预格式化文本或其他等宽结构只承载需要保持字面格式的材料。普通概念和说明继续使用正文。

中文正文默认使用中文全角标点，引号使用外层「」、内层『』。中文补充说明通常使用全角括号 `（）`；英文原文、代码、公式、URL、命令和其他需要保持字面的材料维持原貌。

## 15.1 中文、英文、数字与空格

中文与独立英文术语、阿拉伯数字、行内代码或行内数学之间，通常保留一个半角空格；中文标点前不额外留空格。例如：

```text
Python Runtime 运行在 User Space 中，并通过 `read()` 等接口访问文件。
```

路径、版本号、URL、函数调用、命令参数、正则表达式、公式、代码和程序输出属于不可拆分字面量，保持原样，不为了视觉统一人为插入空格。

中文普通并列优先使用顿号、逗号或「与」，不为了省字大量使用 `/`。已经形成稳定技术写法的 `I/O`、`Client/Server` 等保留原样。中文破折号使用 `——`，不使用半角连字符代替。

## 15.2 中文术语、英文术语与缩写

术语呈现遵循以下规则：

| 情况 | 首次出现 | 后续主称 |
| --- | --- | --- |
| 中文名称成熟、自然且常用 | 中文术语（English Term, ABBR） | 中文 |
| 英文在中文技术社区明显更常用 | 必要时使用 `English（中文解释）` | 英文 |
| 缩写已经成为常见称呼 | 全称与缩写建立一次对应 | 缩写 |
| 中英文都常见 | 建立一次对应 | 选择更符合当前语境的一种并保持一致 |
| 真实标识或字面量 | 保持原样 | 保持原样并使用代码格式 |

双语锚点服务于理解和检索，不要求机械中文化。Token、Tokenizer、Checkpoint、KV Cache、Batch、dtype、Benchmark、Serving、Kernel、LoRA、MoE、Prefill、Decode 等词按技术社区习惯和具体语境决定主称。术语是否使用准确、是否发生泛化和局部歧义，由《术语审校》进一步检查。

# 16. 附录承载高密度但会打断主线的内容

附录适合：

- 完整参数与命令速查；
- 大型术语表；
- 详细数据；
- 长清单；
- 推导细节；
- 扩展案例；
- 版本差异；
- 参考资料；
- 对主线有价值但阅读时不必立即展开的内容。

正文保留支撑当前论证和理解所需的最小充分内容，并在需要时指向附录。

附录仍然属于文档的一部分，标题、术语和引用关系与正文保持一致。

# 17. 长文修改时同时检查局部和全局

修改一段或一章以后，检查它是否改变了全文其他位置的含义。

重点检查：

- 标题层级和编号；
- 目录；
- 交叉引用；
- 首次定义位置；
- 术语和缩写；
- 图表编号与正文引用；
- 章节之间的前提关系；
- 摘要和结论；
- 同一事实在其他章节中的旧表述；
- 附录和速查表。

局部修改如果改变了概念边界、章节职责或核心结论，应继续向上游和下游检查相关内容，而不是只保证修改段落自身正确。

# 18. 文档拆分和合并依据职责变化

一个文件持续增长时，根据内容是否形成稳定的独立职责决定是否拆分。

适合拆分的信号包括：

- 某一部分已经可以独立阅读和维护；
- 它的修改频率明显不同；
- 它有自己的读者或使用场景；
- 它开始被多个文档复用；
- 当前文件的标题层级需要持续下钻才能容纳它。

多个短文件如果高度依赖同一上下文、经常一起修改、单独阅读意义很弱，可以合并。

拆分以后让依赖方向明确：公共规则或基础内容由多个下游文档引用；下游文档补充自己的特殊内容，不复制一份独立的公共规则。

# 19. 文档正文和维护信息分开

文档正文描述当前有效的内容。

普通知识文档优先使用稳定文件名。规范、审校手册和其他需要独立加载的插件文档，如果必须从文件列表中直接识别版本，可以在文件名末尾增加 `_vX.Y.Z`。正文标题和交叉引用仍然使用不带版本号的稳定名称。

现行目录只保留每份规范或插件的最新版本。旧版本需要追溯时移入历史目录，不与现行版本并列。版本日期、修改原因和编辑过程由历史文件、文件版本历史、Issue 或讨论记录保存，不在正文末尾继续维护版本日志。

文档头部只保留会影响当前使用的信息，例如状态、用途、依赖、被依赖和替代关系。过去为什么修改、模型曾经怎样失败、编辑过程中尝试过哪些方案，不持续占用现行正文。

# 20. 写完后的全文检查

完成或大幅修改文档后，依次检查：

1. 文档目标是否清楚，顶层章节是否都服务于这个目标？
2. 各章节是否承担不同而明确的职责？
3. 内容顺序是否满足前置关系，读者是否在需要某概念之前已经获得它？
4. 标题层级是否真实反映从属关系？
5. 编号是否仍然连续，交叉引用是否有效？
6. 自然段是否先写出新增的事实或判断，再提供具体依据；需要的反面观点是否集中在实际辨析的位置？
7. 列表项目是否真正并列，并在非穷尽时说明范围？
8. 表格中的对象是否共享同一组比较维度？
9. 结构化表达是否只显示已经成立的关系？
10. 重要术语是否有清楚的首次建立位置，后文称呼是否一致？
11. 跨章节重复是否承担导航或回接功能，而不是重新完整讲一遍？
12. 摘要、导语、章节小结和结论是否各自承担真实职责，且以正面研究结果为中心？
13. 附录是否承接了会打断主线的高密度内容？
14. 局部修改是否同步检查了目录、定义、术语、引用、摘要和结论？
15. 正文语言是否仍然遵循《中文表达》？
16. 中文标点、引号和字面材料是否保持一致？
17. 领域专用格式是否交给相应扩展规范处理？

# 21. 格式选择速查

| 内容关系或任务 | 默认形式 |
| --- | --- |
| 连续解释、因果、论证和叙事 | 自然段 |
| 全文的大主题分区 | H1 / H2 |
| 章内机制、对象或问题子块 | H2 / H3 |
| 真正并列的条件、步骤、类型 | 列表 |
| 共享维度的比较或稳定对应 | 表格 |
| 普通重点 | 粗体 |
| 引语、术语或特殊说法 | 直角引号 |
| 真正的引用材料 | 引用块 |
| 高频但打断主线的细节 | 附录 |
| 长期维护和交叉引用所需定位 | 编号 |
| 专业代码、公式、图形和引用格式 | 领域扩展 |

最终判断顺序是：

> **先确定内容关系，再选择结构；先保证全文职责清楚，再优化局部版式。**
